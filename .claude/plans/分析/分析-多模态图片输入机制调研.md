# 分析-多模态图片输入机制调研

- **日期**：2026-10-30
- **目的**：为 CLFCode 多模态图片输入设计提供对照证据——dsh（deepseek-harness）与 Claude Code CLI 如何处理图片输入、模型能力差异、历史回放与失败降级
- **上游动机**：用户实机发现 CLFCode 无法识别图片；经取证确认是宿主链路无多模态设计（见 `设计-多模态图片输入.md` §一）
- **用户实际用法（2026-10-30）**：准备图片目录 → 自然语言指路（"测试下放了图片，叫 dsh 桌面端"）→ 模型自己找目录/模糊匹配文件名 → 用 Read 工具读完整路径拿图。不是粘贴附件。

---

## 一、结论摘要

1. **dsh 与 Claude Code 的核心路线一致：模型通过工具读图**，不是客户端把图片塞进首条 user 消息。路径由模型自己定位，失败由模型自己重试/总结。
2. **模型能力是声明式元数据**（dsh 的 `inputModalities`），不是模型名硬编码；dsh 内置表中 flash 声明 `text+image`，pro 默认 `text`。
3. **失败一律软着陆**：dsh 的 `read_image` 在模型不支持时返回错误文本而非抛异常；历史图片在切到 text-only 模型时统一替换文字占位；Claude Code 的 Read 路线同样让模型自行处理识别失败。
4. **历史图片的两种控费策略**：dsh = 每轮重发 + 超预算卸载最旧（持久化）；Claude Code = 每轮重发 + 超限剥离最旧；社区工具则把历史图片降级为占位。CLFCode 用户已拍板「最近 3 轮保留」。
5. **协议差异**：dsh 直连 DeepSeek 走 Messages API（`{type:'image', source:{...}}`）；CLFCode 走 OpenAI 兼容 Chat Completions（`image_url`）。后者官方明确支持 user 消息带图；tool 消息带图 schema 允许但文档矛盾，**保守做法是工具消息保持文本、随后追加一条带图 user 消息**——dsh 官方序列化正是这样做的。

## 二、dsh（deepseek-harness）源码机制

> 调研范围：`E:\deepseek-harness`（pnpm monorepo，TypeScript）。以下均为源码证实，行号以调研时版本为准。

### 2.1 模型能力表（flash / pro 差异的源头）

`packages/llm/llm-deepseek/src/models.ts:8-23`

```ts
export const DEFAULT_MODELS: DeepSeekCatalogModel[] = [

    id: 'deepseek-flash',
    name: 'DeepSeek-V4.1-Flash',
    contextWindow: OFFICIAL_CONTEXT_WINDOW,
    inputModalities: ['text', 'image'],    // flash 声明图片输入
    ...
  },
  {
    id: 'deepseek-v4-pro',
    name: 'DeepSeek-V4-Pro',
    ...
    // 没有 inputModalities -> 默认 text-only

```

- 默认值与校验：`config.ts:88`（`.default(['text'])`）、`model-info.ts:52, 71-77`（未编目模型按 text-only）
- 能力也可来自服务端 `/models` 的 `input_modalities`（`listing.ts:172-199`、`listed-catalog.ts:49-73`）
- **没有任何按模型名比较 flash/pro 的分支**

### 2.2 图片入口：统一收敛到附件服务

5 条入口（Web 粘贴、拖拽、文件选择器、Host prompt 参数、`read_image` 工具），全部最终进入 `AttachmentStore`。关键的是第 5 条：

`packages/fs/tool-fs/src/read-image.ts:209-257, 270-275`

```ts
name: 'read_image',
description: 'Read a PNG/JPEG/WebP/GIF file and return the image itself. ...',
...
await assertImageCapableRoute(ctx, exec, args.file_path)
const data = await ctx.fs.readBytes(target, exec.signal, byteCap)
...
ref = await attachments.saveImage({ data, mediaType, name: basename(target.displayPath) })
```

- 产出两个内容块：文本信封 + `{ type: 'image', attachment: ref }`（`read-image.ts:193-198`）
- **能力门禁在工具内部**；不支持时走 `assertImageCapableRoute` 返回错误文本（见 2.4）

### 2.3 消息结构与序列化

`packages/llm/llm/src/types.ts:80-96`

```ts
export interface ImageBlock {
  type: 'image'
  attachment: ImageAttachmentRef   // sha256 内容寻址引用
  offloaded?: true                 // 已卸载：每轮只发占位文本
}
```

- 图片只允许在 **user 消息和 tool result**；assistant 不支持（`images.ts:49-51`、`serialize.ts:36`）
- 直连 DeepSeek 序列化：`{type:'image', source:{type:'base64', media_type, data}}` 或 `source:{type:'file', file_id}`（`llm-deepseek/src/serialize.ts:73-78`）；**无 `image_url`、无 `detail`**
- 图片前额外发一段模型可读的 handle 文本（`serialize.ts:65-78`）
- OpenAI `image_url` 转换在外部依赖 `pi-ai` 中（`node_modules/.../dist/api/openai-completions.js:949-955`），dsh 仓库内零命中

### 2.4 模型不支持时的分层处理

| 层 | 位置 | 行为 |
|---|---|---|
| Host prompt 准入 | `packages/api/session-controller/src/commands.ts:314-327` | 新 prompt 带图且模型无 `image` → 抛 `MODEL_DOES_NOT_SUPPORT_IMAGES`，提示换模型 |
| `read_image` 工具 | `packages/fs/tool-fs/src/read-image.ts:120-131` | 返回错误文本，**不抛异常**，模型可继续 |
| 发送适配器（第二道防线） | `packages/llm/llm-deepseek/src/images.ts:44-51` | `UNSUPPORTED_CONTENT` |
| **历史图片（软降级）** | `packages/llm/llm/src/index.ts:1105-1109` | `projectImagesForTextModel` → 文字占位 |

历史占位文案（`packages/llm/llm/src/content.ts:76-79`）：

```
[image omitted because this model accepts text only; attachment sha256:...]
```

> 关键：**切到 pro 不会因旧图报错**；新发图片才被 Host 拒绝。CLFCode 按用户定调把「新发图片」也改为软跳过，不硬拒绝。

### 2.5 限制与超限

- 源准入（`attachment-local/src/index.ts:34-46`）：50 MiB/图、20 张/消息、200 MiB/消息、64M 像素、65,535px
- 请求预算（`llm-deepseek/src/request-pricing.ts:20-31`）：单图 2 MiB、长边 4096px；inline 20 MiB、Files 128 MiB、600 张
- 超预算：**不截断**——持久化 `image/offload` 决策（最旧优先）后重试（`compaction-image-offload/src/index.ts:25-41`）
- 源准入超限：明确错误码（`TOO_MANY_IMAGES` / `IMAGES_TOO_LARGE` / `UNSUPPORTED_IMAGE_TYPE`）

### 2.6 持久化与历史回放

- 会话日志只存 `ImageAttachmentRef`：`attachmentId`（sha256）+ mediaType + bytes + width + height + name，**不存 base64、不存路径**（`session-format-v3-to-v4/src/system-message.ts:18-31`）
- 字节存内容寻址仓库：`DSH_HOME/attachments/v1/objects/<xx>/<sha256>`（`attachment-local/src/store.ts:51-54, 191-202`）
- 历史**每轮重发所有未卸载图片出现位置**，同一附件单请求内去重（`llm-deepseek/src/images.ts:38-61`）
- offload 是持久化表面事实，不是请求期临时裁剪（`content.ts:251-273`）

## 三、Claude Code CLI 机制

> 来源：官方文档、GitHub issue、社区实测（Claude Code 闭源，无源码）。用户已在 flash / pro 后端实测 Read 路线。

### 3.1 入口与载体

| 方式 | 机制 |
|---|---|
| 粘贴（Ctrl+V / Windows Alt+V） | 图片作为 base64 inline `image` 块进入 user 消息，显示 `[Image #1]` |
| 拖拽 | 同上 |
| 提示中写路径 | **宿主不自动附加**；模型调用 `Read` 工具，工具按扩展名返回图片视觉内容 |

- `Read` 工具：PNG/JPEG/GIF/WebP 返回 base64 图片内容；文本/PDF/notebook 分流；另有 128MB 硬限并自动缩放
- 新版把粘贴图落盘（`~/.claude/image-cache/` 或 `CLAUDE_CODE_TMPDIR`）并在消息中注入 `[Image: source: path]`，但请求体中仍带 base64（issue #91705 实测 800 个请求体确认）

### 3.2 历史与超限

- 会话 jsonl **存 base64**；每轮全量重发，靠 prompt caching 摊薄
- 图片过多/过大被判 `unprocessable` 时，从**最旧图片**批量剥离并重试（510 → 255 → 127 档），替换 `[media removed: request limit]`（v2.1.290）
- 不可处理图片 → 文字占位并重试（v2.1.142+）

### 3.3 限制

- 单图最长边 8000px；上下文中 >20 张时 2000–3000px；100 张/请求；约 5 MiB base64/图、32MB 请求体
- 格式 PNG/JPEG/GIF/WebP；BMP/TIFF/SVG 报错

### 3.4 不支持视觉的模型

- 无统一前置能力判定（自家模型都支持）
- 第三方网关接纯文本模型：API 200 但静默忽略，或硬拒绝（404 / 请求失败）
- 用户实测（flash / pro）：Read 路线不崩，最多提示识别失败，模型自行重试或总结

## 四、DeepSeek Chat Completions 协议证据

- **官方 schema**：`tool` 消息 content 允许 `string | object[]`（可含 `image_url` 内容块）；图片格式 JPEG/PNG/GIF/WebP
- **官方 vision 指南**：只描述 `user` 消息带图；`system`/`assistant` 返回 400；未提 `tool`
- **实测**（LiteLLM issue #44211）：直接向 `POST /chat/completions` 发送 `role:"tool"` + base64 `image_url` → HTTP 200 且正确识别（复测两次）
- **dsh 官方序列化**：tool 消息保持纯文本，工具结果图片作为**紧随其后的 user 消息**注入（`"Attached image(s) from tool result:"` + `image_url`），理由是不依赖未文档化的网关容忍度
- **结论**：CLFCode 第一版采用保守方案（tool 文本 + 追加 user 图片消息），跨 provider 最稳

## 五、机制对照

| 维度 | dsh | Claude Code | CLFCode 定案 |
|---|---|---|---|
| 图片入口 | 粘贴/拖拽/选择器 + `read_image` 工具 | 粘贴/拖拽 + `Read` 工具 | **工具读图为主**（扩展 `read_file`） |
| 路径定位 | 模型自己找 | 模型自己找 | 模型自己找（复用 list_directory/搜索） |
| 能力判定 | 模型表 `inputModalities` | 无前置判定 | 配置表 + `flash` 兜底 |
| 新请求不支持 | Host 硬拒绝提示 | 软失败 | **软跳过，不报错**（用户定调） |
| 历史不支持 | 静默文字占位 | 软失败 | 静默文字占位 |
| 历史控费 | 每轮重发 + 持久化卸载最旧 | 每轮重发 + 超限剥离 | **最近 3 轮保留**（用户已定） |
| 持久化 | sha256 引用 | base64 | **路径引用**（用户已定） |
| 超限行为 | 明确拒绝 / 卸载重试 | 剥离重试 | 工具返回错误文本（软失败） |
| 协议载体 | Messages API | Anthropic | **OpenAI Chat Completions + 追加 user 消息** |

## 六、对 CLFCode 的启示（设计输入）

1. **入口选工具读图**，用户已拍板；宿主不做路径解析。
2. **能力判定独立成函数**，配置表优先、`flash` 兜底；判定只影响「是否尝试发送」，不产生报错。
3. **失败三层软着陆**：工具层跳过 → 发送层降级重试 → 历史层文字占位。
4. **协议保守**：tool 消息文本 + 追加 user 图片消息；不赌 tool content 数组带图。
5. **持久化路径引用**（用户已定），发送时按需读取；文件丢失降级文字。
6. **历史最近 3 轮**（用户已定），超出降级文字占位。
7. **复用现有工具链**：`list_directory` / `search_content` 负责定位，`read_file` 扩展图片识别；不新增目录遍历/模糊匹配逻辑。
