# 分析-复制粘贴功能修改

日期：2026-08-17

## 一、需求

| # | 现状问题 | 期望 |
|---|---------|------|
| 1 | 复制：Shift+拖选+右键（终端原生）复制的是**渲染网格**，逻辑换行全部丢失——软换行处无 `\n`，只有渲染行尾才有 | 复制出来的文本换行正确（等于逻辑文本） |
| 2 | 粘贴：Ctrl+V / Shift+右键（终端原生）多行粘贴时，**每一行触发一次提交** | 多行粘贴原样插入输入框，Enter 时一次性提交 |

用户决策（2026-08-17）：
- 复制：**应用内选区模式**（全量方案，键盘/鼠标选择任意显示内容）
- 粘贴：**双通道接管**（Ctrl+V 与 Shift+右键）

## 二、根因链

### 问题 1（复制换行错误）
应用内无任何复制代码（grep 证实）→ 复制完全由终端模拟器完成 → 终端只认识渲染后的字符网格 → 软换行（视口宽度截断）在网格中与硬换行无法区分 → 逻辑换行丢失。**终端原生拖选复制无法修复，必须在应用内做复制入口。**

### 问题 2（粘贴逐行提交）
Windows Terminal 拦截 Ctrl+V / Shift+右键 → 剪贴板文本以 KEY_EVENT 批量写入控制台输入缓冲（`\n` → `VK_RETURN`）→ FTXUI 转成 `Event::Return` → `CLFRepl.cpp:414` CatchEvent 对每个 Return 一律走提交分支 → N 行粘贴 = N 次提交。

## 四、方案轮廓

### A. 粘贴：事件突发合并器（CLFPasteCoalescer）

**原理**：两条通道的粘贴都走同一条事件路径（字符 + Return 突发批次）。同一 `ReadConsoleInput` 批次内事件间隔 μs 级；人手键入 >100ms。**用时间戳区分"粘贴换行"与"回车提交"——不读剪贴板、不依赖终端协议、不 patch 3rdparty，双通道天然覆盖。**

状态机三态：
- `IDLE`：正常处理
- `PENDING_SUBMIT`：Return 到达 → 暂不提交，进入 40ms 宽限窗（文本保留在输入框）
- `PASTE_MODE`：宽限窗内来了 Character **或 Return**（后者为粘贴含空行的特征，恢复文本补两个 `'\n'`）→ 撤销待提交，进入粘贴态；此态内 Return = 插 `'\n'`（复用 Ctrl+N 机制）；静默超阈值后懒退出回 IDLE
- 时间来源：Event 无 timestamp 字段，合并器在 CatchEvent 处理时记录 `steady_clock::now()`（同批次连续处理，时差近似成立）

行为特性：
- 单行粘贴带尾 `\n`：40ms 内无后续事件 → 正常提交（与手打回车等价，符合直觉）
- 多行粘贴：宽限窗内后续字符必达（同批次 μs 级）→ 全部并入输入框，一次性提交
- 宽限窗计时用 40ms 线程（项目已有 `m_escTimer` 模式）；合并器为纯状态机对象，**注入时钟可单测**
- 误判面：人手"回车+40ms 内再打字"概率极低；即使误判也只是把一次提交变成换行插入，可恢复
- 粘贴在确认栏激活期：confirm 屏蔽所有事件（既有行为），粘贴文本被吞——与现状一致，不改

### B. 复制：应用内选区模式

**核心构件**：
1. **行映射表 RowMap**：渲染器建 `allLines` 的同一趟循环里并行生成
   ```
   RowInfo { Kind(kind), size_t lineIdx, size_t partIdx, size_t byteStart, size_t byteEnd }
   Kind ∈ { Content, Pending, ThinkingFold, ThinkingLine, FoldSummary, FoldLine, Progress, Status, ScrollHint }
   ```
   每个渲染行记录"来自哪个逻辑行的哪个字节区间"——选区坐标回溯的依据。ScrollHint 行不可选。
2. **选区状态机**：锚点 + 游标（渲染行坐标），归一化区间。鼠标左键拖拽进入/扩展；键盘进入快捷键（候选 Ctrl+S，注意终端 XOFF 风险，spike 顺带验证）；方向键/Home/End/PgUp/PgDn 移动游标；Esc 取消；Enter/Ctrl+C 复制并退出；确认栏激活时屏蔽。
3. **高亮渲染**：选区覆盖的行拆三段（前/选/后），选区段 `| bgcolor(...)`——行由应用自建 Elements，天然可行。
4. **复制拼接**：按 RowMap 回溯——**同一逻辑行的多个 part 拼接不加 `\n`，跨逻辑行才加**（否则硬换行点会引入假换行）；拼接结果 `CLFClipboard::write`。
5. **坐标换算**：鼠标 `(x, y)` → 可见窗口行（y-1，减滚动提示行偏移）→ 列→ 字节偏移（displayWidth 逆向走查，CJK 感知）。

**覆盖范围**：全部显示内容（助手回复、用户消息、工具输出、思考展开行、折叠块展开行、进度行、状态行）——与"所见"一致。

## 六、风险与取舍

| 风险 | 应对 |
|------|------|
| 合并窗阈值误判（人手极快键入） | 40ms 阈值 + 注入时钟单测 + 误判可恢复（仅换行 vs 提交差异） |
| 选区与滚动联动（拖拽越界自动滚动） | 一期不做：滚轮可滚动（既有），拖拽越界滚动列二期 |
| CJK 宽度：4 字节 emoji 计宽 2 与多数终端一致；组合字符不精确 | 接受（显示本身即如此） |
| pendingLine 按字节 wrap 与主内容按显示宽度 wrap 不一致（既有） | 行映射表跟随现有逻辑，不顺手重构 |
| FTXUI Input 组件对鼠标点击的处理（点击定位光标） | CatchEvent 先拦截选区相关事件即可，spike S1 顺带观察 |

## 八、结论

两条需求均可行，且底层设施意外齐备（CLFClipboard 早已就位、鼠标事件链路已通）。粘贴走事件突发合并（无协议依赖、双通道天然覆盖）；复制走应用内选区 + 行映射回溯（换行正确性由逻辑拼接保证）。风险集中在终端行为细节，spike 一次性覆盖。**建议：spike → 设计文档（多轮审查定稿）→ 实现。**
