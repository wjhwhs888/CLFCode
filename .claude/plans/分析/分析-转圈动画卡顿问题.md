# 转圈动画卡顿问题分析

> 2026-09-09 调查记录。状态：**待用户回来一起讨论**（用户有事暂离）。
> 本文档记录问题现象、已完成的调查结论、验证方案与候选修根方向，供讨论使用。

## 一、问题现象

- **用户报告**：执行命令后面的转圈显示、Working 前面的转圈显示——"不是以前的丝滑显示了，而是卡顿的"。
- **时间点**：v0.7.3（commit `f49465b`，2026-09-08）发布后观察到。
- **涉及的两处转圈**（`src/CLFUI/CLFReplView.cpp`）：
  - 进度块末行的动画帧（`CLFReplView.cpp:307-308`，执行中态）
  - 状态行 Running 状态点（`CLFReplView.cpp:320-321`，"Working" 前面的转圈）
  - 两处**共用同一个 frame 变量**（P1-1 帧计算上提设计）。

## 二、调查结论一：转圈渲染逻辑本身零改动

git 历史证据：

- `CLFReplView.cpp:296` 的 `kSpinFrames`（⠋⠙⠹⠸⠼⠴⠦⠧⠇⠏）及帧计算
  （`frame = nowMs / 100 % 10`，`CLFReplView.cpp:297-299`）自批次 A1 拆分
  （commit `d6cc79b`，`Renderer→CLFReplView` 纯搬移）**创建以来零改动**
  （`git log -L 293,341:src/CLFUI/CLFReplView.cpp` 仅一条记录）。
- 动画驱动 Timer（CLFAgentLoop.cpp:112-122 的 Timer #2，1Hz `requestRefresh`）自
  v0.3.x 时代（2bfc19a）存在，v0.4.1（c42af0d）仅改退出机制（sleep 轮询 → 条件
  变量），**驱动频率语义未变**。

**但是**：昨天（2026-09-08）的 `f49465b`（v0.7.3）动了渲染管线底层三处，是转圈
观感变化的最大嫌疑（见 §四）。

## 三、转圈动画的完整机制（因果链）

转圈是**纯事件驱动**动画（`CLFReplView.cpp:294` 注释自证："事件驱动，无定时器
线程——流静止则动画静止"）：

```
frame 序号 = steady_clock::now() / 100ms % 10   —— 只在重绘时计算（CLFReplView.cpp:297-299）
                          ▲
                          │ 重绘触发链（FTXUI 内部，3rdparty/ftxui/.../app.cpp）
                          │
emitContent/showProgress 等 ──► CLFTerminal::requestRefresh()（CLFTerminal.cpp:50-52）
                          │        = m_screen->PostEvent(Event::Custom)
                          ▼
               PostEvent（app.cpp:1534-1537）
                          │ RequestAnimationFrame（app.cpp:1551-1561，33ms hysteresis）
                          ▼
               animation_requested_ = true
                          │ ≤15ms 后
                          ▼
               PostAnimationTask 每 15ms 推 AnimationTask（app.cpp:1418-1425，66fps 自循环）
                          │ 处理时 animation_requested_==true 才继续（app.cpp:932-934）
                          ▼
               OnAnimation → frame_valid_ = false（app.cpp:941-943）
                          │
                          ▼
               下一次 RunOnce 的 Draw 实际重绘（frame_valid_==true 时 Draw 直接 return，
               app.cpp:1004-1006）→ 转圈帧更新
```

**关键事实**：

1. **每个 PostEvent 只产生一帧重绘**（`animation_requested_` 在 AnimationTask
   处理时被消费置 false，app.cpp:936）。组件树里没有 FTXUI 原生 animation 装饰器
   （转圈是手算 frame 的静态 text），`OnAnimation` 不会为转圈请求下一帧。
2. **帧率 = 事件频率**：
   - LLM 流式输出期：每 chunk 一个 PostEvent → 高频 → 丝滑；
   - 工具执行期有持续输出（build、下载等）：中频 → 尚可；
   - **静止期**（安静命令、等待 LLM 首字节）：唯一兜底 = Timer #2 **1Hz**
     `requestRefresh()`（CLFAgentLoop.cpp:120-121，注释："F13: 1Hz 驱动——工具
     执行期无流式事件，靠此修复界面冻结 + 动画最低帧率"）→ **1fps，秒跳一帧，
     肉眼即卡顿**。
3. FTXUI 主循环节奏与 alt screen 无关：`FetchTerminalEvents` 在 Windows 上非阻塞
   （GetNumberOfConsoleInputEvents 轮询，app.cpp:1304-1335），`RunOnceBlocking`
   由 15ms 周期的 AnimationTask 自驱动（app.cpp:840-860）。

## 四、f49465b（v0.7.3）动的三处渲染管线底层

| # | 改动 | 位置 | 内容 |
|---|------|------|------|
| 1 | **alt screen 切换** | `CLFRepl.cpp:137` | `FullscreenPrimaryScreen()` → `Fullscreen()`。目的：跳过 primary 模式下每 500ms 的 CPR 光标查询（Draw 的 `!use_alternative_screen_` 条件，app.cpp:1066），修 CLion 中文输入抖动。行为变化：退出后屏幕恢复，对话不在终端滚动历史（用户已接受）。 |
| 2 | **帧尾光标 CUP 绝对定位** | `3rdparty/.../app.cpp:1087-1095` | 相对移动序列（`ESC[nA/nD`，dy/dx==0 时零输出）→ 无条件两条 CUP（帧尾 `ESC[y;xH` 到输入框 + 帧头 `ESC[dimy;dimxH` 回右下角）。目的：修 JediTerm autowrap 边界偏差。 |
| 3 | **输入光标 Blinking → 稳态** | `3rdparty/.../input.cpp:101-110` | `focusCursorBarBlinking/BlockBlinking` → 稳态 `Bar/Block`。目的：光标闪烁节奏与帧率解耦。与转圈无直接关系。 |

FTXUI 内部的动画/事件/重绘链路（§三）**不依赖 alt screen 模式**——改动 #1 影响的
是**终端渲染路径**（ConPTY → JediTerm 对 alternate screen 内容的 repaint 策略）。

## 五、嫌疑点排序与初步判断

| 嫌疑 | 判断 | 理由 |
|------|------|------|
| ① alt screen 切换 | **最大嫌疑** | 转圈代码与事件链均未变，唯一系统性变化是绘制模式。JediTerm/ConPTY 对 alt screen 的渲染路径与 primary 不同，可能放大每帧渲染成本或改变 repaint 策略。需 A/B 实证。 |
| ② CUP 每帧无条件输出 | 次级嫌疑 | 每帧多 2 条 CUP 转义（字节量微小），但若 JediTerm 对光标移动触发额外 repaint，会放大渲染成本。 |
| ③ 观察场景事件流变稀 | 待排除 | 若观察时命令恰好安静输出 / LLM 无流式首字节，天然 1fps（§三.2 机制自证）。需固定场景对比。 |
| ④ 渲染负载渐进增长 | 可能性低 | 行映射每帧重建（CLFReplView.cpp:140-162），内容多时帧耗时长；但这是渐进性影响，不匹配"突变"。 |

## 六、验证方案（用户回来后执行）

1. **V1 A/B 最快验证**（改动一行，重建即可）：`CLFRepl.cpp:137` 临时改回
   `FullscreenPrimaryScreen()`，在**同一场景**（同一安静命令 / 同一 Working 期）观察：
   - 转圈恢复丝滑 → 根因 = alt screen 切换 → 进入 §七 D2/D1 路线；
   - 依旧卡顿 → 根因不在 alt screen，转 V2 取证。
2. **V2 取证量化**（memory：terminal-forensics 两步取证法）：
   - `CLF_DEBUG_EVENTS=1` 事件日志 → 量化事件流频率（每秒 PostEvent 次数）；
   - stdout 重定向捕获 VT 流 → 数转圈字符变化频率，客观对比 v0.7.2 / v0.7.3。
3. **V3 版本对比**：v0.7.2（7496140）与 v0.7.3（f49465b）同一安静场景各跑一次，
   排除场景因素。

## 七、候选修根方向（讨论素材）

- **D1（若保留 alt screen）**：为转圈加运行期高频驱动——Running 状态期间以
  ~100ms 周期 PostEvent（复用 Timer #2 或独立周期定时器，仅 Running/进度可见时
  驱动，静止即停——不违背"流静止则动画静止"的设计初衷，改为"转圈可见则驱动"）。
  成本最低，但需确认高频 PostEvent 不会重新引入 v0.7.3 修掉的问题（IME 抖动源是
  CPR 查询而非 PostEvent，理论上无冲突）。
- **D2（回 primary + 单独关 CPR）**：patch `app.cpp` 使 CPR 查询可配置关闭
  （`!use_alternative_screen_` 条件外再叠加应用开关），保留 primary 渲染路径的
  同时消除 IME 抖动源。改动侵入 3rdparty，但比整屏切 alt 更精准。
- **D3（接受现状）**：若用户认为静止期 1fps 可接受（转圈仍在动、只是不丝滑），
  仅记录为已知行为，不做改动。
- 若 V1/V3 证明是场景/事件流因素（嫌疑 ③）而非 v0.7.3 回归 → 无需修根，仅记录。

## 九、调查结论落地（2026-09-09，实施完成）

### 转圈卡顿真根因（推翻 §五 嫌疑 ①）

A/B 实证四组数据：primary+CPR 开=丝滑 / alt+CPR 关=卡顿 / primary+CPR 开=丝滑 /
**primary+CPR 关=卡顿**——转圈丝滑的真正驱动是 **CPR 周期查询的往返事件流**
（响应字节与事件管线交错形成无心插柳的重绘心跳，§三.2 静止期 1fps 即无此
心跳的结果）。alt screen 只是"顺带关闭 CPR"的帮凶。

### 修复（D4 定案）

1. 回 primary 屏幕 + `TrackCursorPosition(false)` 精准关闭 CPR 周期查询
   （IME 抖动修复保持；首帧与 resize 保留 force 校准，3rdparty patch）。
2. 转圈显式动画驱动：runTurn Timer 1Hz → 50ms（20Hz），setStatusTextOnly
   按秒去重——不再依赖 CPR 意外心跳，回合结束即停。
3. 附带撤销 v0.7.3 行为变化：退出后对话恢复保留在终端滚动历史。

### 拖选校准（外部终端）

CPR 响应校准不可靠后改为 **Windows 自校准**：`GetConsoleScreenBufferInfo`
光标 − 帧尾 CUP 目标（LastFrameCursor，3rdparty 新增捕获）= frame 原点；
修正公式 `x + CursorOffsetX − origin` 与 CPR 校准幂等（外部终端 CPR 正常
时同样正确）。

### CLion(JediTerm) 拖选偏移（用户定案：接受局限）

取证链：CPR 查询发出零响应（首帧与启动稳定后均实测）→ JediTerm 的 SGR
鼠标 y 含**内部行号计数偏移**（4~6+，每次启动增长约 +2——`\033[3J` 清屏
不清计数、ConPTY 缓冲=视口 27 行、全部程序侧信号不可测）→ **默认补偿 5
（用户实测定案：CLion 拖选对齐）** + `CLF_MOUSE_OFFSET_Y` 环境变量精确
校准，仅 `TERMINAL_EMULATOR=JetBrains-JediTerm` 探测命中时生效（外部终端
零影响）。已知局限：向上滚动终端视口后需滚回底部再拖选。

### 未走路线备忘

- D1 高频驱动（配合 alt screen）——被 D4（primary + 驱动）取代
- MOUSE_EVENT 输入通道改造（关闭 VT 鼠标输入走传统事件）——彻底修根候选，
  但需改造 FTXUI 输入管线，中文输入/键盘行为有回归风险，用户未选
- `\033[3J` 清滚动缓冲——实证生效但不清 JediTerm 行号计数，无法稳定偏移
