# CLFCode 输入事件架构分析

## 一、评估标准（基于 Qt 设计模式）

| # | 原则 | 说明 |
|---|------|------|
| 1 | **模块职责单一** | 每层只管自己的事；不改事件模块就不碰事件模块 |
| 2 | **修改隔离** | 改功能逻辑时不波及事件分发，改绘制时不波及业务 |
| 3 | **扩展开放/修改关闭** | 新增功能参照现有模式，新增文件或针对性改动，不影响已有 |
| 4 | **用户操作可控** | 快捷键可配置、输入行为可覆盖，防止终端误操作 |

## 二、当前架构分析

### 2.1 已有做得好的

| 模块 | 职责 | 单一性 | OCP |
|------|------|--------|-----|
| `CLFConsole` | 原始键盘读取（`_getch`/`readKey`） | ✅ | — |
| `CLFTerminal` | 纯终端渲染（颜色/布局/输入区绘制） | ✅ | — |
| `CLFAgentLoop` | API + 工具调用闭环 | ✅ | — |
| `CLFCommandDispatcher` | 斜杠命令注册表（新增命令只加注册） | ✅ | ✅ |
| `CLFAnsi` | ANSI 颜色/尺寸原语 | ✅ | — |
| `CLFScrollBuffer` | 线程安全滚动缓冲 | ✅ | — |

### 2.2 问题——CLFRepl::run() 违反 SRP

```
CLFRepl::run()  ~200 行，混合 4 种职责：

  ┌─────────────────────────────────────┐
  │  缩放轮询检测  │  应属于输入/事件层  │
  │  按键读取      │  应属于输入层      │
  │  switch(key)   │  应属于事件→动作映射│
  │  状态变更      │  应属于业务层      │
  │  绘制调用      │  应属于渲染触发    │
  └─────────────────────────────────────┘
```

### 2.3 当前输入处理的修改半径

以"新增 Delete 键删除光标后字符"为例，需要改动：

```
CLFConsole.hpp    → 加 CLFKey::Delete
CLFConsole.cpp    → 加 _getch 映射
CLFRepl.cpp       → 加 case CLFKey::Delete: 逻辑
                     （涉及 m_input.erase / m_cursorPos / drawInputArea）
══════════════════════════════════════════
        3 个文件，2 个模块层级
```

### 2.4 缺失的模块

| 层级 | 当前 | Qt 对应 |
|------|------|---------|
| 原始输入 | `CLFConsole::readKey()` | `QKeyEvent` |
| **事件→动作映射** | **❌ 不存在，嵌入在 switch 里** | `QShortcut` / `eventFilter` |
| 动作分发 | `CLFRepl::run()` switch | `signal/slot` |
| 状态管理 | `m_input` / `m_cursorPos` 散落 | `QTextEdit` model |
| 渲染触发 | 直接调用 `CLFTerminal::drawInputArea()` | `update()` → `paintEvent()` |

## 三、建议方案：新增 `CLFInputHandler`

### 3.1 目标架构

```
CLFConsole              ← 原始输入（不变）
    │ CLFKeyEvent
    ▼
CLFInputHandler  [新增] ← 事件→Action 映射表
    │ Action 枚举
    ▼
CLFRepl                 ← 纯编排（大幅瘦身）
    │
    ├──► CLFAgentLoop   业务逻辑
    └──► CLFTerminal    渲染输出
```

### 3.2 核心设计

```cpp
// ==== 动作枚举（语义级，不绑定具体按键）====
enum class InputAction {
    None,
    InsertChar,      // 插入字符
    DeleteBefore,    // 退格（光标前删除）
    DeleteAfter,     // Delete（光标后删除）
    MoveLeft, MoveRight, MoveUp, MoveDown,
    MoveHome, MoveEnd,
    Submit,          // 提交输入
    NewLine,         // 插入换行
    ClearInput,      // 清空
    CycleMode,       // 切换安全模式
    Interrupt,       // Ctrl+C
    ExitApp,
};

// ==== 按键和弦 ====
struct KeyChord {
    char ch;       // 普通字符
    CLFKey key;    // 特殊键
    bool shift, ctrl, alt;
};

// ==== 映射表 ====
class CLFInputHandler {
    std::map<KeyChord, InputAction> m_actionMap;
    
    // 将原始 CLFKeyEvent → InputAction（查表）
    InputAction map(const CLFKeyEvent& ev);
    
    // 运行时修改映射（未来可读配置文件）
    void rebind(KeyChord chord, InputAction action);
};
```

### 3.3 CLFRepl 瘦身效果

```cpp
// 之前 ~200 行 switch，之后 ~30 行分派：
while (true) {
    auto key = CLFConsole::readKey();
    auto action = m_inputHandler.map(key);
    applyAction(action, key.m_utf8);
    // applyAction 内部修改 m_input/m_cursorPos，然后触发 CLFTerminal
}
```

### 3.4 改动范围

| 文件 | 操作 | 影响 |
|------|------|------|
| **新增** `CLFInputHandler.hpp/cpp` | 创建 | 150 行新代码 |
| `CLFRepl.hpp` | 加 `m_inputHandler` 成员 | +2 行 |
| `CLFRepl.cpp` | switch 替换为 applyAction | ~140 行简化 |
| `CLFConsole.hpp` | 不变 | — |
| `CLFTerminal.cpp` | 不变 | — |
| `CLFAgentLoop` | 不变 | — |

## 四、对照四项原则的改善

### 4.1 模块职责单一

| 之前 | 之后 |
|------|------|
| `CLFRepl::run()` 管按键解析+分派+业务+绘制 | `CLFRepl::run()` 只管编排 |
| 按键→业务逻辑耦合在 switch 里 | `CLFInputHandler` 专门做映射 |
| 无法单独测试映射逻辑 | `CLFInputHandler` 可独立单元测试 |

### 4.2 修改隔离

```
新增快捷键：
  之前: 改 CLFConsole(枚举) + CLFConsole(检测) + CLFRepl(switch) = 3 文件
  之后: 改 CLFInputHandler(加一行映射) = 1 文件

改输入行为：
  之前: 改 CLFRepl switch case 内部逻辑
  之后: 改 applyAction 对应 action 分支
```

### 4.3 扩展开放（OCP）

```
新增功能：
  1. 首先看 CLFInputHandler 是否已有对应 Action
  2. 有 → 只加映射；没有 → 加 Action 枚举 + 映射 + applyAction 处理
  3. 不影响已有 Action 的处理逻辑

对比之前：
  必须深入 CLFRepl::run() switch 里加 case
```

### 4.4 用户操作可控

```
未来：
  - 读配置文件 → CLFInputHandler::rebind()
  - 用户可自定义快捷键
  - 终端误操作时用 Ctrl+Z undo 缓冲区
```

## 五、鼠标事件（前瞻）

当前终端鼠标事件需通过 Windows Console API（`ENABLE_MOUSE_INPUT` + `ReadConsoleInput`）读取，不在 `_getch` 范围内。作为独立模块 `CLFMouse`：

```
CLFMouse → MouseEvent → CLFInputHandler → Action
```

可支持：点击定位光标、滚轮滚动、选中文本。不做在此次分析范围内。

## 六、绘制区域模型分析

### 6.1 区域划分与触发规则

```
┌──────────────────────────┐
│                          │
│   ContentRegion          │  ← DECSTBM 滚动区
│   滚动显示区              │  update(text) → 格式调整+显示
│                          │  resize(w)   → 按新宽度重新折行
│   纯显示器职责：          │  不存内容逻辑，只做渲染
│   收到什么显示什么         │
├──────────────────────────┤  ← 上分隔线（底部锚定）
│  InputRegion             │  update(text, cursor)
│  多行输入区              │  换行时向上扩展，始终贴合底部
├──────────────────────────┤  ← 下分隔线（底部锚定）
│  StatusLine              │  状态标题+内容
│  ModeLine                │  模式+快捷键提示
└──────────────────────────┘
```

### 6.2 区域独立触发规则

| 触发场景 | ContentRegion | InputRegion | ModeLine | StatusLine |
|---------|:---:|:---:|:---:|:---:|
| API 响应到达（模型输出） | ✅ 更新 | — | — | ✅ 可更新 |
| 用户输入字符/移动光标 | — | ✅ 更新 | — | — |
| Shift+Tab 切换模式 | — | — | ✅ 更新 | — |
| 工具执行状态回调 | — | — | — | ✅ 更新 |
| 终端缩放（高度变化） | ✅ 重排 | ✅ 重定位 | ✅ 重定位 | ✅ 重定位 |
| 输入换行（行数变化） | ✅ 上移 | ✅ 扩展 | ✅ 联动 | ✅ 联动 |

### 6.3 各区域约束

```
ContentRegion:
  - 绝对位置: 第 1 行 ~ 第 (H - 固定区行数) 行
  - 固定区行数 = 上分隔(1) + 输入行(N) + 下分隔(1) + 状态行(1)
  - 缩放时: 重新计算区域边界 + 按新宽度折行显示缓冲内容
  - 滚动: DECSTBM 自动管理

InputRegion:
  - 绝对位置: 上分隔线下方，下分隔线上方
  - 始终贴合底部, 行数 = 1 + 换行符数量
  - 单行 → 多行: 上分隔线上移, ContentRegion 下边界上移
  - 多行 → 单行: 上分隔线下移, ContentRegion 下边界下移

ModeLine + StatusLine:
  - 绝对位置: 最底部 2 行 (下分隔线之下)
  - 永远固定, 不受 ContentRegion 滚动影响
  - 缩放时: 重新计算行号, 内容不变
```

### 6.4 当前实现 vs 该模型

| 维度 | 当前 | 该模型 | 差距 |
|------|------|--------|------|
| ContentRegion | `scrollPrint` 直接写 stdout + 行缓冲 | 纯显示器, 宽度格式化 | 需加重排逻辑 |
| InputRegion | `drawInputArea` 独立渲染 | 底部锚定 + 动态扩展 | ✅ 基本一致 |
| ModeLine | `drawModeArea` 独立渲染 | 底部锚定 | ✅ 一致 |
| StatusLine | `drawStatusArea` 调用 `scrollPrint` 写入滚动区 | 独立固定行, 不参与滚动 | ❌ 需移出滚动区 |
| 区域独立性 | `drawInputArea` 全量重绘整个固定区 | 只更新变化的区域 | ⚠️ 优化项 |

### 6.5 最终确认布局（2026-08-03 讨论确认）

自底向上：

```
 行号 (H=30 为例)
┌                                                          ┐
│ 1                                                        │
│         ⑦ 滚动内容区 (ContentRegion)                        │
│         DECSTBM 管理                                      │
│         纯显示器：给我什么，显示什么，不做业务判断             │
│                                                          │
│ H-11   ⑥ 工作状态区 (StatusRegion)                         │
│        1 行起步: "· Thinking… (3s)"                       │
│        可树形展开:                                         │
│          working: 调整目录结构 (123s)                       │
│          ph1> 🆕 DECSTBM 滚动区重构                         │
│          ph2> 🆕 Shift+Tab 模式切换                         │
│ H-10 ──────────────── 上分隔线 ────────────────────────  │
│ H-9    ⑤ 输入区 (InputRegion)                             │
│ H-8    下边界固定，换行时向上扩展 (上分隔线联动)              │
│ H-7 ──────────────── 下分隔线 ──────────────────────────  │
│ H-6    ④ 工作模式区 (ModeLine)                             │
│        "auto mode on · shift+tab to cycle · ..."         │
│ H-5    ③ 确认区 (ConfirmRegion)                           │
│        未触发: 空行  |  触发: [●]确认 [ ]取消              │
└                                                          ┘

② LayoutEngine (横跨所有区域, 缩放/换行时重算边界)
① EventDispatcher (统一事件→区域 dirty 标记)
```

### 6.6 各区职责 + 触发规则

| # | 区域 | 行数 | 更新触发 | 职责 |
|---|------|------|---------|------|
| ⑦ | ContentRegion | 剩余全部 | StreamChunk/StreamDone/ToolExecDone | **纯显示器**: 只做格式调整+宽度重排, 不做内容判断 |
| ⑥ | StatusRegion | 1+(树形N行) | ThinkingTick/ThinkingDone/ToolExec | 工作状态: 思考/执行进度/树形步骤 |
| ⑤ | InputRegion | 1+换行数 | KeyPress | 多行输入框, 底锚定, 上扩展 |
| ④ | ModeLine | 1 | ShiftTab | 安全模式+快捷键提示 |
| ③ | ConfirmRegion | 1 | ConfirmRequest/ConfirmResult | 空行/确认菜单 |
| ② | LayoutEngine | — | Resize/InputLineChange | 重算所有区域边界, 联动 |
| ① | EventDispatcher | — | 全部事件源 | 事件→dirty flag→帧末渲染 |

### 6.7 底部锚定规则

```
固定区域 (从底向上, 共 5+N 行):
  ConfirmRegion  1 行  [始终底部]
  ModeLine       1 行  [始终底部]
  下分隔线       1 行  [始终底部]
  InputRegion    N 行  [底锚定, 多行时上分隔线上移]
  上分隔线       1 行  [随 Input 联动]

可变区域:
  StatusRegion   M 行  [1 行起步, 树形展开时增长]
                        [挤压 ContentRegion 下边界上移]
  ContentRegion  剩余  [DECSTBM 滚动]

总固定区 = 5 + N + M
ContentBottom = H - (5 + N + M)
```

### 6.8 当前实现 vs 确认布局 — 差距清单

| 差距 | 当前 | 目标 | 改动 |
|------|------|------|------|
| 确认区位置 | `scrollPrint` 写入滚动区 | 固定底部 1 行 | `drawConfirmBar` 新方法 |
| 状态区位置 | `scrollPrint` 写入滚动区 | 上分隔线上方, 独立渲染 | `drawStatusLine/Tree` 新方法 |
| 状态区能力 | 只支持 "▍ title + 内容" 两行 | 1 行起步, 树形展开 | `s_statusTree` 缓冲 |
| ThinkingIndicator | 直接 `std::cout` 写 | 推 StatusRegion 事件 | `Event::ThinkingTick` |
| ModeLine 提示 | "? for help" | "/help for help" | 改文字 |

### 6.9 改动文件清单

| 文件 | 操作 | 量 |
|------|------|-----|
| `CLFTerminal.hpp` | 加 StatusRegion/ConfirmRegion API, 删旧状态区 API | ~20 行 |

## 七、触发机制分析

### 7.1 系统中有哪些触发源

```
触发源                          产生位置                  影响区域
──────────────────────────────────────────────────────────────────
键盘按下                        CLFConsole::readKey()      InputRegion / ModeLine
API 流式数据到达                 postJsonStream 回调        ContentRegion
ThinkingIndicator 每秒滴答       后台线程                   ContentRegion
命令执行超时                    CLFCommandExec             ContentRegion
工具执行状态回调                m_statusCallback           StatusLine (当前在滚动区)
高风险确认                      executeTools 内部          ContentRegion + ConfirmArea
终端缩放                        主循环轮询                 全部区域
斜杠命令                        submit() → handleCommand   ContentRegion
会话恢复/保存                   submit / 启动检测          ContentRegion
```

### 7.2 当前触发→处理映射（谁调了谁）

```
CLFRepl::run()
  │
  ├─ readKey ──→ switch(key) ──→ m_input 变更 ──→ drawInputArea()    [直接]
  │                                            ──→ drawModeArea()     [直接]
  │
  ├─ submit() ──→ toContentArea()               [直接调绘制]
  │           ──→ CLFCommandDispatcher::handle() [命令处理]
  │           ──→ m_agent.runTurn()              [业务]
  │
  └─ 缩放检测 ──→ redrawAll()                    [直接调绘制]

CLFAgentLoop::runTurn()
  │
  ├─ postJsonStream 回调 ──→ streamProc.feedLine()  [数据]
  │                      ──→ CLFTerminal::scrollPrint()  [直接调绘制!]
  │                      ──→ CLFConsole::checkEscape()    [跨层调输入!]
  │
  ├─ ThinkingIndicator ──→ std::cout 直接写          [绕过所有层!]
  │
  └─ CLFToolExecutor::execute()
        └─ m_confirmCallback ──→ CLFRepl::confirmDialog()  [反向回调]
             └─ CLFTerminal::drawConfirmArea()              [直接调绘制]
```

### 7.3 问题：触发与处理紧密耦合

```
问题 1: AgentLoop 直接调终端
  runTurn() 内部直接调用 CLFTerminal::scrollPrint()
  → 业务层依赖渲染层，换渲染实现需改业务代码

问题 2: ThinkingIndicator 绕过所有层
  后台线程直接写 std::cout
  → 滚动区绘制和 thinking 绘制竞争 stdout

问题 3: 安全确认反向回调
  CLFToolExecutor → m_confirmCallback → CLFRepl::confirmDialog
  → 调用链跨越 3 层（工具→Agent→Repl），难以追踪

问题 4: 缩放是轮询不是事件
  while(true) { getTerminalHeight(); } 每轮循环检查
  → 真正的 resize 事件被轮询替代，有延迟
```

### 7.4 目标：触发⇄处理解耦

参照 Qt 模式，引入一个轻量的事件通道：

```
        触发源                        事件通道                   处理者
  ┌──────────────┐            ┌──────────────┐         ┌──────────────┐
  │ CLFConsole   │──key──────→│              │─input──→│ CLFRepl      │
  │              │            │              │         │ (状态管理)    │
  │ ThinkingInd. │──tick─────→│  EventBus    │─display→│ CLFTerminal  │
  │              │            │              │         │ (渲染)        │
  │ postJsonStr. │──data─────→│ (简单队列)    │─state──→│ CLFAgentLoop │
  │              │            │              │         │ (业务)        │
  │ 主循环轮询    │──resize───→│              │         │              │
  └──────────────┘            └──────────────┘         └──────────────┘
```

### 7.5 事件类型设计

```cpp
enum class EventType {
    KeyInput,       // 键盘输入 (CLFKeyEvent)
    StreamData,     // API 流式数据 (line/chunk)
    ThinkingTick,   // 思考计时滴答 (seconds)
    ToolStatus,     // 工具执行状态 (title, content)
    ConfirmRequest, // 高风险确认请求 (prompt, callback)
    Resize,         // 终端尺寸变化 (width, height)
    SessionChanged, // 会话状态变更 (saved/restored/cleared)
};
```

### 7.6 各触发源改造方式

| 当前 | 改造 |
|------|------|
| `CLFRepl::run()` switch 直接调 `drawInputArea` | switch 产出 `KeyInput` 事件 → CLFRepl 处理状态 → 通知重绘 |
| `runTurn()` 内 `CLFTerminal::scrollPrint()` | 产出 `StreamData` 事件 → CLFTerminal 的 display handler |
| `ThinkingIndicator` 直接写 `std::cout` | 产出 `ThinkingTick` 事件 → CLFTerminal 在滚动区渲染 |
| `m_confirmCallback` 闭包回调 | 产出 `ConfirmRequest` 事件 → CLFRepl 响应 |
| 主循环轮询 `getTerminalHeight()` | Windows `ReadConsoleInput` 的 `WINDOW_BUFFER_SIZE_EVENT` 或保持轮询但改为产出 `Resize` 事件 |
| `m_statusCallback` | 产出 `ToolStatus` 事件 → CLFTerminal 更新底部状态行 |

### 7.7 复杂度评估

```
方案 A: 完整事件总线
  EventBus 类 + Event 基类 + 类型分发 + 订阅/退订
  ~300 行新代码, 3 新文件
  收益: 完全解耦, 可单元测试

方案 B: 最小改——事件枚举 + 单一 dispatch 函数  
  只加 EventType 枚举, CLFRepl::run() 改为 dispatchEvent()
  不改现有调用, 只把直接调绘制改成先改状态再触发渲染
  ~80 行改动, 0 新文件
  收益: 低成本解耦, 为未来重构留接口

方案 C (当前状态): 直接调用
  0 改动
```

## 八、最终架构设计（一步到位）

### 8.1 决策依据

后续任务（上下文污染管理、历史记录回看、工具链增强）只涉及内容逻辑，不会再动 UI 框架。因此：

> **UI 架构必须一次性做到位，后续只在模块内部微调。**

### 8.3 事件定义

```cpp
enum class EventType {
    // 输入类
    KeyPress,        // 键盘按键 (KeyChord + char)
    
    // API 流式数据
    StreamChunk,     // 文本增量到达 (text)
    StreamDone,      // 流结束 (finish_reason)
    StreamError,     // 流错误 (message)
    StreamInterrupted, // 用户中断
    
    // 思考进度
    ThinkingTick,    // 每秒滴答 (elapsed_seconds)
    ThinkingDone,    // 思考结束
    
    // 工具执行
    ToolExecStart,   // 开始执行 (tool_name, params)
    ToolExecDone,    // 执行完成 (result)
    ConfirmRequest,  // 安全确认请求 (prompt)
    ConfirmResult,   // 用户确认结果 (allow/deny)
    
    // 系统
    Resize,          // 终端尺寸变化 (width, height)
    SessionSaved,    // 会话已保存
    SessionRestored, // 会话已恢复
    AppExit,         // 退出
};

struct Event {
    EventType type;
    // payload (union/variant — 根据 type 取对应字段)
    std::string text, arg1, arg2;
    int i1, i2;
    void* ptr;  // 复杂数据指针（如 ConfirmRequest 的 callback）
};
```

### 8.4 EventDispatcher

```cpp
class EventDispatcher {
public:
    // 注册处理器（按事件类型订阅）
    void subscribe(EventType type, std::function<void(const Event&)> handler);
    
    // 分发事件（主循环调用）
    void dispatch(const Event& event);
    
    // 每个主循环帧末：处理所有排队事件 + 触发重绘
    void flush();
    
private:
    std::unordered_map<EventType, std::vector<std::function<void(const Event&)>>> m_handlers;
    std::vector<Event> m_queue;
};
```

### 8.5 各模块的 Handler 职责

```
CLFRepl (状态管理):
  订阅: KeyPress, ConfirmResult, Resize, SessionSaved/Restored, AppExit
  不调绘制, 只改状态 (m_input, m_cursorPos, m_modeName)
  
CLFTerminal (渲染):
  订阅: StreamChunk, StreamDone, StreamError, StreamInterrupted,
        ThinkingTick, ThinkingDone, ToolExecStart, ToolExecDone, Resize
  只做渲染, 不存业务状态

CLFAgentLoop (业务):
  订阅: StreamChunk, StreamDone, ToolExecDone, ConfirmRequest
  处理 API 交互 + 工具执行, 不调绘制

CLFCommandDispatcher:
  订阅: KeyPress (特殊键映射)
  只做命令匹配
```

### 8.6 主循环变为

```cpp
int CLFRepl::run() {
    setupEventHandlers();  // 注册所有 handler
    
    while (true) {
        // ① 收集输入事件
        pollResize();        // → Event::Resize
        auto key = readKey(); // → Event::KeyPress
        
        // ② 分发
        m_dispatcher.dispatch(keyEvent);
        m_dispatcher.dispatch(resizeEvent);
        
        // ③ 帧末：一次性渲染所有 dirty region
        m_dispatcher.flush();  // → CLFTerminal::renderDirtyRegions()
    }
}
```

### 8.7 区域渲染（dirty 标记）

```cpp
class CLFTerminal {
    enum DirtyFlag {
        DIRTY_CONTENT  = 1 << 0,  // ⑦ 滚动区
        DIRTY_STATUS   = 1 << 1,  // ⑥ 状态区
        DIRTY_INPUT    = 1 << 2,  // ⑤ 输入区
        DIRTY_MODE     = 1 << 3,  // ④ 模式区
        DIRTY_CONFIRM  = 1 << 4,  // ③ 确认区
        DIRTY_LAYOUT   = 1 << 5,  // ② 全部重算(缩放/换行)
    };
    int m_dirty = 0;
    
    void markDirty(DirtyFlag f) { m_dirty |= f; }
    
    void renderDirtyRegions() {
        if (m_dirty & DIRTY_LAYOUT)  { recomputeLayout(); /* fall through */ }
        if (m_dirty & DIRTY_CONTENT) renderContentRegion();
        if (m_dirty & DIRTY_INPUT)   renderInputRegion();
        if (m_dirty & DIRTY_MODE)    renderModeLine();
        if (m_dirty & DIRTY_STATUS)  renderStatusLine();
        m_dirty = 0;
    }
};
```

### 9.4 事件与绘制解耦 — 关键规则

```
规则 1: 触发源不直接调绘制
  ❌ ThinkingIndicator → std::cout << "· Thinking…"
  ✅ ThinkingIndicator → push ThinkingTick → CLFTerminal::drawStatusLine

规则 2: 绘制不关心触发源
  ❌ drawStatusLine("Thinking…") 被 ThinkingIndicator 直接调用
  ✅ CLFTerminal 只管 "给我什么文本, 显示在状态区"

规则 3: 事件通道是唯一入口
  ❌ runTurn 内直接 scrollPrint
  ✅ runTurn 内 push StreamChunk → dispatch → scrollPrint

规则 4: 帧末统一渲染
  ❌ 每个事件立刻绘制 (可能一帧内重绘 10 次)
  ✅ 一帧内收集所有事件, 帧末合并 dirty flags, 一次渲染
```

### 9.5 主要改动点

| 当前 | 事件化改造 |
|------|----------|

## 十一、思考信息展示（reasoning_content）

当前 `CLFStreamAccumulator::feedDelta` 只捕获 `delta.content` 字段。DeepSeek 思考模型将推理过程放在 `delta.reasoning_content` 中（不计入 content），这部分数据当前被丢弃。

方案：在 `CLFStreamAccumulator` 中增加 `m_reasoning` 缓冲，`CLFTerminal` 提供 `showReasoning(text)` 方法以暗色显示。

不改动 `CLFAgentLoop::runTurn` 的编排逻辑——仅扩展数据通道。
