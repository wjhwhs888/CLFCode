## 1. 一句话定义

> **Subagent = 模型发起、运行时装配并监护、另一个模型执行、结论以消息形式异步回投的工具。**

它的价值是 **上下文隔离**（并行为附带），代价是 **过程不可见、结果质量无保障**。

关键认知：**subagent 是工具，不是魔法。** 它和其他工具（read / write / search）同级，都注册进同一个工具注册表，模型只能看到 name + schema + description。

---

## 2. 三层分工：谁在做什么

| 层 | 实体 | 职责 |
|---|---|---|
| **决策** | 父 agent 的那次 LLM 请求 | 委不委派、派几个、prompt 写什么、起什么名、选哪个 preset/模型 |
| **执行** | 运行时（`ctx.subagents` / 自建 SubagentManager） | 准入、装配、护栏、生命周期、结果递送 |
| **干活** | 子 agent 自己的 LLM 循环 | 在独立上下文里把活干完 |

### 关键：模型不能选"找谁执行"

`provider`（spawn / fork / acp / codex…）是**配置在 YAML 里写死的**，模型看不到也改不了。

模型能选的只是"用叫 `subagent` 的工具还是叫 `subagent_fork` 的工具"，但每个工具背后连谁，是部署方定的。

### 用户能控什么

| 层 | 谁能控 | 性质 |
|---|---|---|
| 配置层 | 用户 | **硬控制**：工具是否注册、允许哪些 provider、maxDepth、并发上限 |
| 提示层 | 用户 | **软引导**："派两个子代理去查 X 和 Y" |
| 调用层 | **模型** | 自己决定是否调用、调用几次 |

用户能**要求**，但不能**强制**。

## 3. 核心机制：异步交付，不是调用返回

这是最容易被误解的地方。

### 工具立刻返回回执

```ts
// dsh 实现
const started = await ctx.subagents.startActivation({ ... })
return { kind: 'activation' as const, name: started.name }
```

`execute` await 的是**准入**（子 agent 已接受任务），然后立刻返回。
渲染给模型的就是一行 `started subagent <name>`。

**dsh README 原话：「本工具不等待结果」**

### 真实时序

```
模型调 subagent → 工具瞬间返回"已启动"
                → 模型继续走主线，或结束本轮
                → 子 agent 在后台跑
                → 跑完，运行时把结论包成一条消息注入父级历史
                → 这条消息唤醒父级的新一轮 LLM 请求
```

### 模型没有"等待"这个动作

系统提示词明确写着：

> `When only waiting for their results remains, end your turn instead of sleeping or polling; the next result starts a new turn.`

真正在等的是**宿主代码**，不是模型。

### dsh 的唤醒机制（供参考）

```ts
this.sendWaking(parent, message, parent.status === 'idle' ? 'queue' : 'steer')
```

| 父级状态 | 投递方式 | 行为 |
|---|---|---|
| **idle** | `queue` → `followup` | 排队，**唤醒 driver，开新轮** |
| **running** | `steer` | 插到 next-step，当前轮下一步就能看到 |

唤醒的关键是给注入消息**打来源标记**，避免被当成用户发言：

```ts
source: {
  kind: 'subagent-settled' as const,
  form: 'notice' as const,
  senderSessionId: childId,
}
```

> **终端 CLI 的取舍**：不做自动唤醒（防止模型自问自答），改为用户下次输入时才消费结果。这是设计选择，不是缺陷。

## 4. 交付物的真相

### 父级收到的是什么

一条 **user 消息**，只有四段：

| 段 | 内容 |
|---|---|
| summary | 结算摘要 + stopReason + 是否可继续 |
| **最终回答** | `finalAssistantOutput` |
| Structured result | 只有请求了 `outputSchema` 才有 |
| diagnostic | 非 completed 时的失败详情 |

### 取值规则（dsh 是规范级的）

> 取**最后一条非空 assistant 消息**；没有则回退到累积的流式文本

而且 `createSettlementMessage` **只保留 `text` 类型块**，图片附件直接丢掉。

### 由此推出三个结论

1. **过程完全不进父级上下文**
   没有 tool call、没有中间步骤、没有推理过程。全留在子会话里。

2. **"最后一条 message" ≠ "总结"**
   如果子 agent 最后一步是调工具（跑测试），后面没有文本 → 取到的是它调工具**之前**那句话。

3. **失败时的语义标记**
   正常中断 → 有结构、无最终文本（这本身就是"失败"标记）

### 输出质量没有保障

这是设计上的真实弱点：

- 无最小长度约束
- 无摘要完整性校验
- 无强制要求

**所以「输出约定」必须写进 prompt，机制不保证。**

### 可用的对策（按可靠性）

| 手段 | 说明 |
|---|---|
| **prompt 里写产出格式** | 工具层唯一可用的手段 |
| **agent_preset 固化纪律** | 需要进程内 spawn + 白名单 |
| **outputSchema（硬约束）** | dsh 服务层支持，但**工具层未暴露给模型** |

### prompt 模板参考

```
<任务描述，自包含>

完成后，在你最后一条消息里按以下结构回报：
1. 结论：任务是否完成（完成 / 部分完成 / 未完成）
2. 关键产出：改了哪些文件 / 得出什么结论（只列结果，不要粘贴全文）
3. 未完成项：哪些没做、为什么、卡在哪
4. 需要我知道的意外：与你预期不同的地方、风险、需要我决策的点

不要只说"已完成"，也不要复述你的执行步骤细节。
```

关键：**简短可以，但不能省掉决策所需信息。**

## 5. 该不该派：唯一的判断标准

### 唯一的问题

> **这件事如果主线自己做，会吃掉多少上下文？**

因为并行已经有了（工具调度器提供），**subagent 唯一不可替代的价值就是上下文隔离。**

### 量化：压缩比

```
压缩比 = 子任务产生的信息量 / 父级真正需要的结论量
```

| 压缩比 | 决策 |
|---|---|
| **高**（读 50 个文件，结论一小段） | ✅ **派** |
| **低**（输入输出差不多大） | ❌ 自己做 |

### 实例

一个子任务要读 20 个文件，每个 3KB：

| | 父级上下文 |
|---|---|
| 主线自己读 | 60KB ≈ **15,000 tokens** |
| 派 subagent | 一条文本 ≈ **300 tokens** |

**50 倍压缩。** 而且那 15k tokens 会一直占着，还会让摘要提前触发——**摘要是会丢信息的**。

### 判断顺序

```
1. 一条确定性命令能出结果吗？
   → 是：直接调工具。结束。

2. 规则固定、要重复跑 / 长时间跑？
   → 是：background job。零成本。

3. 需要判断、探索、可能改主意？
   → subagent。继续 4。

4. 压缩比够高吗？
   → 太低（几分钟做完、结果只要几行）：主线自己做。
   → 够高（读大量内容、结果只是结论）：派。

5. 会不会和别的并行任务写同一批文件？
   → 会：切分范围或改串行。运行时不做合并、不做冲突检测。
```

### 成本模型

每次 subagent 往返：

```
父级付出：写一段完整的 brief（自包含、不能省略上下文）
子级付出：一整个会话的 token
父级收到：一句话结论
```

**所以 subagent 有"起订量"。** 任务太小，开子代理是纯亏——不是不能做，是成本模型不成立。

## 6. 三个易混对象的分辨

### Subagent vs Background Job

| | subagent | background job |
|---|---|---|
| **里面装什么** | **一个 LLM 会话** | **一个进程** |
| 能回答什么 | "这正常吗"（需判断） | "数字变了没"（确定性） |
| 能改主意吗 | ✅ 能 | ❌ 脚本写死了 |
| token 成本 | 一次完整会话 | **零** |
| 启动后返回 | 回执 | job id |
| 完成唤醒 | ✅ | ✅ |
| 上下文隔离 | ✅ | 不占上下文 |

**分类标准：里面装的是什么。** 不是"是不是后台"、不是"并行了没"。

| 特征 | subagent | background job |
|---|---|---|
| 并行/不阻塞 | ✅ | ✅ |
| 异步交付 | ✅ | ✅ |
| 完成唤醒 | ✅ | ✅ |
| 派活 | ✅ | ✅ |

**这些特征没有一个能区分两者。**

一句话：**background job 是你写好的规则在跑；subagent 是一个会看情况改主意的人在跑。**

### Subagent vs 任务清单（todo）

| | todo_write | subagent |
|---|---|---|
| execute | 同步，立即返回 | 同步返回**回执**，真结果异步 |
| 结果来源 | 由**入参推导**（回显） | 由**另一个 LLM loop** 跑出来 |
| 成本 | 可以忽略 | 一次完整模型会话 |
| 上下文 | 同一上下文 | **隔离** |
| 本质 | **状态改写** | **派活** |

**重要**：todo 的 `in_progress` 状态**不代表真的并行**。真实执行仍是顺序的。

### Subagent vs 同轮工具并行

| | 工具调度器并行 | subagent |
|---|---|---|
| 时间跨度 | **一轮之内** | **跨回合** |
| 完成条件 | 全部收齐按序提交，回合才能过 | 不要求这一轮等 |

**把长命对象塞进短命调度器，会死锁。**

### fork vs spawn（一个概念撞车）

| | Unix `fork()` | dsh `fork` |
|---|---|---|
| fork 什么 | 复制**进程内存** | 复制**父级已完成对话轮次** |
| 与并发的关系 | 是并发原语 | **毫无关系** |

**dsh 里 fork 和 spawn 的并发行为完全一样。** 唯一差别是子 agent 的初始上下文：

- `spawn` → 全新开始
- `fork` → 塞入父级已完成轮次的一次性快照（**看不到进行中的那一轮**）

## 7. 实现要点（C++ 视角）

### 架构骨架

```
工具 handler（注册在 CLFTools）
   └─ 立刻返回回执，调用 SubagentManager::launch(...)
SubagentManager（新子系统）
   ├─ 创建/启动/取消/回收 + 注册表
   ├─ 每子 agent：独立 loop / 独立 HttpClient / 空输出 / 空白事件总线
   └─ 完成后 push 结果队列
父级 runTurn 开头 → drain 队列 → 注入上下文
```

### 四个必须自己写的东西

| 部件 | 为什么必须独立 |
|---|---|
| **独立 HTTP 客户端** | `abort()` 是实例级的，共用会互相误杀 |
| **独立输出通道** | 子 agent 写终端会打烂 REPL；且 `setOutput` 同时注册中断回调 |
| **独立事件总线** | 父总线是**单生产者**假设，子线程直接发会破坏保序 |
| **独立工具注册** | handler 捕获各自 `*this`，不能共享 `m_tools` |

### 工具 handler 必须立刻返回

**绝对不能让 handler 等子 agent 跑完。** 三个后果：

1. **占槽位**：阻塞的 handler 永久占住一个并发槽
2. **队首阻塞**：调度器"队首未完成，后面必须等" → 这一轮卡死
3. **没有兜底**：工具执行器没有工具级超时，会永远卡住

> ⚠️ 这不是"同步 vs 异步"的问题。**关键在于：返回值压根不是结果的交付通道。**
> 结果从队列来，不从 `return` 来。

### 并发与深度限制

| 限制 | 独立配置 | 说明 |
|---|---|---|
| `m_maxActiveSubagents` | 默认 2–3 | 同时活着的子 agent 数（**不能**和同轮工具并发共用） |
| `m_subagentMaxDepth` | 默认 1 | 子 agent 也有工具集，不拦就无限递归 |

### 结果三态

结果队列的消息必须能表达三种状态：

| 状态 | 含义 | 是否带诊断 |
|---|---|---|
| 成功 | 正常完成 | 带最终文本 |
| 失败 | 异常结束 | **必须带原因**（用于决策重试/改派/自己上） |
| 取消 | 被中断 | 带取消来源 |

### 工具复用边界

| 可复用 | 必须分离 |
|---|---|
| 工具**定义**（name/schema/description） | 工具**注册**（handler 闭包） |
| `CLFToolScheduler`（每子 agent 一个实例） | —— |
| `CLFAgentLoop`（新实例） | HTTP client、输出、事件总线 |
| 存盘逻辑（事件路径） | 文件路径、FileCtx 实例 |

## 8. 取消的四个场景

**取消不是一个机制。** 范围不同，机制就得分开。

| 场景 | 范围 | 要点 |
|---|---|---|
| **单个子任务跑飞** | 只杀那一个 | 共用 client 做不到 |
| **子任务异常** | 只标记失败，其余继续 | 不能拖垮全局 |
| **工具执行中的中断** | 需要循环检查点 | `abort()` 时是空操作 |
| **主任务/程序退出** | 全部级联 | 否则 `std::thread` 未 join → `std::terminate` |

### 五个关键点

**① abort 是全杀，不是单杀**

```cpp
virtual void abort() = 0;   // 中止"正在进行的请求"（单数，无句柄）
```

- 父子共用 client → ESC 杀全部（可能是你要的）
- **但反方向也成立**：子 agent 超时/取消 → 把父级的流式请求杀了
- 而且 `m_aborted = false` 在每个请求入口无条件重置，并发下会互相清掉状态

**② abort 不等于终止循环**

`abort()` 只打断**在途的 HTTP 请求**。循环会看到失败响应，然后**去重试**。

所以取消必须同时：**置取消标记 + abort**。

**③ 工具执行中 abort 是空操作**

子 agent 正在跑工具（不在 HTTP 里）时，`abort()` 完全无效。必须有循环检查点。

**④ 中途杀掉会留下坏掉的会话文件**

不变量：**tool_calls 声明数 == tool 结果数**（否则 API 拒绝）。

杀掉时如果已写 assistant tool_calls 但没写 tool 结果 → 子会话文件废了。

**⑤ 同步结束的完整序列**

```
1. 置 cancel 标记（让循环在下一个检查点退出）
2. abort 该子 agent 自己的 client
3. join 子线程（有界等待）
4. flush 子会话 + 补 [interrupted] 合成结果（修 dangling tool_calls）
5. 释放并发槽、摘除注册表条目
```

## 9. 三个必须隔离的边界

### 边界一：上下文

```
父上下文中只有：结论一条消息
子会话文件中才有：完整过程
```

**过程只存在于子会话文件，不在父上下文。**

| 层 | 状态 |
|---|---|
| **结果** | **隐含**在父上下文中（存在，只是无标记） |
| **过程** | **不存在**于父上下文（不是隐含，是压根没传） |

### 边界二：事件

**父级事件总线是单生产者假设支撑的。** 子 agent 直接发事件会破坏地基：

| 后果 | 说明 |
|---|---|
| `seq` 保序失效 | 父级和子级 delta 交错，渲染混在一起 |
| **重放与上下文不一致** | UI 重放出过程，但模型上下文里没有 |
| Lossless 背压传导 | 订阅者慢 → **阻塞生产者** |

**正确做法**：

```
子 agent A ──► 自己独立的总线 ──► 自己的 SessionWriter
子 agent B ──► 自己独立的总线 ──► 自己的 SessionWriter
                   │
          父级在 drain 时自己发布预览性状态事件
父级总线 ◄── SubagentStarted / SubagentFinished
```

**父总线里每一条带 sub 标识的事件，都是父级自己发的摘要，不是子级的过程。**

### 边界三：存储

```
父会话文件 + 上下文 ✓
子会话文件 ─ 独立，不复用、不合并
```

**主会话只存结论，过程留在子会话文件。** 两份文件各自成立，不需要互相引用。

### 包含链原则

> **存储 ⊇ 上下文 ⊇ 显示**

| 层 | 说明 |
|---|---|
| 会话文件 | 全量消息差集，`restoreSession` 的数据源 |
| 上下文 | 从文件重建，模型实际看到的 |
| 请求视图 | 按 token 预算从尾部截断 |
| 显示 | 可折叠、可降噪 |

**降噪只允许发生在最外层的显示层，绝不能发生在存储层。**

方向不能反：
- 显示比上下文少 → 正常（降噪）
- 请求视图比上下文少 → 正常（窗口截断）
- **上下文比文件多 → 出问题**（resume 后模型遗忘）

### resume 的边界

| | resume | 事后追溯 |
|---|---|---|
| 时机 | 每次恢复 | 需要时 |
| 读什么 | **只读主会话文件** | 主文件 → 子文件 |
| 要子文件吗 | **不要** | 要 |

**子任务完成后，过程就死亡了**——它的价值在被压成结论那一刻就已经转移。

前提：子任务必须真完成，结果真进了父会话文件。**不存在跨会话的子任务**（会话结束，子任务线程也结束）。

## 10. 崩溃防护：坡顶立牌子

### 问题

进程被强杀时，父会话文件里**什么都没有**。

因为 turn 行只在 `TurnFinished` / `Interrupted` 时写，那一刻两者都没发生。结果队列在内存里，一起没了。

**结果：resume 之后，父级完全不知道曾经派过子任务。** 不是"知道它失败了"，是**连它存在过都不知道**。

### 解决：write-ahead（预写意图）

```
1. 派发前，先写一行：{ type: "subagent_launch", id: "uuid", brief: "...", turnId: ... }
2. flush
3. 才真正启动子 agent
```

| 结束方式 | 文件里的样子 |
|---|---|
| 正常完成 | launch 行 + 结果 ✅ |
| 正常取消 | launch 行 + 失败结果 ✅ |
| **崩溃** | **launch 行，无结果** ← 孤儿，一眼可见 |

### 现成模式：事件到达即写

不需要发明新机制。todo 已经是这个模式：

> **事件到达即写**：清单变化立即落 `todo_snapshot` 行（**不等轮末**）

`subagent_launch` 照抄这个形状。

### resume 时处理孤儿

| 子文件状态 | 含义 | 危险性 |
|---|---|---|
| 有回合、无最终文本 | 正常中断/取消 | 中 |
| **launch 有、结果无** | **运行期崩溃，完全不可信** | **高** |

第二种必须在 resume 时**显式告知父级**：

```
[子任务 reviewer 未能完成：运行期中断，结果不可信]
```

否则父级会带着空洞继续往下走。

### 救得回什么

| 能救 | 救不回 |
|---|---|
| 知道派过、派了什么 | 子任务已经做的工作 |
| 知道它没回来 | 它做到哪一步 |
| 决策：重跑 / 自己做 / 放弃 | —— |

**这不是"等死"，是"出事后能站起来"。**

### 结构完整性由构造保证

如果存盘走**事件重建路径**（不是上下文差集），结构完整性天然成立：

```cpp
// 即使 withAssistant=false（中断），assistant 仍然带上 tool_calls 声明
if ((withAssistant && !ev.m_text.empty()) || !m_toolEvents.empty()) {
    assistant.m_content = withAssistant ? ev.m_text : "";   // 文本为空
    for (const auto& tool : m_toolEvents) {                 // 声明照建
        assistant.m_toolCalls.push_back(...);
    }
}
```

| 情况 | 结果 |
|---|---|
| 正常结束 | 带文本写入 |
| 中断/取消 | 无文本写入（**结构合法**） |
| 进程崩溃 | 整轮不写（→ 需要 launch 行兜底） |

**所以"不完整丢弃"这条规则不需要写**——结构完整性是重建过程自带的性质，不是过滤出来的。

**丢弃不完整回合反而有害**：子任务被取消/异常死掉的那些回合，正是不完整的，也是最该留的痕迹。

## 11. 常见误区清单

| 误区 | 实际 |
|---|---|
| subagent 返回结果 | 返回**回执**，结果异步注入 |
| 模型等结果 | 模型**结束本轮**，被新消息唤醒 |
| 过程会传给父级 | 只传**最后一条非空文本** |
| 模型选执行者 | **配置**写死，模型选不了 |
| 结果保证有总结 | 纯靠 prompt，无校验 |
| 提高 reasoning effort 能改善汇报 | 反而**更短**（更多进 thinking） |
| todo 和 subagent 同类 | todo 是状态改写，subagent 是派活 |
| subagent 的核心是并行 | 核心是**上下文隔离**，并行为附带 |
| "读不用等写" | **写是屏障**，它前后都得串行 |
| 子任务事件加个标识走父总线就行 | 破坏单生产者假设，必须独立总线 |
| 不完整消息丢弃 | 结构要补齐，失败靠语义表达 |
| 子任务上下文需要父级感知 | **完全不需要**；提示词带任务要求，不带上下文 |
| 崩溃时至少能看到部分数据 | **什么都没有**，除非预写 |

## 12. 自检题

能用自己的话答上来，才算真懂。

**Q1：为什么工具 handler 不能等子 agent 结果？**
> 答案要出现两个词：**占槽位**、**卡这一轮**。
> 只说"会更慢"没到位。
> 更准确的说法：结果**不从返回值来**，从队列来。

**Q2：background job 里也是异步、也唤醒，为什么它不算 subagent？**
> 关键是**里面装的是什么**：进程 vs LLM 会话。
> 答"因为它是脚本"不够，要说清：脚本写死了规则，不能改主意。

**Q3：工具调度器那个并行，为什么不能直接拿来跑 subagent？**
> 答案落在**时间粒度**：一个是同轮内收齐结果才能过，一个是跨回合、不要求这一轮等。

**Q4：派出去的子 agent，父级最后能拿到什么？**
> **一条消息，内容是它最后那段文本。** 没有过程、没有 tool call。
> 答"结果"就还没抠透。

**Q5：如果子 agent 的事件进了父总线，`/resume` 之后会发生什么？**
> UI 会重放出子 agent 的全过程，但模型上下文里只有那句结论。
> **这个不一致会一直存在。**

**Q6：进程崩溃时，父会话文件里有什么？**
> **什么都没有。** 连"派过子任务"都不知道。
> 这就是为什么需要预写 launch 行。

```
1. SubagentManager（创建/启动/取消/回收 + 注册表）

7. 并发上限 m_maxActiveSubagents / 深度 m_subagentMaxDepth
8. 预写 launch 行（崩溃可见性）
9. 结果入父上下文（可折叠显示，不污染重放）
```

**最小闭环**：第 1–6 步。做完就能验证"子 agent 跑完，结果有没有出现在父级上下文里"。

**明确不做**：
- ❌ 让 handler 阻塞等结果
- ❌ 把 subagent 塞进同轮工具调度器
- ❌ 无锁上下文上跨线程写
- ❌ 指望模型自己写清输出约定
- ❌ 没有 maxDepth 就放出递归能力
- ❌ 子过程事件进父总线

### 13.2 补充一：语义依赖不可检测（最重要）

**原文档讲的是「机制如何运行」，没讲「机制的边界在哪」。**

原文档 §3.2 的表格已经正确显示 `{R1,R2}` → `{W3}` → `{R4,R5}`，即写是屏障。但它没有明说一个关键推论：

> **调度器不理解语义，只尊重顺序。** 模型给出的调用顺序**就是**它对依赖关系的声明。

后果：

| 模型写法 | 行为 | 正确吗 |
|---|---|---|
| `[write, read]` | read 等 write 提交 | ✅ 读到新内容 |
| `[read, write]` | read 先跑 | ✅ 通常是想要的 |
| **`[read, write, read]`** | 两个 read 分别在屏障两侧 | ✅ 正确 |
| **`[write, read]` 但模型写成 `[read, write]`** | read 先执行 | ❌ **读到旧数据** |

**最后一行是补充重点：顺序排错时，调度器不会报错，也不会纠正，读到什么就是什么。**

所以「读不用等写」这个直觉是**错的**——准确说法是：

> **不是「读不用等写」，而是「连续的安全调用可以重叠；写是屏障，它前后都得串行」。**

对 subagent 的启示：**父级切分并行子任务的范围，也是一种依赖声明。** 调度器不会发现两个子任务在写同一个文件。

### 13.3 补充二：subagent 不能作为工具调度项

原文档全文未涉及 subagent。今天得出的结论要补上：

| | 工具调度器 | subagent |
|---|---|---|
| 时间跨度 | **一轮之内** | **跨回合** |
| 完成条件 | 全部收齐按序提交，回合才能过 | 不要求这一轮等 |

**把长命对象塞进短命调度器 → head-of-line 直接变死锁。**

原文档 §16.1 把 head-of-line blocking 列为「可接受的代价」，那个判断在**同轮工具**范围内是成立的（工具再慢也就几十秒）。但 subagent 是分钟到小时级——同一个机制放在那个量级上，代价从「可接受」变成「不可用」。

**这是同一机制在不同时间尺度上的适用性边界**，值得单独记住。

### 13.4 补充三：跨 agent 写冲突不在保护范围

原文档 §16.3 提到：

> 必须自行保证语义安全（同文件冲突、锁竞争等）

但那是**单 agent 内**的语境。补上 subagent 场景：

| 冲突源 | 有保护吗 |
|---|---|
| 同一 agent 内，工具间写同一文件 | ✅ 写是屏障 → 串行 |
| **父 agent 与子 agent 写同一文件** | ❌ **无任何保护** |
| **两个子 agent 写同一文件** | ❌ **无任何保护** |

调度器只在**自己的 agent 内**生效。每个子 agent 有自己的调度器实例，跨实例之间没有任何协调。

**所以「切分不重叠的写范围」必须由父级在派发时完成**，不是运行时能补救的。这也是原文档 §16.3 那条建议在 subagent 语境下要**升级为硬要求**的原因。

### 13.5 补充四：`abort()` 是实例级，不是请求级

原文档 §7 讲的取消是 **step 内的 `AbortSignal`**，协作式、按调用生效。这个机制本身没问题。

但补一个原文档不涉及的层面：**HTTP 客户端的 `abort()` 是实例级的**。

```cpp
virtual void abort() = 0;   // 中止"正在进行的请求"（无请求句柄）
```

| 场景 | 后果 |
|---|---|
| 父级 ESC | ✅ 杀掉全部（可能是想要的） |
| **子 agent 超时/取消** | ❌ **连带杀掉父级的在途请求** |
| 两个子 agent 并发 | ❌ 互相清掉中断标志 |

**所以每个 agent 必须有自己的 client 实例。** 这与工具调度器的 signal 机制是两个层面，不要混淆。

### 13.6 补充五：逐参数判定的生产使用率
