# 分析-agent 流程门禁与任务分级设计

> **状态**：分析稿（讨论沉淀，供后续研究；不定接口、不定数据结构）
> **创建**：2026-09-11
> **来源**：人机多轮讨论（目标：精确指导大模型干活 → 前置工作 → 实现前预审 → 软硬约束选型 → 任务分级）
> **性质**：本分析讨论的是 **agent 工作流机制本身**（非 CLFCode 项目功能），放此备查
> **关联**：《分析-dsh沙箱机制.md》（同属对 agent 基础设施的观察）

## 一、问题缘起

**目标**：让 agent 精确干活——靠"详细设计方案"（具体到步骤、示例代码、测试步骤）指导执行，减少返工。

**观察到的现状**：

1. 真正干活的重心是"**设计 → 代码实现**"环节；而前期的**分析、设计、审查是不显式的、可有可无的**——经常被跳过
2. 跳过的方式很隐蔽：一句"给我设计个 X"就直接进设计，前置工作（需求澄清、现状取证、约束明确）没做
3. 目前靠**人工**（使用者每步拍板）+ **pro 取证**兜着，没有机制化

**用户的核心判断**（讨论后确立）：

> 设计出问题，绝大多数不是模型设计能力不够，是**输入不够**——模型只好拿假设填空。

## 二、核心洞察（讨论中形成的结论）

### 2.1 模型用假设填空，假设不显式就是地雷

- pro 的"全局思考"能保证设计**自洽**，保证不了**符合现实**：它不知道的现状（代码实际长什么样、已有约定、真实意图）只能猜
- 猜的东西不写出来 → 设计文档看起来完美，实施时发现地基是假的 → 返工最贵
- **前置工作的本质：把"模型必须猜的"变成"已知的"**

### 2.2 流程状态必须在产物里，不能在 agent 脑子里

- 模型永远觉得"我已经想过了"——只要流程状态是主观的，门禁必然被绕过
- **第一原则：门禁检查的是产物，不是 agent 的自我报告**
- 实证：CLFCode 项目这套流程能跑，本质是因为有 `.claude/plans/` 产物体系 + 人在每个环节拍板

### 2.3 少返工的真实来源：每步消除一类不确定性

| 步骤 | 消除的不确定性 | 可检查的判据 |
|---|---|---|
| 分析 | 需求/现状的未知 | 未知项清单为空、现状有取证 |
| 设计 | 方案/接口的未知 | 改动点明确、验收标准可执行 |
| 测试/回归 | 实现正确性的未知 | 用例覆盖、回归全绿 |

> 门禁该问的是"**这类不确定性清了吗**"，而不是"文档写了吗"——前者挡真问题，后者催生走过场的文档。

### 2.4 事实类 vs 逻辑类：模型审查的边界（最贵的一课）

| 问题类型 | 例子 | 谁来抓 |
|---|---|---|
| **逻辑类**（缺口/矛盾/不完备） | 缺验收标准、方案自相矛盾、功能点漏设计 | 独立模型审查（新上下文）**有效** |
| **事实类**（现状断言对不对） | "现在工具注册是 X 样"（实际是 Y） | **必须实读取证/实测**——模型审查会自信地确认错误事实（与作者共享盲区） |

**实证（CLFCode 项目三处，均由 pro 实读取证翻案）**：

| 项 | 原设计（基于扫描报告的推断） | 取证结论 | 若未取证直接实施 |
|---|---|---|---|
| C1 | FileOps"移入 CLFCore 目录"（最省事） | 与阶段 2 能力插件边界冲突 | "拆了又焊"，阶段 2 必须再返工 |
| A2 | UTF-8 截断做双函数（安全版+字节版） | 全库无精确字节场景 | 多一个没人用的函数 + 双份测试 |
| B2 | cmdClear 有确认交互，需收敛 4 方法 | 无确认交互（证伪） | 改错地方 |

> 三处都不是"设计得不好"，是**推断代替了取证**。

### 2.5 前置工作的最小构成（三侧 + 一清单）

| 侧 | 要补什么 | 缺了会怎样 |
|---|---|---|
| 目标侧 | 成功标准、**不做什么**（非目标） | 设计跑偏/镀金 |
| 现状侧 | 涉及既有系统的，**实读取证** | 设计基于错误现实 → 实施即返工 |
| 约束侧 | 接口/结构/兼容性红线 | 方案被推翻重来 |
| **假设清单** | 模型自补的每条假设，标"待验证/已验证" | 地雷埋进设计 |

## 三、实现前预审门（设计 → 开发的关口）

**定位**：设计完成后、进入代码开发之前，引入一次独立检查；能发现的问题在此刻提出，交使用者决策。

### 3.1 "自检"与"独立调用"是两件事

- **同上下文自检** = 自己批自己作业（确认偏差，只会答"基本完整，建议补充"）→ 只适合机械核对
- **独立调用（新上下文）** = 新鲜视角，真正挑刺 → 适合逻辑审查
- 两者分工：自检管"清单在不在"，独立调用管"有没有矛盾/缺口/未定义边界"

### 3.2 不能问"完整吗"——必须清单化逐条核对

| 维度 | 核对项 |
|---|---|
| 设计完整性 | 目标/非目标、现状取证、改动点、接口定义、验收标准、风险、假设清单 |
| **功能完备性** | 需求每个功能点 → 设计里有对应条目？（双向追溯：漏的 / 镀金的） |
| **测试覆盖** | 每个改动点有验证方式？边界/失败路径覆盖？验收标准能跑出通过/失败？ |
| 现状一致性 | 设计里对既有系统的断言，逐条有取证？ |
| 可逆性 | 出问题怎么退？ |

**输入包必须完整**：设计文档 + 需求（目标/非目标）+ 现状取证事实——三者缺一，检查者无从判断"完备"。

### 3.3 输出收敛成"能否实施 + 最小决策集"

预审产出**不是**问题清单直甩使用者（负担重 → 全部放行），要三级收敛：

- **硬缺口**（缺验收标准、测试计划空白）→ 必须补，不补不许实施
- **疑点**（假设未验证、边界未定义）→ 收进"需用户决策项"（最好 ≤3 条，附默认建议）
- **建议**（可选优化）→ 只记录，不阻塞、不清单化

**结论一句话**：可进入实施 / 需先补充 X / 需你先拍板 Y 和 Z。

## 四、软硬约束三档选型（用户纠结点及解法）

### 4.1 三档的软肋（用户总结）

| 档 | 软肋 |
|---|---|
| skill 规范 | 软——主要看大模型（可能不加载、加载了也可能不遵守） |
| 系统提示词 | 软——每次必携带，消耗资源 |
| 代码级设计 | 硬——限制 agent 能力，"必须这么干" |

### 4.2 解法：规则分两类，各有唯一解

| 规则类型 | 例子 | 放哪 | 理由 |
|---|---|---|---|
| **机械可判定** | 有没有设计产物、验收标准字段是否为空、测试跑没跑 | **代码/门禁** | 不需要模型判断——放代码是替它省注意力，不是限制能力 |
| **需要判断** | 设计够不够好、这次算不算大改、假设要不要验 | **skill / 提示词 + 独立审查 + 人** | 代码写不出判定函数；"软"是这类规则的**本质**，不是缺陷 |

> 决策不是"放哪"，而是"**这条规则属于哪一类**"。分完类，两条路都是唯一解。

### 4.3 代码限制的是"自由度"，不是"能力"

- 自由度不是越多越好（类型系统/编译器/测试都在"限制"程序员，换来可靠）
- **关键是限制的位置**——参照 git：本地随便 commit/rebase（自由），只有 **push / force-push** 设门禁（不可逆）
- 推论：**只限制不可逆关口**（动手写代码前、发布前、删数据前），过程（读、分析、试跑、探索）保持自由
- **探索给自由，落地给门禁**

### 4.4 让"软约束"变可靠的方法

| 没用的写法（靠自觉） | 有用的写法（靠结构） |
|---|---|
| "设计要做完整" | "设计产物必须回答这 6 项：目标/现状取证/改动点/验收标准/风险/假设清单" |
| "实施前要审查设计" | "实施前产出预审结论：可实施 / 需补 X / 需决策 Y" |
| "注意别遗漏测试" | "测试计划必须逐条对应改动点" |

- **把行为要求变成产物结构**：不填就是肉眼可见的缺失（人一眼能查、独立模型能查、将来机械检查也查得动）
- **检查点代替规则**：规则会被忽略，检查点不会——流程停在那儿等人
- **提示词只留钩子**：系统提示里不塞规范全文，只放"写设计/实施前必须加载 design 规范 skill"一行

### 4.5 资源顾虑的化解

```
系统提示词：1-2 行钩子（触发指针）      ← 成本可忽略
skill：完整规范（按需加载）             ← 成本只在用到时
代码：1-2 个不可逆关口的门禁            ← 开发量可控
```

## 五、任务分级与流程裁剪（文档 vs 代码）

### 5.1 分类轴不是"代码 vs 文档"，是三个属性

| 属性 | 代码（重） | 文档（轻） |
|---|---|---|
| 返工代价 | 高（重编/重测/牵连模块） | 低（改几个字） |
| **可验证性** | **有硬反馈**（编译/测试） | **没有客观验证** |
| 分解性 | 可拆（接口定了各写各的） | 通常一口气写完 |

### 5.2 文档的真相：缺编译器 → 错误静默存活

- 代码写错会挂；文档写错**没人报错**（写错的 API、过时的流程、不存在的功能）
- 感受上"文档流程可有可无"，真实原因是**没有反馈逼着你做**
- 实证：CLFCode P2-6——注释说"SystemPromptBuilder 调 FileOps::readFile"，实读证伪（其用裸 ifstream 自读）

**结论：文档需要的不是"没有门禁"，是不同形态的门禁**——核心是**取证**与**审阅**，替代代码的编译与测试。

### 5.3 两条最小动作集

| | 代码链路（重） | 文档链路（重） |
|---|---|---|
| 前置 | 现状取证 → 详细设计 → 预审门 | 目标/受众明确 → **关键事实取证** |
| 主体 | 实施 | 落笔（写就是设计，无需单独设计环节） |
| 收尾 | 测试 → 回归 | **成稿审阅**（挑事实错误、挑结构） |
| 硬反馈替代 | 编译器/测试 | **独立审阅者 + 取证** |

### 5.4 廉价分级 + 按代价裁剪

```
任务进来 → 廉价分级（两个问题）：
  ① 这次产物会被别人/以后依赖吗？
  ② 做错了返工代价大吗？
      两个都"否" → 直接干（代码/文档同理）
      有一个"是" → 取对应类型的最小必要动作集
```

- 分级判定必须**廉价**（分级本身不能成负担，否则又成仪式）
- 实操：agent 提分级建议 + 使用者一句话确认/推翻（比让它自决可靠）
- **把关总量不变，从"全链路"变成"按代价分配"**

## 六、可量化标准与自检法

1. **详细方案的验收标准**：执行期"**待决策项 ≈ 0**"——执行者不需要做设计决策，方案才够详细
2. **执行者视角评审法**：把方案给执行者（或假装是），问"照着这个能不能干？哪里还得我自己拿主意？"——**凡是需要拿主意的地方，就是该补的地方**（pro 审查时列"待裁决点"即此法）
3. **详细度的边界**：写死"影响做成什么样"的（接口/数据结构/路径命名/错误策略/边界行为/验收标准/测试用例），放开"怎么敲键盘"的（循环写法/局部算法/实现顺序）
4. **详细度上限提醒**：过度详细会把方案本身的错误一起固化 → 必须配"**允许偏离**"机制：执行中发现方案有误 → 停下提出 → 决策 → 修订

## 七、落地形态建议（分层 + 演进）

| 层 | 放什么 | 触发时机 |
|---|---|---|
| 系统提示词 | 极简铁律（≤5 条）+ 规范 skill 的触发钩子 | 全程 |
| skill | 规范主体：设计模板、预审清单、取证表、各任务类型最小动作集 | 按任务加载（描述里的 "Use when..." 决定触发） |
| 代码/门禁 | 仅"机械可判定 + 违反有不可逆损失"的关口（如：无设计产物不许进入实施） | 动作发生瞬间 |
| 独立审查 + 人 | 判断类（设计质量、取舍） | 预审门 / 实施后验收 |

**演进路径**（不要预先硬化）：

```
① 先写 skill（快、便宜、可迭代）
② 试跑，记录"哪些规则反复被违反"
③ 其中"能机械判定 + 代价大"的 → 提格为代码门禁
   其余（判断类）→ 永远留在 skill + 独立审查 + 人
```

> 门禁规则要**从未遂事故里长出来**，不能拍脑袋预先设计——预先设计的门禁要么误伤（简单任务被拦），要么被绕过（模型学会走豁免通道），变成新仪式。

## 八、待研究（开放问题）

1. **分级判定**怎么做到"廉价又准确"？（两个问题够不够？谁来判？误判的兜底？）
2. **预审的输入包与输出格式**具体设计（独立调用的提示怎么组织、清单怎么呈现）
3. **假设清单的可验证性**：谁来验、验证记录放哪、验证通过的标准是什么
4. **文档类任务的取证与审阅**如何低成本落地（受众明确、事实核对的最小动作）
5. **各任务类型的最小动作集**需要逐个沉淀（代码/文档/调研/配置/数据…）
6. 与 **dsh 现有原语**的映射：goal / plan / todo / subagent / hooks / skill 各承担哪一环
7. 流程"稳定"的判据（何时该把手工流程固化成模板/机制）——目前的判断：**同类纠偏开始重复出现、不再有新方向冒出时**

## 九、原则清单（便于记忆）

1. 设计出问题多半不是能力不够，是**输入不够**——模型用假设填空
2. **流程状态必须在产物里**，不在 agent 脑子里
3. 每步消除**一类不确定性**——判据问"不确定性清了吗"，不问"文档写了吗"
4. **模型审查抓逻辑，实读取证抓事实**——事实类错误模型会自信确认
5. 代码限制的是**自由度**不是能力——**只限制不可逆关口**（git 的 push/force-push）
6. **把行为要求变成产物结构**——软约束从"靠自觉"变成"靠完整性"
7. 详细度的极限不是写得多，是**执行者不用拿主意**（待决策项 ≈ 0）
8. **把关总量不变，按代价分配**——轻任务近乎零环节，重任务上全套
9. 门禁要**从未遂事故里长出来**，不预先设计
10. 允许偏离：执行中发现方案有误 → 停下提出 → 决策 → 修订（防止把方案错误一起固化）
