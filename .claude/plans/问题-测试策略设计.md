# 问题-测试策略设计

## 最终方案

核心思路：**不测试 LLM，测试代码对 LLM 响应的处理能力。**

## 三层策略

| 层级 | 名称 | 频率 | 测什么 |
|:---|:---|:---|:---|
| L1 | 单元测试 | 每次提交 | 纯逻辑：Context 截断、配置加载、序列化、安全策略 |
| L2 | 集成测试 | 每次提交 | Mock LLM → Agent 行为验证 |
| L3 | E2E | 手动/发布前 | 真实 API 调用，断言宽松 |

## L1 单元测试

少量，只测不依赖外部服务的纯逻辑类：
- `CLFContext` 的 token 估算和截断
- `CLFConfigLoader` 的 JSON 解析
- `CLFSecurityPolicy` 的模式判断
- `CLFFileOps` / `CLFCommandExec` 的函数逻辑

## L2 集成测试（主力）

**Mock HTTP 客户端**，从 `test/fixtures/` 读取预设 JSON 响应。

```
test/fixtures/
├── response_normal.json          ← LLM 返回纯文本
├── response_tool_calls.json      ← LLM 请求读文件
├── response_multi_tools.json     ← LLM 请求多个工具
├── response_error_400.json       ← API 返回 400
├── response_malformed.json       ← API 返回乱数据
└── response_stream.txt           ← SSE 流式数据（多行）
```

测试场景示例：
```
"LLM 请求 readFile → Agent 执行 → 结果回 LLM → 得到最终答案"
  ① 注入 response_tool_calls.json
  ② 验证 fileOps.readFile 被正确调用
  ③ 验证上下文包含工具结果
  ④ 注入 response_normal.json
  ⑤ 验证最终输出符合预期
```

LLM 的不确定性被完全消除——测的是 Agent 调度逻辑，不是模型智商。

## L3 E2E

手动触发，真实 DeepSeek API 调用。断言宽松——不精确匹配，只验证任务完成。

```
"Agent 能读取配置文件": 
  输入  "读 config/agent_settings.json，告诉我 base_url"
  断言  exit code == 0 && stdout 包含 "api.deepseek.com"
```
