**CLFContext.cpp（205）——本轮次大发现**

| 混杂点 | 位置 | 问题 |

### 🟡 轻度问题

**CLFConfigLoader.cpp（233）——"追加打补丁"形态的典型样本**
- `loadFromFile` 30+ 个 `if (cfg.contains(...))` 解析块（:90-202）——每加一个配置项改 2 处（CLFAgentConfig struct + 解析块），函数随版本无限变长
- 处置：表驱动重写（静态字段映射表：`{key, 读取 lambda}` 或 `{key, 目标指针+类型枚举}`）——C++17 无反射，用 constexpr 表 + switch 最小化；或接受现状仅记录（pro 执行时评估收益）
- 其余（findProjectRoot/resolvePath）OK

**CLFSecurityPolicy.cpp（120）——双簇职责**
- 簇 1：模式安全策略（isAllowed/getModeName/nextMode/modeFromString）
- 簇 2：危险命令检测（isDangerousCommand×2/normalizeCommand/kDangerousPatterns/allowlist）——注释自承"提示层而非安全边界"，性质不同
- 处置：拆 `CLFDangerousCommandDetector`（纯检测可独立测试）；SecurityPolicy 持实例组合

**CLFProtocolAdapter.cpp（231）——2 小项**
- `isUsageStreamSupported`（:17-29）硬编码 deepseek.com——加 provider 必改代码（O 违反）；处置：配置声明或 provider 表（阶段 3 多 provider 时必要）
- `parseAssistantResponse` 错误文本装 `m_content`（:100/108/117，"[Error] ..." 字符串）+ m_finishReason="error" 标志——**错误语义与内容混杂**；处置：显式 m_error 字段（A4b 结果定型时一并）

**CLFLogger.cpp（111）——1 隐患**
- :97 `std::filesystem::path logPath(m_filePath)` 窄字符构造——**MSVC 按 ANSI 代码页解释 UTF-8 路径，中文日志路径会创建乱码目录**（编码陷阱族，与 memory 记录同族）；:102 `ofstream::open(m_filePath)` 同患
- 处置：u8path 双修（顺手批）

**CLFClipboard.cpp（40）——错误耦合**
- include CLFCore/CLFContext.hpp 仅为 sanitizeUtf8——UI 层错误依赖 core 的重型头；随 sanitizeUtf8 归位 CLFEncoding 自然消除

**CLFToolExecutor.cpp / CLFBuiltinTools.cpp / CLFTerminal.cpp**：分册已列（P0-2/P1-5/1-2/1-3/1-4），无新增。

### 🟢 干净文件亮点（不动的理由）

- CLFMessageCodec：字段 helpers 已被 jsonl 与覆盖式**共用**（已收敛过一轮）；与 ProtocolAdapter::serializeMessage 的格式差异是**协议差异非重复**（会话文件格式 vs API 格式，勿合并）
- CLFAsyncSubmit：m_submitting 已 atomic（无数据竞争）
- CLFSearchContent/CLFCommandExec/CLFFileOps/CLFWebFetch：职责单一、仅依赖 basic 层——**迁 DLL 条件天然满足**（验证阶段 2 拆分）
- CLFPasteCoalescer/CLFSelectionModel/CLFTipsBar/CLFPeriodicTimer：纯逻辑状态机/工具，设计文档齐全
