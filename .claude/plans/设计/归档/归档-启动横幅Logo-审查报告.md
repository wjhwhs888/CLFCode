   → 文档假设"w≤0 就不折行"错误，**照样按 78 硬切**
5. **验证方案会给出假绿**：§7 步骤 0 的 probe 路径
   （`parse → color/bold → hbox → Screen::ToString`）**恰好绕过了唯一会出问题的
   `CLFReplView` 硬换行**（且见 F0a：FTXUI 只裁剪不折行）

**为什么这是 F0 而非 F1**：该结论**推翻整个宽度论证的前提**——
"选紧凑变体还是宽变体""判据用码点还是 `string_width`"全部是**伪问题**；
`charWidth` 口径下块字宽度**≈2×**，**块字在 80 列终端上无法存活**。

**讽刺之处**：`renderCharWidth`（[CLFTextUtil.cpp:147-152](../../../src/CLFTypes/CLFTextUtil.cpp#L147-L152)）

**但折行路径用的是粗口径的 `charWidth`**。`CLFTextUtil.hpp:52-54` 声称的

### F0a — FTXUI 对超宽内容是**裁剪而非折行**——§4.2 的「超宽折行」论断错误

**原文**（§4.2 决策表）：「终端 121 列充裕；**FTXUI 按行渲染，超宽折行**」

**实测证据**：

- `Text::Render`：`if (x <= box_.x_max) { screen.CellAt(x, y).character = cell; }`
  —— 越界字符**直接丢弃**，**无任何换行分支**
  （[text.cpp:94-126](../../../3rdparty/ftxui/src/ftxui/dom/text.cpp#L94-L126)）
- `HBox::SetBox` 按 `requirement.min_x` 顺序分配 `box.x_max`，同样不折行
- 折行**只**由 `CLFReplView.cpp:187` 的硬换行完成（见 F0）

**后果**：§7 步骤 0 的 probe 若用固定尺寸 `Screen::Create` 渲染超宽内容，
看到的是**被裁掉**，会把 F0 的撕裂误判为"没折行、看起来正常"；
也可能把裁剪误读成缺字/豆腐块，**污染 §4.4 的判读**。

**修正建议**：probe 不靠目测 `Screen::ToString()`，直接对每行调
`ftxui::string_width()` 断言；且**必须额外**跑一遍用 `CLFReplView.cpp:186-196`
同口径复刻的硬折行，否则无法证明生产路径成立。

### F0b — 变体 3「纯 ASCII」若有行以 `|` 开头，会被表格检测**吞掉并重排**

> ⚠️ 本条直接影响 F0 的补救方案 (a)：**ASCII 兜底字形本身有坑**。

**证据**（[CLFTerminal.cpp:138-150](../../../src/CLFUI/CLFTerminal.cpp#L138-L150)）：
`\n` 到达时若该行首（跳过空白后）是 `|`，整行进 `m_tableBuffer` 而非 `m_contentBuffer`；
随后 `flushTable()`（[CLFTerminal.cpp:160-221](../../../src/CLFUI/CLFTerminal.cpp#L160-L221)）
按 Markdown 表格处理——按 `|` 切单元格、用 `displayWidth` 补列宽、
每列重包成 `"| " + cell + " |"`。

常见 ASCII 大字（Banner / Doom / Standard 等）**不乏以 `|` 开头的行**。
一旦命中，那几行 logo 会被**当表格重排补空格加边框，视觉直接报废**，
且**只在启动瞬间出现一次，极难归因**。

**修正建议**：§7 候选字形的验收项加硬判据——
「**每行首个非空白字符不得为 `|`**」；变体 3 定稿前逐行跑一遍。

### F0c — §5.4 栈恢复伪码未定义「压旧值还是压新值」，误读会引入**新的跨段污染**

**原文**（§5.4 伪码）：`fg = fgStack.empty() ? -1 : fgStack.back();`，
注释仅写「`\033[1m` / `\033[3Xm` 在'值实际改变时'压栈」——**没说压哪个值**。

**误读后果**（若实现成"压入刚设置的新值"）：最外层 reset 会把刚被清掉的属性**又还原回来**：

| 现行调用 | 位置 | 误读后的后果 |

| `bold("● CLFCode") + " — CLI Agent Framework for Code"` | [CLFRepl.cpp:280-281](../../../src/CLFUI/CLFRepl.cpp#L280-L281) | reset 后 bold 仍 true → **tagline 整行变粗** |
| `red("✗ 异常: ") + e.what()` | [CLFRepl.cpp:359-360](../../../src/CLFUI/CLFRepl.cpp#L359-L360) | reset 后 fg 仍 31 → **整条错误消息变红** |
| `red("✗ ") + firstLineCapped(msg,200)` | [CLFTerminal.cpp:363-367](../../../src/CLFUI/CLFTerminal.cpp#L363-L367) | 同上 |

全是"无报错、布局不变、只变视觉"，正落进 §2.3 自己定义的"难定位"类别。

**另一处缺口**：`22`（bold 关，[CLFAnsiParser.cpp:41](../../../src/CLFUI/CLFAnsiParser.cpp#L41)）
与 `39`（前景默认，`:43`）在伪码里**没有对应出栈动作**，
而模型内容流的 SGR 白名单允许这两个码通过
（[CLFTerminal.cpp:127-135](../../../src/CLFUI/CLFTerminal.cpp#L127-L135)）——

**修正建议**：伪码补明「**压旧值**」（`fgStack.push_back(fg); fg = code;`）
或改为"每层存整份状态快照"；为 `22/39` 明确 pop 语义；
把 `\033[22m` / `\033[39m` **单列为回归用例**，而不只是步骤 5 写的"多余 reset 边界"。

### F1 — 块字宽度：决策表（38）与文档实际展示的样例（58）是**两个不同变体**，互不匹配

**原文**：

- §4.2 决策表：「宽度 **≤ 40 列** ｜ 终端 121 列充裕；FTXUI 按行渲染，超宽折行」
- §6.1：「→ 判断须写 `w > 0 && w < 40`」
- §8-2：「块字每行显示宽度 **≤ 40 列**（UTF-8 码点计）」
- §4.2 的样例块字本体（设计稿 163–168 行）

**实测（主审本机复算，码点数与字节数一致——证实全为单宽）**：

| 设计稿行 | 码点/字节 | 内容 |
|---|---|---|
| 163 / 164 / 167 / 168 | **58** | 宽变体（字间双空格） |
| 165 / 166 | **56** | 宽变体（行尾缺 2 空格） |
| 169（tagline + 版本） | 49 | — |

**问题性质（比"数字写错"更麻烦）**：

> ⚠️ **主审自我修正**：主审初稿称"决策表的 40 参考的是紧凑变体（38 列）"，
> 经复算**该说法错误**——紧凑变体（去掉字间空格）**同样是 58 码点**
> （主审实测；`displayWidth` 口径 = 116）。**两个变体都远超 40**，
> 故"40"不是"选错了变体"，而是**从未算对过**。

| 变体 | 码点数 | `displayWidth`（实际折行判据） |
|---|---|---|
| 文档展示的宽变体 | 56–58 | 89–110 |
| 紧凑变体（去字间空格，主审实测） | **58** | **116** |
| tagline + 版本行 | 49 | 50 |

**因此**：

1. **没有任何变体满足 ≤40**——差距不是微调，是 58 vs 40（`displayWidth` 口径下 2–3 倍）
2. pro 若**照抄文档里的样例**（最自然的做法）→ 得 58 码点 → **违反决策表与 §8-2**
3. pro 若**按 ≤40 缩** → 必须换成文档没展示、也没定义过的第三种字形
4. **§6.1 另有逻辑漏洞**：终端宽 41–57 列时 `w < 40` 为假 → 不触发降级 → 照打 58 列
   → **折行 → 违反 §8-3「窄终端下不折行」**。阈值 40 与"不折行"目标之间没有推导关系
5. **且真正的判据见 F0**：`displayWidth` 口径下块字 ≈2×，
   即使真的做到 40 码点，也会被判为 80 → 在 78 列的 fallback 阈值下**依然折行**

**关于"码点计数"判据（修正主审与审查员 A 的分歧）**：

- 主审实测：文档样例全为单宽字符，**码点计数在此例中结果正确**
- 审查员 A 实测：审查员自己构造的 58 列变体同样为单宽，结论一致
- **但判据仍然要换**：理由不是"码点算错了"，而是**码点数测不出字体双宽渲染**
  （§4.4 已指出 `█`/`╗` 在部分 CJK 字体下可能渲染 2 格，
  而 FTXUI 的全宽表 [string.cpp:33-73](../../../3rdparty/ftxui/src/ftxui/screen/string.cpp#L33-L73)
  **不含** U+2500–259F，即 FTXUI 恒按 1 格布局 → 一旦字体渲染 2 格就会**整行错位**）。
- FTXUI 自带 `string_width()`（[string.hpp:29](../../../3rdparty/ftxui/include/ftxui/screen/string.hpp#L29)），
  **应改用它**，且它只解决"模型宽度"，**测不出**字体实渲染宽度——后者只能实机目视。

**修正建议**：

1. §4.2 的**展示样例与决策表统一到同一个变体**（建议用紧凑 38 列变体，已接近 40 上限）
2. 阈值**由 §7 步骤 0 实测回填**；回填前写占位（如"目标 ≤ 终端宽 − 余量，待回填"）
3. §6.1 阈值改为「`w <` 块字实测宽度 + 安全余量」，并**补上 41–57 列区间的处置决定**

### M1 — 宽度判据：结论对，**论证错**，且遗漏真正的风险

**原文**（§7 步骤 0 取证项②、§8-2）：以「UTF-8 **码点**数」为显示宽度判据；

1. **FTXUI 提供权威函数** `string_width()`，

### M11 — 【新增维度】§4.4 只列了"缺字/粗细/基线"，**漏了"宽度歧义"**

U+2500–257F（Box Drawing）与 U+2580–259F（Block Elements）在 Unicode
`EastAsianWidth.txt` 中是 **Ambiguous(A)**；CJK 语境下终端把它们渲染成 **2 格**
有历史先例（GNOME VTE 有专门的 "CJK: Fix width of Box Drawing and Block Elements
characters" 提交）。一旦命中，FTXUI 的 Screen 缓冲格数与实际终端格数**差一倍**，
`Screen::ToString()` 的输出在真终端上**整行右移/回绕**。

**这比缺字更隐蔽**——不缺字、不报错，只是整体错位。

**修正建议**：步骤 0 实机验证加一条——在目标终端把块字行与其后紧跟的一串标记字符
（如 `|<--58-->|`）同屏输出，确认标记确实落在**第 58 列**而不是第 116 列；
同时确认终端的"歧义宽度字符"设置为**窄**。

> 注：本条与 F0 **不同**。F0 是**项目内部口径**（`charWidth`）导致的错算，
> 与字体/终端无关，**必然发生**；M11 是**字体/终端**层面的歧义，**取决于环境**。
> 两者叠加时块字宽度可能被算成真宽的 4 倍。
