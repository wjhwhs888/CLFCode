## 二、read_file 的 workspace 校验参数化（本步唯一棘手的点）

**现状**：read_file 的边界校验（`isWithinWorkspace`）经 `CLFConfigLoader::getWorkingDir()`（core）取工作区根——插件不可链 core。

**定案（参数化，最小改动）**：

- 共享 handler 签名：`readFileToolHandler(args, allowAbsolute, workspaceRootUtf8)`——`workspaceRootUtf8` 为空串 = **跳过边界校验**
- `CLFBuiltinTools` 注册处传 `CLFConfigLoader::getWorkingDir()`——**主程序行为零变化**（qa_CLFBuiltinTools 回归钉死）
- 插件 `callTool` 路由传空串（2.2a 阶段跳过校验）——**⚠ 硬约束：2.2b 切换前必须定案校验归属**（倾向：校验移宿主侧装配处，与 CLFSecurityPolicy 同层——安全策略归 core 是既定架构；届时插件 handler 的 workspaceRoot 参数退出使用或删除）

> 风险声明：2.2a 出口时插件 read_file 无边界校验——但插件**未接线主程序**（宿主仍走静态注册），零实际风险面。此缺口与切换时序绑定，如实记录不掩盖。

## 三、共享 handler 设计（CLFFileOpsHandlers）

```cpp
// CLFFileOpsHandlers.hpp — 文件工具 handler 共享实现（2.2a，2026-09-21）
// 双消费者：CLFBuiltinTools（宿主静态注册，2.2b 前）与 tools.fileops 插件 DLL。
// 只依赖能力层（CLFFileOps）+ nlohmann json（第三方）——不依赖 core/UI。
// 2.2b 宿主装配切换插件后，CLFBuiltinTools 的注册删除、本文件仅剩插件消费者。
namespace CLF::CLFCapabilities {

// read_file：allowAbsolute=true 时跳过边界校验；workspaceRootUtf8 为空串 = 跳过
std::string readFileToolHandler(const std::string& args,
                                bool allowAbsolute,
                                const std::string& workspaceRootUtf8);
// write_file / edit_file / list_directory（零 core 依赖，直接共享）
std::string writeFileToolHandler(const std::string& args);
std::string editFileToolHandler(const std::string& args);
std::string listDirectoryToolHandler(const std::string& args);

} // namespace CLF::CLFCapabilities
```

**迁移内容**（从 CLFBuiltinTools.cpp anonymous 迁入，逻辑原样保真）：
- `withHandlerScaffold`（脚手架：parse/try-catch/dump）
- `sliceLines`（read 行范围切片）、`kMaxReadFileSize` 常量
- `isWithinWorkspace(workspaceRoot, path, err)`——**参数化改造**（原依赖 ConfigLoader 的取根改参数传入；逐段比较防前缀误判的语义不变）
- 4 个 handler 实现体

**CLFBuiltinTools.cpp 变化**：删 4 个 handler 实现 + `isWithinWorkspace`/`sliceLines`/`kMaxReadFileSize`（`withHandlerScaffold` **保留**——executeCommand/webFetch/get_current_time/echo 仍在用；executeCommand 的 cwd 校验改调共享参数化版 isWithinWorkspace）；注册 lambda 改 `readFileToolHandler(args, allowAbsoluteRead, CLFConfigLoader::getWorkingDir())`。

## 四、插件壳设计（CLFFileOpsPlugin）

```cpp
// CLFFileOpsPlugin.cpp — tools.fileops.dll 工厂与插件壳（2.2a）
// 多继承三接口：CLFPlugin（自描述/生命周期）+ CLFFileServiceImpl（file 服务，
// 复用进程内实现零重写——多继承子对象约束：服务表项各自视角 static_cast）
// + ICLFToolProvider（4 工具元数据 + callTool 路由到共享 handler）

class CLFFileOpsPlugin : public CLF::CLFPluginApi::CLFPlugin,
                         public CLF::CLFCapabilities::CLFFileServiceImpl,
                         public CLF::CLFPluginApi::ICLFToolProvider {
public:
    explicit CLFFileOpsPlugin(const CLF::CLFPluginApi::CLFHostApi* host)
        : m_host(host) {
        m_services[0] = {"file", static_cast<ICLFFileService*>(this)};
        m_services[1] = {"tool.provider", static_cast<ICLFToolProvider*>(this)};
        m_services[2] = {nullptr, nullptr};
    }
    // CLFPlugin：name="tools.fileops"、version="1.0.0"、hostApiVersion、
    // requiresServices=空、services()、init（true）、shutdown
    // ICLFToolProvider：toolCount=4；toolMeta 返回 4 个 CLFToolMetaPOD
    //   （read_file Read+ToolFlagRead / write_file Write / edit_file Write /
    //    list_directory Read+ToolFlagRead——与 CLFBuiltinTools 注册同文案同值）；
    //   callTool 按名路由 → 共享 handler（read_file 传 workspaceRoot="" 暂跳过校验，
    //   §二 注记）
};
extern "C" CLF_PLUGIN_EXPORT CLFPlugin* CLFPluginCreate(const CLFHostApi* host);
extern "C" CLF_PLUGIN_EXPORT void CLFPluginDestroy(CLFPlugin* plugin);
```

**关键点**：
- 元数据 4 套（name/description/parametersSchema/risk/flags）与 CLFBuiltinTools 注册**同文案同值**——2.2b 切换后模型看到的工具定义零变化
- `CLFFileServiceImpl` 多继承直接复用（无状态无成员，§一取证）——服务表项 `static_cast<ICLFFileService*>(this)` 指向该子对象 ✓
- 插件编码约定（2.1 §1.2 注记）：禁文件级非平凡静态对象；服务表为成员；异常零逸出

## 五、CMake

```cmake
# src/CMakeLists.txt（clf_capabilities 之后；插件不链 clf_core——只链它需要的）
```
