## 〇、拍板的方向（用户原话要点）

> - "C++，一定是动态库热拔插，这个是必然方向，如果是静态的，插件化的意义就不大了"
> - "插件化自己插件管自己的，自己给自己兜底" —— **插件自治 + 自兜底**
> - "你们插件的调用全部是外部的插件管理管的" —— **所有插件调用由外部插件管理器统管**

三点推演：
1. **静态编译期注册 = 无意义** → 每个模块是一个独立 DLL，可运行时加载/停用/替换
2. **自治**：每个插件自己管理自己的初始化/配置/状态/资源/错误处理；不给全局单例或隐式共享
3. **外部管理器统管**：插件之间**不直接互调**，一切调用（含模型→工具）经插件管理器路由——这是启用/停用隔离与热替换的前提

## 一、目标架构（DLL 热拔插形态）

```
main（极薄入口）
  └─ CLFPluginManager（外部插件管理器 —— 唯一编排者）
       ├─ 发现：扫描 plugins/*.dll（Windows 下 .dll / 跨平台预留 .so）
       ├─ 元数据读取 → 依赖图 → 拓扑排序 → 按序加载
       ├─ 生命周期：加载 / 启用 / 停用 / 卸载 / 热替换
       ├─ 调用路由：服务注册表 + 路由（一切外部调用的唯一入口）
       └─ 配置注入：各插件自己的配置段

插件 DLL（自治，自己管自己，自己给自己兜底）
  ├─ basic 插件      —— 宏/UTF-8/时间/结果类型（无业务，最底层）
  ├─ 能力插件        —— FileOps / CommandExec / Search / WebFetch（偏业务领域）
  ├─ 工具插件集      —— 元功能提供者："我提供了，你可以调"
  ├─ 适配器插件      —— handler：模型 JSON ↔ 能力翻译
  ├─ agent/会话/摘要/安全 插件 —— core 拆出的子单元
  ├─ network 插件    —— HTTP
  └─ UI 插件         —— 通过接口与后端交互（分界线）
```

**核心特征**：
- 依赖单向向下：basic → 能力 → core → 适配器 → UI
- 每个模块自治：内聚功能、对外统一接口、不越界、自兜底
- 模型/核心**永不直连**任何工具实现，一律 `manager.find("write_file")` 经管理器

## 三、DLL 热拔插设计（Windows/MSVC 约束下）

### 3.1 ABI 边界：C 工厂符号 + 纯虚接口

C++ 无稳定 ABI（尤其跨编译器/版本），**DLL 边界上禁止直接导出 C++ 类/STL/异常**。标准做法：

```cpp
// 每个插件 DLL 只导出两个 C 符号（唯一导出面）
extern "C" __declspec(dllexport)
CLFPlugin* CLFPluginCreate(const CLFHostApi* host);
extern "C" __declspec(dllexport)
void       CLFPluginDestroy(CLFPlugin* plugin);
```

- `CLFPlugin` = 纯虚接口（vtable 固定布局），导出面只有 C 符号，其余全部隐藏
- **跨边界禁传 STL 容器/string/异常**：字符串用 `const char*` + 长度或宿主提供的分配回调；复杂数据用 POD 结构或宿主 API 序列化（JSON）
- **接口版本化**：`CLFPlugin_v1` / `CLFHostApi_v1`——接口不兼容升级 = 新版本号，老 DLL 可继续用
- **内存归属规则**：谁分配谁释放；跨边界分配走宿主注入的 alloc/free（避免 CRT 堆不一致，强制统一 /MD）
- 插件内部可自由用 STL，仅在边界转换

```cpp
// 插件自描述（管理器加载后第一件事：读元数据，建依赖图）
class CLFPlugin {
public:
    virtual const char* name() const = 0;          // 全局唯一 ID，如 "tools.fileops"
    virtual const char* version() const = 0;
    virtual const char** requires() const = 0;     // 依赖的插件 ID（可空）
    virtual const char** provides() const = 0;     // 提供的服务名（可空）
    virtual bool init() = 0;                        // 自治初始化（失败 → 管理器标记禁用，其余不受影响）
    virtual void shutdown() = 0;                    // 自治清理
    // + 本插件领域的能力接口（如工具提供者：listTools/findTool/callTool）
};
```

### 3.2 CLFHostApi：管理器给插件的注入面

```cpp
class CLFHostApi {
public:
    virtual void log(Level, const char* msg) = 0;              // 日志（管理器统一）
    virtual const char* config(const char* pluginId, const char* key) = 0; // 本插件配置段
    virtual CLFService* getService(const char* pluginId, const char* service) = 0; // 经管理器拿依赖服务
    virtual void* alloc(size_t); virtual void free(void*);      // 跨边界内存
};
```

- 插件**拿依赖只能走 `host->getService(...)`** → 管理器路由 → 满足"调用全部由外部插件管理器管"
- 服务不可用（依赖被停用/加载失败）→ 返回 null → **调用方自兜底**（降级/报错，不崩）

### 3.3 管理器职责（CLFPluginManager）

| 职责 | 说明 |
|---|---|
| 发现 | 扫描 `plugins/` 目录的 DLL |
| 元数据/依赖图 | 轻量加载读 name/requires/provides → 拓扑排序 → 检出缺失/环 |
| 加载 | 按拓扑序 `LoadLibrary` + 工厂创建 + `init()` |
| 启用/停用 | 停用 = 先 quiesce（无在途调用）→ 通知依赖方 → `shutdown` → `FreeLibrary` |
| 调用路由 | 服务注册表：`(pluginId, service) → 实例`，find/list 供模型适配与 UI 用 |
| 配置注入 | 各插件读自己的配置段（见 §3.5） |
| 热替换 | 停用旧 DLL → 加载新 DLL → 路由切到新实例（新版本能力生效） |
| 隔离兜底 | 单插件 `init` 失败/运行异常 → 只标记该插件不可用，管理器与其余插件不受影响 |

**局限如实说明**：进程内 DLL 无真崩溃隔离（插件段错误 = 整个进程挂）。真隔离 = 进程级/独立进程，成本高一个量级——列为后续可选项，不阻塞当前设计。

### 3.4 "热"的语义（CLI 场景下务实的定义）

CLI agent 对话中热换工具插件是罕见场景，设计上支持但界定为：
- **启动发现 + `/plugin` 管理命令**：list / load / unload / reload（reload = 热替换）
- 卸载/替换仅在 **quiesce** 后执行（无在途工具调用；agent 空闲/回合边界）
- 对话中禁停用的兜底：模型已发起的调用若目标插件被停 → 管理器返回明确错误 → 模型自兜底（已有"工具失败重试/放弃"路径复用）

### 3.5 配置与数据归属（自治的具体化）

- 每个插件**自己的配置段**：独立文件 `config/plugins/<name>.toml`（或主配置分段注入）——推荐独立文件，卸载/替换不影响别的插件
- 每个插件**自己的状态/数据**：不写全局单例；数据文件路径经 host API 获取，不得越界写
- 兜底数据面：如 TipsBar 的 hardcoded fallback 模式可推广——插件缺配置/缺数据源时用内置默认自兜底

## 四、试点与演进路径

### 试点选择（改动最小、验证最全）

> 建议：**FileOps 文件工具组迁出为首个 DLL 插件**（自包含、无网络依赖、可离线验证），同时实现 CLFPluginManager 骨架。
> 备选：WebFetch（独立网络能力，但依赖 network 插件，试点期多一层依赖）。

试点验证点：
1. 动态加载：manager 发现并加载 FileOps DLL，读元数据入注册表
2. 路由：模型适配层调 `write_file` 改经 `manager.find("write_file")` → 路由到 DLL 内实现
3. 停用/热替换：`/plugin unload tools.fileops` → 再 `reload` 新版 DLL → 路由切新实例
4. 兜底：停用后模型再调 write_file → 管理器返回明确错误，模型走已有失败路径不崩
5. 依赖解析：FileOps DLL 声明 requires（如 basic），缺失时管理器报错且不影响其他插件

### 内部插件化子路径（对应总纲阶段 2；顺序 = 先管理器 → 试点 → 铺开）

```
2.1 插件管理系统：CLFPluginManager 骨架 + ABI 定义
    （CLFPlugin / CLFHostApi 接口 + 版本号 + CMake 每插件一个 DLL target）
2.2 试点：FileOps 迁出为首个 DLL 插件
    验证：动态加载 / 能力路由 / 停用 / 热替换 / 兜底 / 依赖解析
2.3 铺开：其余工具组（CommandExec / Search / WebFetch / 内置工具）逐一迁 DLL
    —— 同步删除 executor 名字匹配、CLFBuiltinTools 内注册散落
2.4 core 拆子插件：会话 / 摘要 / 安全 / todo 独立；adapter（handler）独立；AgentLoop 变纯编排
2.5 main 变薄：启动插件管理器 → 加载插件列表 → 初始化配置 → 等待输入
反向迭代：任一子步发现阶段 1 拆分不合理 → 回流修正（总纲 §三 出口标准重新核验）
```

### 构建/部署约束（MSVC，写入工程约定）

- 全插件统一编译链：MSVC + 统一运行时（/MD）+ 统一平台工具集 → CRT/STL 堆一致，跨边界安全
- 每个插件 = 独立 CMake target（`add_library(... SHARED)`），只导出工厂 C 符号，其余 `__declspec(dllexport)` 一律不加
- 接口头（CLFPlugin/CLFHostApi/POD 结构）= 唯一跨 DLL 共享头，独立小目标或 header-only，禁依赖其他头
