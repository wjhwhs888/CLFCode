## 一、背景与目标

### 1.1 背景
用户提问「脚本是不是 Windows 专用」触发对全仓平台耦合的摸底。结论：脚本层 100% Windows 专用（且依赖文件锁/rename 语义），但脚本不在本轮范围；程序层存在**分散、隐式、部分从未编译**的平台耦合。

### 1.2 目标（三条，缺一不可）
1. **收敛**：把散在多文件多处的 `#ifdef _WIN32` 与平台 API 调用，收敛到**单一平台能力层**。
2. **补分支**：对「只有 Windows 分支」「空实现」「退化实现」的点，**补齐显式分支**并标注未验证状态——不删除、不隐藏（用户定调：保留 + 加分支）。
3. **消重复**：合并完全重复的平台逻辑（exe 目录两处、`.dll` 后缀两处）。
4. **为第二期留门**（2026-09-22 目标升级）：平台层同时是**多平台接缝**——第一期只交 Windows 实现，但接口形状与 `[未验证]` 分支必须按「**将来要真编译**」的标准写，不许写成占位垃圾（第二期见 §十五）。

### 1.3 非目标（**第一期**明确不做）
- **第一期不做**「让 Linux 跑起来」——那是第二期（§十五）；但**不再禁止**为它留接缝。
- 第一期不加 Linux CI（CI 矩阵属第二期评估项）。
- 不引入运行时多态（虚接口 / 工厂）；**CMake 选源文件**留待第二期再议（§十五 决策点）。
- 不动 `3rdparty/`（含 FTXUI 的 patch）。
- 不动构建脚本、发布脚本、安装脚本（**脚本层的跨平台属第二期**，见 §十五）。
- 不重构无关模块；不做「顺手优化」。

### 2.4 本轮新实证的现成缺陷（不属跨平台，但同批可消）

★ **缺陷 1：临时文件清理双向错位**
- 清理端：`src/CLFUI/CLFRepl.cpp:139-143` 扫描**当前目录**的 `clf_cmd_stdout_*` / `clf_cmd_stderr_*`；
- 写入端：Windows 分支用匿名管道，**根本不产生临时文件**（`src/CLFTools/CLFCommandExec.cpp:44-163`）；POSIX 分支写在 `/tmp`（`CLFCommandExec.cpp:168-169`）。
- **判定**：Windows 上该循环是死代码；POSIX 上错位清理。两平台都清不到东西。

★ **缺陷 2：`2>nul` 无平台守卫**
- `src/CLFCore/CLFSystemInfoProvider.cpp:82, 90, 100` 裸露 `2>nul`，同一文件 `:34` 却用了 `2>/dev/null`；
- **判定**：POSIX 下 `sh` 会把它解释为「重定向到当前目录下名为 `nul` 的文件」——生成垃圾文件且不抑制 stderr。
- 测试侧同源字面量：`src/test/qa_CLFSystemComponents.cpp:117`。

★ **缺陷 3：测试自身绑定 Windows 编码语义**
- `src/test/qa_CLFWebFetch.cpp:124-128` 断言 `toUtf8(GBK 字节) == "中文"`，**无 `#ifdef` 保护**；而 POSIX 下 `toUtf8` 为恒等返回（`src/CLFTypes/CLFEncoding.cpp:35`）。

### 2.5 完全重复的实现（天然接缝）
- **exe 所在目录**：`src/CLFCore/CLFConfigLoader.cpp:139-153` vs `src/CLFCore/CLFPluginManager.cpp:87-100`（后者另缺 `PATH_MAX` 对照）。
- **动态库后缀 `.dll`**：`src/CLFCore/CLFPluginManager.cpp:233`（扫描过滤）与 `:436`（拼路径）。

### 2.6 从未编译且已知有硬伤的分支（保留但必须标注）
| 位置 | 硬伤 |
|------|------|
| `CLFCommandExec.cpp:193` | 使用 `SIGKILL` 但本文件仅包含 `<sys/wait.h>` `<unistd.h>`，无 `<signal.h>`/`<csignal>` |
| `CLFConfigLoader.cpp:147` / `CLFPluginManager.cpp:94` | 使用 `PATH_MAX` 但无 `<climits>`/`<limits.h>` 显式包含 |

## 三、设计原则（用户定调 + 项目宪法）

1. **零行为变更**：Windows 侧行为、输出、退出码逐字节不变。
2. **零运行时成本**：编译期收敛（宏 + inline），不引入间接调用。
3. **能力层不装策略**：平台层只提供「原语」，业务判断留在调用方。
4. **保留 + 加分支**（用户定调）：非 Windows 分支保留，缺失的补齐，**每个未验证分支必须显式标注**。
5. **单点收敛（第一期口径，2026-09-22 修订）**：第一期的目标形态是「把散落的 `#ifdef _WIN32` 集中在 1 个文件内」；**第二期该文件即成为真正的多平台接缝**（§十五）——所以第一期就要按"将来会真编译"的标准写分支，而不是写成永远编不过的占位。

## 四、平台层设计

### 4.1 落点与依赖
- **新增**：`src/CLFTypes/CLFPlatform.hpp` + `src/CLFTypes/CLFPlatform.cpp`
- **注册**：加入 `clf_types` target（`src/CMakeLists.txt:44-48` 源清单加一行）
- **理由（SDP/SAP）**：`clf_types` 是最底层、零项目依赖、很少变化的稳定组件；与既有 `CLFEncoding` / `CLFTextUtil` 同层同性质。
- **命名空间**：跟随 `CLFEncoding` 先例用 `CLF::CLFCore`（**不新开命名空间**）。
- **命名**：类名 `CLFPlatform`；函数小驼峰；全部 `static` 成员或匿名命名空间自由函数（二选一由 pro 按既有 `CLFEncoding` 风格定）。

### 4.2 接口清单（6 组，全部为原语）

| 组 | 接口签名（建议） | 收敛目标 |
|----|------------------|----------|
| 路径 | `static std::string executableDir();` | `CLFConfigLoader.cpp:139-153` + `CLFPluginManager.cpp:87-100` 合一 |
| 动态库 | `static const char* dynamicLibraryExtension();` | `CLFPluginManager.cpp:233, 436` |
| Shell | `static const char* nullDevice();` | `CLFSystemInfoProvider.cpp:82, 90, 100` |
| 控制台 | `static bool enableVirtualTerminal();`<br>`static bool consoleSize(int& w, int& h);`<br>`static bool setRawInputMode();`<br>`static bool initConsoleEncoding();`<br>`static bool consoleCursorPosition(int& x, int& y);` | `CLFAnsi.cpp:16-30 / 38-66`、`main.cpp:52-55`、`CLFRepl.cpp:243-257`、`CLFReplView.cpp:529-533` |
| 剪贴板 | `static std::string readClipboard();`<br>`static bool writeClipboard(const std::string&);` | `CLFClipboard.cpp` 整文件 |
| 临时文件 | `static std::string makeTempFilePath(const std::string& prefix);` | `CLFCommandExec.cpp:168-169` + `CLFRepl.cpp:139-143` |

**行为约定（必须写进头文件注释）**：
- `executableDir()` 返回 UTF-8 窄串；失败返回空串，由调用方回落 `fs::current_path()`。
- `consoleCursorPosition()` 返回**1 基**坐标或 false——基准口径见 §九 风险。
- `makeTempFilePath()` 返回**绝对路径**；非 Windows 侧读 `TMPDIR`、Windows 侧读 `TEMP`，均不带创建动作（是否创建由调用方决定）。

### 4.3 关键分寸：明确不下沉

| 不下沉项 | 原因 |
|----------|------|
| `CLFReplView::calibratePoint` 的**算法**（origin 1 基、JediTerm 补偿 4、`CLF_MOUSE_OFFSET_Y`） | 依赖 FTXUI 的 `LastFrameCursor`（帧状态），平台层不可见；平台层只提供「取控制台光标位置」原语 |
| `executableDir()` 之后的**策略** | CLFConfigLoader 向上找 `CMakeLists.txt`、PluginManager 拼 `plugins`——能力层不装策略 |
| `CLFEncoding` | 已是干净接缝；POSIX 恒等返回在语义上正确（字节流本即 UTF-8），**不改** |
| `CLFTerminal.cpp:7-11` 的 `windows.h` include | 经确认全文件未使用任何 Windows 符号（仅 include + `#undef min/max`）→ 属**死 include**，本批可顺手删除（零风险） |
| CMake 平台分支、`3rdparty` | 超出本设计范围 |

### 4.4 形态铁律
- header-only inline + 单一 cpp 内集中 `#ifdef`；
- **禁止**虚接口 / 抽象工厂 / pimpl；**CMake 选源文件**第一期不用（第二期重议，见 §十五）；
- 每个非 Windows 分支必须以统一标记注释，并**写清它依赖哪个平台 API / 缺什么头文件**：
  `// [未验证] 非 Windows 分支：Windows 构建不覆盖；依赖 <signal.h> 的 SIGKILL（E 类已知缺头）`
- **第二期要求**：这些分支要**真编译真验证**（§十五）——所以标记不是免责声明，而是**待办清单**（§十一 E 类已列 4 处编译风险）。

### 15.3 由矩阵直接推出的硬约束（第一期就要遵守）

1. **二进制兼容底线 = glibc 2.17**：在 Ubuntu 24.04 编出的产物**不能**直接跑到 CentOS 7（`GLIBC_2.3x` 符号缺失）。要么在老基线（CentOS 7 或等价容器）上构建，要么 devtoolset + 静态链接 `libstdc++`。
2. **C++17 需要新编译器**：CentOS 7 默认 GCC 4.8.5 编不过我们的代码（`std::filesystem`、`if constexpr` 等）→ 必须 SCL `devtoolset`（或 `llvm-toolset`）。
3. **插件 ABI 多一个 OS 维度**：已有"同一编译链与运行时库"约束（阶段 2 §3.5）；跨 OS 后还要加"**同 OS 同 glibc 基线**"——插件 DLL/SO 不可跨系统复用。
4. **CMake 版本前置**：本仓要求 `cmake_minimum_required(3.20)`，CentOS 7 自带远低于此 → 构建前置条件必须写清（自带 CMake 或从 kitware 源装）。
5. **脚本层**：`install.ps1` 等仍是 PowerShell（第一期冻结）；第二期需要 Linux 安装/升级/卸载链路（`sh` + 打包格式），届时另设计。
