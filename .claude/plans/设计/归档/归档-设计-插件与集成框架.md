## 一、两个世界（机制不同，不共用"能力契约"）

| | 内部插件世界 | 第三方集成世界 |
|---|---|---|
| 内容 | 自研模块 / 自研工具 | 外部系统（dsh / Claude Code / MCP server / 子代理…） |
| 机制 | **进程内插件**（native DLL 热拔插），主进程 = CLFCode | **进程间通信（IPC）**，CLFCode 是主进程，对外部进程说话 |
| 协议 | C 工厂 + 纯虚接口（内部 ABI，见分册） | **每目标各自适配，不强行统一**（用户决策：不同系统调用方式不同，强统不划算） |
| 契约 | 自研工具的既有契约（CLFToolSpec 等）直接用 | 每个适配插件负责把外部能力映射到模型可见面；映射方式适配自定 |

> v0.1 曾假设"一个能力契约跨 native/MCP/脚本 + declarative 脚本后端"，**已废弃**：
> 第三方一律走 IPC（即使脚本工具也以子进程形态），没有"进程内声明式脚本"这一形态。

## 二、全局三阶段路线图（用户拍板顺序）

```
阶段 1：功能梳理与拆分
  模块化梳理清楚 → 编译 → 运行 → 测试 → 功能无缺陷、正常使用
  出口标准：无 P0/P1 缺陷、拆分合理、全功能回归通过
  （当前代码审查文档 = 本阶段依据；执行中可能发现拆分不彻底 → 回到本阶段修正）

阶段 2：内部插件化
  2.1 先做【插件管理系统】（CLFPluginManager：发现/加载/生命周期/注册/路由）
  2.2 用 1-2 个模块插件化改造试点（成功后再铺开）
  2.3 试点成功后改造其余模块
  反向迭代：插件化过程中发现阶段 1 某些拆分不够/不细/不合理 → 回头修
  （技术细节见《代码审查-插件化演进规划.md》：DLL ABI、热拔插、试点）

阶段 3：第三方集成
  自研【第三方工具集成插件】，第一个目标 = **dsh**
  每外部系统一个适配插件（各自协议），先做目标协议调研
  安装模型：配置文件声明 + 未装提示 + load 命令加载
```

**阶段间不可跳**：阶段 1 修不稳就直接插件化会放大问题；阶段 2 不完成，阶段 3 的适配插件无处挂载。

## 三、阶段 1：功能梳理与拆分（先行，当前进行中）

- 输入：第一轮扫描报告（结构/SOLID/重复）+ 问题清单与重构方案（P0/P1/P2、批次 A/B/C）
- 内容：模块边界梳理清楚（**按未来插件边界来划**：自包含、对外统一接口、依赖单向向下、无循环）、修缺陷、编译运行测试、无缺陷正常使用
- 拆分蓝图（按未来插件归属分层）：
  ```
  basic（无业务：宏/UTF-8/时间/结果类型） → 能力（FileOps/CommandExec/Search/WebFetch）
  → core（agent 编排/会话/摘要/安全/todo） → 适配器（handler）→ UI（接口分界）
  ```
- 出口：P0/P1 清零、模块依赖图干净、功能回归全绿

## 四、阶段 2：内部插件化（细节见分册）

- 顺序（用户）：**先插件管理系统** → 1-2 模块试点 → 成功 → 铺开其余

  管理器 = 发现/依赖拓扑/生命周期/quiesce 后卸载/调用路由；进程内无真崩溃隔离（如实标注）
- 反向迭代通道：插件化暴露的阶段 1 拆分问题回流修正

## 五、阶段 3：第三方集成（IPC，dsh 试点）

### 5.1 形态

```
CLFCode 主进程
  └─ 第三方工具集成插件（自研，挂载在插件管理系统上）
       └─ 适配插件 × N（每外部系统一个）
            ├─ dsh 适配（试点）
            ├─ MCP server 适配（待定）
            ├─ Claude Code 适配（待定）
            └─ …（按需）
```

- 每个适配插件自己定义与该外部系统的调用方式/线协议/消息映射（**不设统一协议层**）
- 共享的只可能是"外部进程生命周期基础件"（spawn / 超时 / 输出限额 / 状态上报）——这是脚手架不是协议，不违背"不强统"

### 5.2 dsh 试点前置：协议调研（桌面调研，不占实现工时）

对 dsh 的对外接口做调研后再定适配方案：
- dsh 是否有可编程外部接口（HTTP API / 进程协议 / 服务端口）？形态与认证？
- dsh 的能力面（工具/服务/子代理）如何被外部程序调用？
- 消息模型：请求-响应 or 流式；事件订阅？

> 调研方式：可在 dsh 侧查 harness 源码/文档（现有 checkout），也可 web 查公开资料——先出调研小结，再定 dsh 适配插件设计。

### 5.3 安装与加载模型（用户决策）

- **配置文件声明**即可（不自动扫描目录安装）
- 管理器**不直接感知**用户机器上装没装目标 → 按需**提示**（如需安装给出指引）
- 用户装好后，**load 命令**加载进来（类似 `/plugin load dsh`）
