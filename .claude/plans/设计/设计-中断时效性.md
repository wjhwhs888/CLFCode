## 定稿摘要（pro 先读这一页）

**一句话根因**：`execute_command` 等慢操作执行期间**没有任何取消检查点**；而取消能力在 ABI 层就不存在（`CLFToolApi.hpp:13`「本 ABI 无取消通道」）。用户实测：56 秒全量测试期间按 ESC，取消要等命令跑完（§2.1 日志铁证）。

**需求（用户定调）**：**任何情况下 ESC/Ctrl+C 都要立即停**；中断要给模型**不误导**的反馈；中断的用量**照计不做减法**。

| 批次 | 内容 | 判定门 |
|------|------|--------|
| **A**（P0） | 取消通道（ABI）+ 命令可取消 + **立即强杀含进程树** + **协议闭合**（执行器内部实现 = 《设计-命令执行层》） | 实机：`node test_ai.js` 中途 ESC → **≤1 秒停 + 无 node 残留 + 中断后继续对话不 400**；qa：声明数 == 结果数 |
| **A2** | `web_fetch`(60s) / `search_content`(无上限) / 自动摘要入口 接入同一通道 | 三者中断均 ≤1 秒返回 |
| **B** | 中断可感知与周边修复：W6 状态行单写、B2 双击退出收敛、B3 Ctrl+C 收尾统一、B4 去 `clear()`、W-usage、quiesce 回归用例 | 实机：中断后状态不被刷掉；连按 ESC 不误退；中断用量计入 |
| **C** | HTTP 立即断：W1 世代号（待决中断不可抹）、W4 等首字节、W3 陈旧注释、W5 测试覆盖 | qa：abort 先于请求 / 请求中两时序；实机：等首字节期间 ESC ≤1 秒生效 |

**不可违反的纪律**：
1. **术语**：**取消**（一次调用）/ **停用·卸载**（插件生命周期）/ **中断**（ESC 总动作）——三者不混用（见文首 §术语）。
2. **文案不误导**：不把"取消"写成"拒绝"（`[Denied by user]` 是另一语义）；不把"结果未知"写成"失败"；**不以 user 消息形态注入**（走 tool 结果通道）。
3. **协议不变量**：任何时刻 `tool_calls` 声明数 == tool 结果数（I1/I2/I3，§11.7）。
4. **明确不改**：选区态 ESC 语义（B1）、待办面板行为（B10）、半截内容不入库、`chcp 65001 >nul &` 包装、管道捕获与编码语义。
5. 立即强杀的副作用（半写文件、半截测试产物）由"**结果未知**"文案承担。

**已知边界（不可修）**：第三方插件若不轮询 `isCancelled`，宿主**无法**强制取消（同步 ABI 固有限制）；流中途被打断时服务端尚未发 usage → 该次用量**无数据可计、不估算**。

## 术语（2026-09-22 用户定调，防歧义）

| 术语 | 含义 | 对应现状 |
|------|------|----------|
| **取消（cancel）** | 用户中止**一次正在执行的调用**（工具/请求） | **本设计要补的**（现状缺失） |
| **停用 / 卸载（disable / unload）** | 插件的生命周期状态切换（`/plugin unload`、`shutdown()`） | 已有 |
| **中断（interrupt）** | 用户按 ESC / Ctrl+C 触发的整体止损动作（= 取消当前回合中的一切在途工作） | 部分生效（见 §二） |

> 本设计中的"停止"一律指 **取消**；涉及插件生命周期时写"停用/卸载"。

## 一、现象（用户实测，三阶段）

| 阶段 | 用户观察 | 中断是否立刻生效 |
|------|----------|------------------|
| ① 流式回复输出阶段 | 按 ESC | ✅ 立刻停止 |
| ② 流式回复执行命令阶段（改代码、查文件等） | 按 ESC | ✅ 立刻中断（尤其改文件时） |
| ③ 命令执行中、模型未回复 | 按 ESC | ❌ **不立刻**；像"HTTP 请求在排队"，模型一出结果就中断成功 |

补充观察（复现期）：ESC 后状态行出现 `⏹ 中断中…`，**不到一秒被刷新掉**；再按仍出现、仍被刷掉；模型内容不显示（命令行还在）。

## 二、取证（铁证）

### 2.1 日志时间线（`doc/log/clf_agent.log`，2026-09-22 15:47 会话）

| 时刻 | 日志 | 说明 |
|------|------|------|
| 15:47:50 | `[Turn] start` → `[API] streaming request, iter=0` | 回合开始 |
| 15:47:52–15:48:03 | `iter=0…7` 每轮 1–2 秒交替（含 todo_write/list_directory/read_file/get_current_time/若干 execute_command） | **这些阶段 ESC 会立刻生效**（工具都很快） |
| **15:48:03** | `[ToolExec] executing: execute_command(chcp 65001 >nul && node test_ai.js > "%TEMP%\t11_a.t…)` | **第一轮全量测试开始** |
| **15:48:59** | `[ToolExec] execute_command done, ok=true, result=5460 chars` | **56 秒后才结束** |
| 15:48:59 | `[Submit] exit, tools=2` | 回合结束（**无** `[Turn] done` → 走中断路径） |
| 15:50:03 | `[Submit] entry, input=/exit` | 用户退出 |

**决定性事实**：`15:48:03 → 15:48:59` 的 56 秒里，日志中**没有任何 `[API] streaming request`**。
→ 这段时间**没有 HTTP 请求在途**。模型早在 15:48:03 就答复完（`iter=7`，`finish=tool_calls`），它在**等命令跑完**。
→ 用户所说"≈15 秒" = 命令的**残余运行时间**（命令 56 秒，ESC 大约在 15:48:44）。

### 2.2 批大小证据（解释用户看到的那行 `⎿ ⏹ 已中断`）
- `tools=2` 是**最后一批的工具个数**，不是回合累计：`CLFToolExecutor.cpp:726` 是 `m_stats.totalCalls = calls.size();`（**赋值**）。
- 该批 2 个工具中，日志只出现 1 条 `executing`（长命令）；第二个在**执行前**被中断检查拦下 → 打印 `  ⎿ ⏹ 已中断`（`CLFToolExecutor.cpp:417`）。
- 随后 `AgentLoop.cpp:366` 又打印 `⏹ 已中断`（`emitInterrupted()`，`CLFAgentLoop.cpp:796`）——**两处文案来源不同，用户同时看到两条**。

### 2.3 中断检查点全清单（代码实读）

| 位置 | 粒度 | 覆盖什么 |
|------|------|----------|
| `CLFHttpClient.cpp:102/121/129` | **每个 SSE 数据块** | 流式输出期间 |
| `CLFAgentLoop.cpp:160` | 每轮 API 请求**之前** | 请求间 |
| `CLFAgentLoop.cpp:188` | 每个 SSE 数据块（Agent 侧） | 数据到达后停止处理 |
| `CLFAgentLoop.cpp:349` | 工具批**执行前** | 批间 |
| `CLFAgentLoop.cpp:366` | 工具批**执行后** | 批间 |
| `CLFToolExecutor.cpp:416` | **每个工具开始前** | 工具间 |
| `CLFToolExecutor.cpp:547/577` | 工具拒绝分支 | 工具间 |
| **命令执行期间** | — | **❌ 无任何检查点** |

### 2.4 结论（根因判定）

> **根因：`execute_command` 执行期间没有任何中断检查点。**
> `CLFCommandExec::executeCommand()` 在自己的轮询循环里等待子进程（Windows `WaitForSingleObject(pi.hProcess, 50)` + `PeekNamedPipe`，`CLFCommandExec.cpp:102-129`；POSIX `waitpid(WNOHANG)` + 100ms，`:186-199`），**从不检查任何中断标志** → 子进程跑到自然结束或超时（上限**默认 600s**，已改为可配置——见 `设计-命令执行层` §10.2）。
> 中断只能在**工具开始前**（`CLFToolExecutor.cpp:416`）或**整批结束后**（`CLFAgentLoop.cpp:366`）被观察到，所以必须等**当前这个工具**结束。

**一个原因解释三个阶段**：中断响应时间 ∝ **当前工具/请求的检查点密度**。
- 阶段①：每块数据一个检查点 → 立刻；
- 阶段②：改文件/查文件的工具只要毫秒级 → 下一个检查点马上到 → 看起来立刻；
- 阶段③：命令跑 56 秒 → 期间零检查点 → 必须等它跑完。

### 2.5 被本次证据排除的假设（但仍登记为真缺陷）

用户"像 HTTP 请求排队"是**误判**（那 56 秒没有请求在排队）。因此下列 HTTP 层假设**不是本次现象的原因**，但仍是真缺陷，列入批次 C：

| 编号 | 缺陷 | 位置 | 状态 |
|------|------|------|------|
| W1 | `m_aborted` 无条件重置，待决中断会被下一次请求抹掉 | `CLFHttpClient.cpp:35` / `:78` | 真实，窗口窄，本次未命中 |
| W2 | 中断路径**零日志痕迹**（`emitInterrupted` 不写日志） | `CLFAgentLoop.cpp:792-799` | 真实（本次靠 ToolExec 日志破案） |
| W3 | 陈旧注释：写"libcurl 层检测到中断"（项目用 httplib） | `CLFAgentLoop.cpp:237` | 证据：该路径自换库后未复验 |
| W4 | "等首字节"窗口唯一依赖 socket shutdown | `CLFHttpClient.cpp:164-170` + httplib `stop()` | 真实，需超长 prefill 才撞到 |
| W5 | HTTP 中断路径**零测试覆盖**（`MockHttpClient::abort()` 空实现） | `qa_CLFAgentLoop.cpp:36` | 真实 |
| **W6** | **状态行双写**：UI 写"中断中…"，AgentLoop turnTimer 覆盖它 | `CLFInputHandler.cpp:392` vs turnTimer | **真实，用户实测可见** |

## 三、根因链（完整因果）

```
用户按 ESC
  → CLFInputHandler.cpp:371-394  terminal->interruptFromUi()
      → CLFAgentLoop.cpp:73-76    m_interrupted = true; httpClient->abort()
  → 此刻若「有工具正在执行」：
      · 没有任何代码读 m_interrupted（命令执行器无此概念）
      · 工具照常跑完（最长 = 配置上限，默认 600s）
  → 工具返回后：
      · CLFToolExecutor.cpp:416 拦下批内后续工具 → 打印 "  ⎿ ⏹ 已中断"
      · CLFAgentLoop.cpp:366     → emitInterrupted() → 打印 "⏹ 已中断" → return "[Interrupted]"
  ⇒ 用户感知："按了 ESC 没反应，等了好久才中断"
```

## 五、批次 A：命令中断（详细设计）

### A.1 取消通道（ABI 变更）

**现状**：`CLFToolApi.hpp:13` 明确写着「**本 ABI 无取消通道**」——这就是根因的契约根源。

**方案**：`CLFToolCallbacks`（`CLFToolApi.hpp:56-62`）**尾部追加**一个函数指针：

```cpp
// 取消查询（尾部新增）：返回 true = 宿主已请求取消本次调用。
// 实现侧应在可中断处轮询，命中即尽快中止并走 onError/onResult；可为 null
bool (*isCancelled)(void* ctx) = nullptr;
```

**ctx 语义升级（关键）**：现在 `ctx = &content`（`std::string*`，纯结果收集器，见 `CLFPluginTools.cpp:82-90`）。升级为**宿主内部调用上下文**：

```
宿主内部结构（CLFPluginTools.cpp 匿名命名空间）：
  struct CLFToolCallCtx { std::string* out; const std::atomic<bool>* interrupt; };
  onResult/onError → 取 ctx->out；isCancelled → 读 ctx->interrupt
```

- 插件侧义务**不变**：只负责把 `ctx` 原样回传给回调——**插件作者不需要理解 ctx 内容**，心智模型零变化。
- **ABI 版本**：结构体布局属契约变化 → **`CLF_PLUGIN_API_VERSION` +1**，同批重编所有插件（项目插件与宿主同一构建树，重编零成本；精确匹配闸门会把旧 DLL 明确拒绝，而不是静默错读）。**（定稿决策 D4：+1）**
- **为何不走"新增服务接口"路线**：取消状态是**每次调用局部**的，而 `CLFService` 是进程/插件级全局对象；用服务承载会让"当前调用"变成隐式全局态（违反 CCP/单一权威）。

### A.3 命令执行器改造（两平台 + 进程树）

> **职责切分（2026-09-22 消歧）**：执行器**内部实现**（进程创建 / 终止 / 杀树 / 输出限额 / 截断 / 错误归一化）的**唯一权威 = `设计-命令执行层.md`**（§七 Windows 要点 / §八 POSIX 要点 / §十一 步骤）。

**签名**（`CLFCommandExec.hpp:21-23`）：


**Windows 分支（`CLFCommandExec.cpp:44-163`）**：
1. `CreateProcessA` → **`CreateProcessW`** + `CREATE_SUSPENDED | CREATE_UNICODE_ENVIRONMENT | CREATE_NO_WINDOW`（**W 版与三个标志的理由见 `设计-命令执行层` §七 第 1 条**）；
2. 建 Job 并纳管（**杀进程树的关键**）：`CreateJobObjectW` → `SetInformationJobObject(JobObjectExtendedLimitInformation, JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE)` → `AssignProcessToJobObject(job, pi.hProcess)` → `ResumeThread(pi.hThread)`；
   - 目的：`cmd.exe /s /c` 会派生 `node.exe` 子树，`TerminateProcess(pi.hProcess)` **只杀 cmd.exe，node 变孤儿**。

   - Job 创建/纳管任一步失败 → **静默回退**到旧行为 + warn（不允许因此让命令执行失败）；
   - `CREATE_SUSPENDED` + 管道 + `CREATE_NO_WINDOW` 的组合需 pro 实测确认（MSVC）。
3. 轮询循环（现有 `WaitForSingleObject(pi.hProcess, 50)`，`:103`）**每轮先查 `isCancelled()`**：命中 → 杀树 helper → `m_interrupted = true` → break；
4. **超时路径同改**（`:125` 现为 `TerminateProcess(pi.hProcess, 1)`）→ 走同一个杀树 helper。**现有超时同样漏杀子树，属既有缺陷，一并修掉**；
5. 收尾 `CloseHandle(job)`（`KILL_ON_JOB_CLOSE` 兜底）。

**POSIX 分支（`:165-219`）**：
1. 子进程 `setsid()`（或 `setpgid(0,0)`）形成独立进程组；
2. 轮询（现有 `waitpid(WNOHANG)` + 100ms，`:186-199`）每轮查 `isCancelled()`；命中 → `kill(-pgid, SIGKILL)`（**负号 = 整组**）→ `m_interrupted = true`；
3. 超时路径（`:193` `kill(child, SIGKILL)`）同改为整组；
4. 补 `<signal.h>` 显式包含（既有 E 类缺陷：`SIGKILL` 无显式包含）；
5. 沿用 `[未验证]` 标注约定（见 `设计-平台层收敛.md` §4.4）。

**保持不变**：`chcp 65001 >nul & ` 包装（`:60`）、匿名管道捕获、cwd 传参、`CLFEncoding` 转换、`m_timedOut` 语义。

## 十一、中断协议闭合（P0，与批次 A 同批）

### 11.1 问题：中断必然产生"已声明未执行"的工具调用

模型一轮可以并行声明多个 `tool_calls`；中断发生在工具批中途时，**已声明的调用会有部分永远拿不到结果**。

**本仓实测证据**（`doc/contextHistory/2026-09-22_15-47-50_*.jsonl`，即用户本次复现）：

```
声明的 tool_call 数: 16
有结果回填的 tool 数: 15
悬空（已声明无结果）: 1 -> call_01_T4njWcaeMmum3yXAV7LO9475
```

### 11.2 为什么这是 P0（协议违规，不只是"模型不知道"）

OpenAI 兼容协议要求：**每个 `tool_calls` 条目都必须有配对的 tool 消息**。
dsh 源码把这句话写死在注释里：*"Close calls before their step: **providers reject dangling assistant calls**"*（`E:\deepseek-harness\packages\core\session\src\repair.ts:91`）。

→ **后果**：中断后若继续对话，下一次请求可能被 API 直接拒绝（400）→ 会话直接坏掉。
→ 触发条件恰恰就是本次复现的路径：工具批中途中断（`CLFAgentLoop.cpp:353` 已 `addAssistantToolCalls`，`:366` 中断返回，被跳过的调用无结果）。用户本次按 `/exit` 退出，所以没炸；**下次"中断后继续提问"就会撞上**。
→ 该风险需 pro **实测确认**（构造：中断 → 立刻发新消息，观察是否 400）。

### 11.3 参照实现（调研结论）

| 参照 | 做法 |
|------|------|
| **dsh（deepseek-harness）** | `interruptedTurnClosers()`（`packages/core/session/src/repair.ts:93-126`）：为每个 pending call **合成一条 `isError: true` 的 tool 结果**（id `interrupted-tool-result-<callId>-<seq>`），错误码区分 `ToolNotStartedError` / `ToolOutcomeUnknownError`，并附固定引导文案（见下）；随后补 `step/end`、`turn/end{reason:{kind:'interrupted'}}` |
| **Claude Code** | 向对话注入固定串 `[Request interrupted by user]` / `[Request interrupted by user for tool use]`（[issue #78915](https://github.com/anthropics/claude-code/issues/78915)）；同类问题在 CC 自身也存在未修（[#26802](https://github.com/anthropics/claude-code/issues/26802)、[#30118](https://github.com/anthropics/claude-code/issues/30118)、[#78151](https://github.com/anthropics/claude-code/issues/78151)）——说明这是行业共性难点，不是本仓独有 |

**dsh 的两段文案（直接可借鉴的中文版原型）**：

| 情形 | 引导语义 |
|------|----------|
| **已派发且已开始**（如被立即强杀的命令） | 结果**未知**；只读/幂等才可重试；可能有副作用时先核实外部状态或询问用户；**不要盲目重试** |
| **已派发未开始**（被批内检查跳过的工具） | 未执行；如仍需要请重新调用 |

> 第二段正好覆盖本设计"**立即强杀**"策略的副作用（半写文件、半截测试产物）——结果未知必须显式告知模型，否则它会以为命令"没跑过"而重跑。

**定稿文案（2026-09-22，pro 直接使用；前缀作为 qa 断言锚点）**

| 情形 | 文案 |
|------|------|
| **已派发且已开始**（被强杀/结果未落盘） | `[interrupted] 该工具调用因用户中断而终止，未获得可信结果；可能已产生部分副作用（例如文件写入或命令执行到一半）。请先核实外部实际状态；仅当操作是只读或幂等时才可直接重试，否则不要盲目重试。` |
| **已派发未开始**（被批内检查跳过） | `[interrupted] 该工具调用因用户中断而未执行，未产生任何副作用。如仍需要，请重新调用。` |

- `[interrupted]` 为**稳定前缀**（qa 断言用），**不得**改用 `[Denied by user]`（那是"用户否决操作"的另一语义，见 §11.9）。
- 两条文案均走 **tool 结果**通道（`success=false` + `interrupted=true`），不新增 user 消息。

### 11.4 方案（CLFCode 落地形态）

1. **补齐位置**：`CLFAgentLoop.cpp:366-369` 的中断返回**之前**，对所有"无结果的 call"补 `m_context.addToolResult(...)`。
2. **谁产出"未执行"结果**：推荐**在 `CLFToolExecutor::execute()` 内产出**——只有它知道跳过原因（批内中断检查 `:416`）。在返回的 `CLFToolResult` 上增加区分位（如 `m_skipped = true` + 原因枚举），AgentLoop 只负责落库。
   - 备选：AgentLoop 用 `parsed.m_toolCalls` 与 `results` 做差集——**不推荐**（丢失"跳过原因"，且差集逻辑分散）。
3. **结果形态**：沿用既有失败路径语义（`formatToolResult` 的 error 分支），`success=false`、`interrupted=true`，文本用 §11.3 两段之一。
4. **不要用 user 消息伪装**：形态应是**工具结果**（工具错误的既有处理路径模型本来就熟），不新增"用户消息"这种会污染对话语义的东西。
5. **会话日志**：沿用 jsonl 追加式保存（结果行照常落盘）——保证事后可判读（本次悬空是靠 jsonl 才发现的）。
6. **不变量（可测）**：**任何时刻，上下文中 `tool_calls` 声明数 == tool 结果数**。这条应写成 qa 断言。

### 11.7 修复方案：运行时闭合 + 加载期修复

1. **运行时**（§11.4）：`CLFAgentLoop.cpp:366` 中断返回**之前**补齐所有无结果的调用；`CLFToolExecutor` 产出"未执行"结果（它才知道跳过原因）。
2. **加载期（repair-on-load，必需）**：`CLFSessionManager::loadJsonl` 载入后做一次**幂等闭合**——扫描 `tool_calls` 声明与 tool 结果，对悬空项补合成结果。
   - **理由**：本次修完，**历史会话里已经存在的坏记录不会自动变好**（本仓至少 1 个已实测）。这与 dsh 的做法一致：dsh 在 resume 时补 `interruptedTurnClosers` 并**持久化**（见 `E:\deepseek-harness\packages\core\session\src\repair.ts` 与 `packages/core/agent-loop/src/index.ts:901-907`）。
3. **不变量（三条，写成 qa 断言）**：
   - **I1** 每条 `assistant.tool_calls[i].id` 有且仅有一条 tool 消息响应；
   - **I2** 不存在孤儿 tool 消息（无对应声明）；
   - **I3** tool 结果紧跟其声明之后（现有追加式天然满足，作为回归钉子）。
4. **可测**：qa 用例断言 I1/I2；另建议把本次用于破案的"会话体检"扫描（统计声明数/结果数/悬空 id）产品化为诊断能力（qa 用例或 `--doctor` 类命令）——**这类问题不体检就看不见**。

### 11.8 为什么是"闭合"而不是"回滚删除"（决定性理由）

回滚（删掉 assistant 的 tool_calls + 已执行的结果）看似更干净，但**危险**：

- **副作用已经发生**：被"立即强杀"的命令、已写入的文件、已改动的代码——**结果未知 ≠ 没发生**。删掉记录会让模型以为"什么都没做"，从而**重跑一遍**（重复副作用、浪费时间）。
- **闭合保留事实**：哪些工具执行成功（真实结果）、哪些未执行、哪些结果未知——模型据此才能做出正确决策（这正是 dsh 那段"不要盲目重试"文案的用意）。
- **实现更局部**：只追加、不删改历史，符合会话 jsonl 的追加式设计（回滚会破坏 append-only 语义）。

### 11.9 "不误导模型"文案纪律（用户关注点）

用户定调：**给反馈可以，但不能误导**。三条硬纪律：

1. **不得把"取消"写成"拒绝"**：项目已有 `[Denied by user]`（确认栏里用户否决，`CLFToolExecutor.cpp:544/574`）——它表达"用户不同意这个操作"；ESC 只是**止损**，不代表否定方案。两种语义混用会让模型误判用户意图。
2. **不得把"结果未知"写成"失败"**：`success=false` + `interrupted=true` + 明确"结果未知/未执行"，不要伪装成普通非零退出码失败。
3. **不得以 user 消息形态注入**：用**工具结果**通道（协议内、模型熟悉的失败路径）。Claude Code 用 `[Request interrupted by user…]` 文本串是其协议架构使然；本仓是 OpenAI 式 messages，正确落点是 tool 结果，而不是伪造一条用户发言。
4. 附带：**已流式输出但被丢弃的半截内容**——现状**不进上下文**（`:232-240` 早退早于入库），但用户**已经看到了**。dsh 的对照做法是保留"安全可见前缀"并打 `interrupted: true` 标记（`packages/core/agent-loop/src/assistant-stream.ts:121-123`）。**本项目定稿：不入库、不进上下文（D6，有意设计）**：中断没回答完的内容不可信；屏幕保留显示并由 `emitInterrupted()` 标注"⏹ 已中断"。

## 十三、边界问题清单（2026-09-22 头脑风暴，Ctrl+C 专项）

### 13.1 Ctrl+C vs ESC：入口不同、出口同源、**收尾不等价**

| 维度 | ESC | Ctrl+C |
|------|-----|--------|
| 入口条件 | **无条件**（选区态除外） | **仅 busy**（空闲：消费但无动作，`CLFInputHandler.cpp:355-367`） |
| 确认栏激活 | 同路 `cancelWithInterrupt`（`:117-135`） | 同 |
| **选区激活** | 清选区、**不中断**（`:155-158`） | **被吞**（`:228` "拖选期间其他事件消费"）→ **不中断** |
| 传播出口 | `terminal->interruptFromUi()` | `terminal->interruptFromUi()` ← **同一个出口** |
| **UI 收尾** | `m_justInterrupted` + 输入框清/恢复 + `m_escCleanupFrames=3` + 状态"⏹ 中断中…" + PostEvent（`:386-393`） | **无任何收尾**（`:362-364` 只发信号） |
| 空闲语义 | 500ms 内两次 → `/exit` | 无动作（2026-09-20 防误触定案） |

**结论**：从 `interruptFromUi()` 往后**完全同一条路**；但**入口条件与 UI 收尾都不同**——所以"效果一致"只在传播层成立。用户"Ctrl+C 好像没启用"的印象来源：空闲时它什么都不做、且没有任何反馈。

### 13.4 补充取证（本轮新增）

**B2｜"空闲"的精确定义（回答用户提问）**

- `asyncSubmit.busy()` = `CLFAsyncSubmit::m_submitting`（atomic bool）：`launch()` 置 true（`CLFAsyncSubmit.cpp:14`），worker 线程**末尾**置 false（`:25`）——即**在 `repl.submit(text)` 整体返回之后**，含 `runTurn` + 全部收尾（`onTurnFinished` / `appendTurnLine()`（jsonl 落盘）/ `setStatus("")` / 换行输出）。
- 因此"空闲"= **提交线程已跑完整个 submit（含历史落盘）**；**不是**"工具结束"，也**不是**"HTTP 请求结束"。
- 它**不覆盖**：UI 渲染队列、命令分发（命令走 UI 线程同步，不 launch）、粘贴 PENDING 态、确认栏等待（等待期间 worker 仍 busy ✔）。
- 时间线：中断 → `runTurn` 提前返回 → submit 收尾（本地 jsonl 追加，通常几 ms）→ 置 false。**总计通常 < 50ms**，远小于 500ms 窗口。
- ⇒ "两次都是空闲 ESC 才退出"**消不掉歧义**：第一次中断后约 50ms 就"空闲"了，第二次 ESC 照样命中退出分支。
- **可选修法**：**(a)** 中断那次 ESC 不参与双击计时（不写 `m_lastEscTime`——中断键与退出键语义分离）；**(b)** 中断后设冷却期（如 800ms 内不判退出）；**(c)** 双击退出要求两次均为空闲态 ESC。
- **定稿结论（2026-09-22）**：采用 **(a) + (b)** —— 连按 ESC 永不误退；空闲连按两次仍能正常退出（冷却只作用于中断后的 800ms 窗口）。

**B4｜根因（对应"实现漏掉了"）**

- **设计意图（代码自带守卫）**：`CLFReplView.cpp:128-132` —— `if (m_needRestoreInput) { if (inputText.empty()) inputText = m_lastSubmittedInput; ... }`，即**只在输入框为空时**才回填上次提交内容。
- **实际行为**：`CLFInputHandler.cpp:387-390` 中断时**无条件** `inputText.clear()` 再置 `m_needRestoreInput` → 渲染层守卫恒成立 → **正在输入的内容被覆盖**。
- ⇒ 修法：去掉无条件 `clear()`（或在输入框非空时不置位），渲染层守卫自然生效。**性质是缺陷，不是产品决策** → B4 由"待决策"降级为"批次 B 缺陷修复"。

**B11｜核实结论：当前无优雅退出通道**

- `src/` 全量 grep：`CTRL_BREAK` / `GenerateConsoleCtrlEvent` / `taskkill` / `SetConsoleCtrlHandler` / `CREATE_NEW_PROCESS_GROUP` / `WM_CLOSE` / `SIGTERM` / `graceful` → **零命中**。
- 唯一终止路径是超时强杀 `TerminateProcess(pi.hProcess, 1)`（`CLFCommandExec.cpp:125`）——既不杀子树，也无优雅协商。
- 用户记忆中的"优雅退出兜底"应为别处（如 `install.ps1` 的占用探测/改名后删、测试临时目录 `RemoveWithRetry`），**不在子进程终止路径上**。
- 若将来要做"宽限期"：Windows 需 `CREATE_NEW_PROCESS_GROUP` + `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT, pid)`（当前创建标志中没有）。本次已选"**立即强杀**"，故仅记录。

**B12｜现状已符合期望（结案）**

- 粘贴合并器**没有弹窗**：它是"静默窗自动提交"状态机（`CLFPasteCoalescer`）。
- ESC 属"其他事件"→ 先走 `onOtherEvent`（`CLFInputHandler.cpp:284-286`）→ `PendingSubmit` 态下 `cancelPendingLocked()` + 回 `Idle` + **PassThrough** → 随后继续走到 ESC 分支 → **既取消待提交、也触发中断**；输入框文本保留（`m_pendingText` 未清、状态回 Idle）。
- ⇒ 用户期望（ESC 可取消、粘贴不该被误提交）**现状已满足**，无需改动。

**工作项 W-usage（批次 B）**：中断路径也要累计 usage

- **现状**：累计点在 `CLFAgentLoop.cpp:310-321`，**位于中断早退之后**（流式 `:232-240`、同步 `:280-287`）→ 中断时**丢弃已到达的** usage 与缓存命中数据。

**会话上下文体检脚本（可复用为回归检查；本次破案用的就是它）**：

```powershell
# 悬空 tool_call 检测：任何时刻"声明数 == 结果数"都应成立
$files = Get-ChildItem doc\contextHistory\*.jsonl
foreach ($f in $files) {
  $lines = [System.IO.File]::ReadAllLines($f.FullName, [System.Text.Encoding]::UTF8)
  for ($i=0; $i -lt $lines.Count; $i++) {
    try { $rec = $lines[$i] | ConvertFrom-Json } catch { continue }
    if (-not $rec.messages) { continue }
    $declared=@(); $answered=@()
    foreach ($m in $rec.messages) {
      if ($m.role -eq 'assistant' -and $m.tool_calls) { foreach ($tc in $m.tool_calls) { $declared += $tc.id } }
      if ($m.role -eq 'tool' -and $m.tool_call_id) { $answered += $m.tool_call_id }
    }
    $dang = @($declared | Where-Object { $answered -notcontains $_ })
    if ($dang.Count -gt 0) { "$($f.Name) 行$($i+1): 声明=$($declared.Count) 结果=$($answered.Count) 悬空=$($dang.Count)" }
  }
}
```
