## 二、CLFTool 扩展（并发安全声明）

### 2.1 字段与语义

```cpp
// CLFTypes.hpp CLFTool 增：
//   并发安全判定（nullptr = 独占，fail-closed 默认）：
//     接收工具参数 JSON 原文；返回严格 true 才允许并行
//     约束（dsh §16.2）：判定内不要抛异常表达"不安全"——直接返回 false
std::function<bool(const std::string& argsJson)> m_isConcurrencySafe;
```

- 默认 nullptr → exclusive（**所有现工具初始全部独占——零行为变化，声明一个放开一个**）
- 首批声明（对齐 dsh §11 分布）：list_directory / read_file / search_content / web_fetch / get_current_time / echo → `[](const std::string&){ return true; }`；execute_command → 逐参数判定（命令含写特征 → false——复用 CLFDangerousCommandDetector 判定结果的反向）；write_file / edit_file / todo_write / compress_context → 保持未声明（独占）
- **工具描述零改动**（判定函数不进 schema——现 m_description/m_parametersSchema 均不含并发字段，加字段时纪律保持）

### 2.2 分类函数

```cpp
// 调度分类（对齐 dsh executionMode）：
//   tool.m_isConcurrencySafe 为空          → Exclusive
//   调用返回非严格 true（含抛异常，catch 吞）→ Exclusive
//   严格 true                              → Parallel
enum class ToolExecMode { Parallel, Exclusive };
ToolExecMode classifyMode(const CLFTool& tool, const std::string& argsJson);
```

## 三、调度器设计（CLFCore 新增 CLFToolScheduler）

### 3.1 定位与边界

- 新文件：`src/CLFCore/CLFToolScheduler.hpp/.cpp`——**只做调度**（分组/并发/归序），工具执行体复用现有 handler 调用逻辑（从 CLFToolExecutor::execute 提取）
- CLFToolExecutor 瘦身为：参数解析 + 单工具执行 + 结果格式化（现 execute 循环拆出）；调度器持有执行器引用
- 事件发射：ToolStarted（prepare 通过、dispatch 前）/ ToolFinished（finalize 后）——经 AgentLoop 注入的 bus

### 3.2 主循环（分组 + 屏障，对齐 dsh tool-calls.ts:85-103）

```cpp
struct SchedulerResult {
    std::vector<CLFToolResult> m_results;   // 模型序
    bool m_concluded{false};                // A5
    bool m_aborted{false};                  // 中断
};

SchedulerResult schedule(const std::vector<CLFToolCall>& calls);

// 伪代码：
//   next = 0; while (next < calls.size()):
//     mode = classifyMode(calls[next])
//     group = mode==Parallel ? 剩余全部（惰性重分类收敛实际边界） : [calls[next]]
//     outcome = runGroup(group, mode)          // 见 3.3
//     next += outcome.consumed; concluded ||= outcome.concluded
//     if (outcome.aborted):
//         appendNotExecutedResults(calls, next, results)   // 既有协议闭合
//         return {results, concluded, aborted}
//   return {results, concluded}
```

### 3.3 runGroup（四阶段 + 提交游标 + 滚动池）

```cpp
// 组内状态（对齐 dsh §4.2）：
//   slots[i]：第 i 个调用的完成结果（std::optional<CLFToolResult> + 状态）
//   nextToStart / committed（连续前缀游标）/ inFlight（并发在途表）
//   std::mutex m; std::condition_variable cv;

// fillPool：while (!aborted && nextToStart < group.size() && inFlight < maxParallel):
//   if (nextToStart>0 && mode==Parallel && classifyMode(next) != Parallel) break  // 惰性重分类
//   startCall(nextToStart++)

// startCall(i)：// 顺序 await（串行闸门）：
//   ① 中断检查（aborted → 停）
//   ② emit ToolStarted（callId）
//   ③ prepare：工具查找 + 参数解析 + **confirm（阻塞，总线请求-响应）** + 安全策略检查
//      ——确认串行化：prepare 逐个串行，弹确认时后续调用不启动（安全优先，用户定调）
//      ——prepare 拒绝/失败 → slots[i] 落合成失败结果（不 dispatch），照常走提交
//   ④ dispatch：std::async 启动 handler 调用（唯一并发段；inFlight 登记）
//      ——完成回调：slots[i] 落结果 → cv 通知提交游标

// commitReady：while (committed < group.size() && slots[committed] 已落):
//   ① finalize：结果格式化（formatToolResult/截断）+ 统计累计（锁保护）
//   ② emit ToolFinished（callId——完成可乱序，发射即此时）
//   ③ results.push_back（模型序）→ concluded 判定
//   ④ committed++

// 收敛：fillPool → while (inFlight 非空) { 等 cv；谁 settle 谁出 inFlight → commitReady → fillPool }
```

### 3.4 线程与同步（C++ 实现定案）

- dispatch 并发 = `std::async(std::launch::async, handler)`（受控并发上限保证线程数 ≤ maxParallel，无需线程池——单步调用量级小）
- 提交游标 = mutex + condition_variable（fillPool/commitReady 在调度线程执行；dispatch 完成回调只落 slots + notify）
- **共享状态串行化清单**（并发下必须锁/原子）：m_lastToolStats 累计（提交游标内串行执行 → 天然安全 ✓）；todo_write 回调 AgentLoop（setTodos/markTodosDirty——**加锁**：AgentLoop todo 状态 mutex，或调度器内把 todo_write 归类独占+提交内执行——设计评审定，倾向 todo_write 保持独占即规避）；m_output 相关（分册 2 后为事件发射——emit 本身总线安全）
- 确认：prepare 串行 = 天然互斥（用户关心点 ✓）

### 3.5 取消语义（沿用 + 补全）

- 中断标志检查点：fillPool 启动前 + prepare 内 + dispatch 完成后提交前
- 已启动 dispatch 的取消：handler 内检查（CLFProcessRunner Job Object 杀树既有）+ 结果照常提交（排空）
- 未启动：appendNotExecutedResults 补合成结果（既有机制，语义与 dsh appendSkippedToolCall 同构）
- 中断后独占屏障不再执行（对齐 dsh §7.2 测试 :590）

### 3.6 失败静默

- 首个失败：停止新派发 → 等 inFlight 排空（照常提交）→ 以首个失败上报（返回 error 语义——AgentLoop 层处理）
- dispatch 异常：slots 落异常结果（不 throw 穿线程边界）——schedulerFailure 只记首个

### 8.2 实施期定案与偏差

1. **拆分落地**（§3.1）：prepare = 查找/统计计数/策略/危险判定/POST 升级/Write 预览渲染+确认+TOCTOU/showProgress（UI 输出全在串行闸门）；run = handler try/catch（零 UI/事件/统计，日志留互斥安全）；finalize = formatToolResult + ✓/✗ 行 + 统计/detailLines + ToolFinished（提交游标内串行）。**统计计数留在 prepare**（串行闸门天然安全 + 与现状"查找成功后计数"逐字一致——blocked/denied 计入的现状语义保持）；**ToolFinished 统一在 finalize 发射**（含 fallback——模型序，E2 钉死）。
2. **std::async → std::thread**（§3.4 偏差，取证见 8.3）：语义等价（受控上限保证线程数 ≤ maxParallel）且无 std::async future 析构阻塞怪癖；收敛后统一 join（inFlight==0 保证不阻塞）。
3. **cap=1 同步执行**（fillPool 内）：串行语义等价 + 免线程开销；qa 静态期套件（qa_CLFToolExecutor 串行等价回归）由此无 dispatch 线程。
4. **[skipped] 文案**（§3.6 未定，实施定义）："该工具调用因前序工具执行失败而未执行"——与 [interrupted]（用户行为）区分，均 qa 锚点。
5. **失败静默语义确认**（§3.6）：全局生效（含串行 cap=1——工具失败后后续不再执行、补 [skipped] 合成结果回传模型）。**串行行为变化**：现状"失败继续下一个" → "失败即停"（dsh 对齐，用户拍板设计定案）。Fallback（denied/blocked/not_found）不触发静默（非 handler 失败，后续照常——现状语义）。执行器 execute 壳 → scheduler 后 qa 无"失败后继续"用例，串行等价回归全绿。
6. **PreparedCall 零裸指针**：toolIndex（m_tools 下标）+ Write 预览标量摘要（WritePreview 结构保持 cpp 内部——Write 独占组语义保证无并发覆盖，注释钉不变量）。
7. **RefreshGuard 语义收敛**：T3 刷新移 finalize（每调用一次含 fallback——T12 断言保持）；中断路径未启动调用少一次 refresh（Interrupted 事件触发 UI 刷新兜底，记录偏差）。

### 8.3 实抓缺陷（取证闭环）

- **qa 全组偶发挂死（本批最大实抓）**：ctest 中 qa_CLFToolExecutor/qa_CLFToolScheduler 挂死零输出。复现矩阵（普通 main / 全局构造器静态期 / boost::ut 静态期 × 调度器串行/并发）逐层打点定位：**动态初始化期（boost::ut 静态期执行惯例）主线程与 dispatch 线程并发触发 CRT 设施初始化（logger 单例/time/string）→ 非确定性死锁**——与 std::async/std::thread 选择无关（两者同挂）；main 期 30 轮并发零复现。定案：① qa_CLFToolScheduler 套件改 main 期执行（轻量断言 QA_EXPECT，环境约束钉头注释）② cap=1 同步执行（qa_CLFToolExecutor 静态期套件免线程）③ 生产路径（main 后调度）不受影响。
- **G1/R1 门闩缺陷**（初版）："到达计数"门闩在串行 bug 下会因超时兜底顺序到达而误通过——改"重叠窗口"门闩（第二到达者观察到同时在等才放行；串行 bug → overlapped 恒 false）。
- **G4 注册表引用缺陷**（初版）：handler 捕获栈上 t3 而非 vector 元素——findTool 查注册表，改栈对象无效。修：改 tools[2]。
- **BatchProgressGuard 聚合括号初始化**：C++17 聚合不支持括号构造 → 加显式构造函数。
- **既有 flaky 观察**：qa_CLFEventBus 并行全量跑偶发失败（两次，单独重跑均过）——B3 时序用例负载敏感，与本批无关，待单独排查。

### 8.5 第三批实施记录（AgentLoop 接入 + 首批声明，2026-10-14）

1. **AgentLoop 切轨**：executeToolCalls 改用 CLFToolScheduler（注入 m_config.m_maxParallelToolCalls）——未声明工具 = 独占 = 串行现行为（qa_CLFAgentLoop 既有用例全绿 = 串行等价实证）。
2. **首批声明落地**（§2.1 清单）：宿主侧打标（插件 ABI 元数据不带并发语义——§2.3 不泄漏）——CLFPluginTools 装配处 concurrencyDeclaration：read_file/list_directory/search_content/web_fetch → 恒 true；execute_command → 逐参数（CLFDangerousCommandDetector 静态判定反向：危险 → 独占、普通 → 并行、坏 JSON → 独占 fail-closed）；CLFBuiltinTools 注册处：get_current_time/echo → 恒 true；write/edit/todo/compress 保持未声明（独占）。
3. **m_firstFailure 最小落地**：AgentLoop 记 warn 日志（结果链已完整回填——失败 + [skipped] 合成，模型自行决定后续）；回合提前终止等更强语义待用户实机感受拍板（偏差记录）。
4. **实抓缺陷（fail-fast 修根）**：F1/F2 并行负载失败取证——失败信号只在提交游标产生，队首慢时已 settle 的失败不能及时停止补位（违反 dsh §8"首个失败停止新派发"）。修根：ok 判定前移到 run（formatToolResult 纯函数并发安全，RunOutcome 带 ok/resultText/lines/chars，finalize 复用不再重判）→ Slot.ok 原子（写序 ok → finished）→ fillPool 头扫 anySettledFailure。用例时序固化：F1 t2 变慢保证 t1 先 settle（dsh 语义"失败前已派发的不撤销"——注释钉死）。
5. **qa 增量**：qa_CLFPluginFileOps G1 装配声明断言（读类并行/写类独占）+ qa_CLFPluginDomains D9（execute_command 逐参数三态 + search/web 恒并行；CMake 补链 clf_tools）。
6. **验证**：ctest 45/45 六连绿（B3 断言竞态同批修根：drainAll"消费到空"语义下断言改为总消费数 = 2）+ --version 冒烟。**实机并行观察 = 第四批**（用户验收点：模型一次多工具响应时并行执行 + 日志时间戳交错 + 结果顺序 + 确认串行弹窗）。

### 8.6 第四批衔接（实机并行观察）

- 用户实机：多工具回合观察并行（日志时间戳交错实证）+ 顺序执行（cap=1）逐字一致 + 中断/取消/失败路径无残留（§六 验收标准）
- 观察项：失败静默串行行为变化（失败即停）实机感受——若用户倾向"失败继续"，调度器改一行
- m_firstFailure 更强语义（回合终止等）待用户拍板
