## 二、目标架构（内部插件世界，2026-09-03 论证修订）

```
main（极薄入口）
  ├─ CLFPluginManager（外部插件管理器 —— 唯一编排者）
  │    ├─ 发现：扫描 plugins/*.dll
  │    ├─ 元数据 → 依赖图 → 拓扑加载
  │    ├─ 生命周期：加载/启用/停用/卸载/热替换
  │    ├─ 调用路由：一切跨插件调用唯一入口
  │    └─ 配置注入：各插件自己的配置段
  │
  ├─ UI 内建（宿主侧，不插件化）—— 主循环/渲染/输入，即 CLFCode 本身
  └─ core 内建（进程内对象，不插件化）—— AgentLoop 编排 / 会话 / 安全 / todo
       └─ 经 manager.getService 调能力插件（接口化，见 §3.1）

插件 DLL（自治：自己管自己、自己给自己兜底）
  ├─ tools.fileops.dll     FileOps + Diff 能力 + read/write/edit/list 工具（试点）
  ├─ tools.command.dll     CommandExec + execute_command
  ├─ tools.search.dll      SearchContent + search_content
  ├─ tools.web.dll         WebFetch + web_fetch
  └─ tools.misc.dll        get_current_time / echo（零依赖小工具，或并入 core 内建工具组）
```

> **论证定案（2026-09-03，取代原图）**：原图把 basic/core/适配器/UI 全部列为 DLL 插件，经逐层论证**收缩**：
> - **basic 不迁**：header-only 静态共享头（宏/inline 编 DLL 反而亏——每 DLL 各自编译一份 inline 代码零收益，见 §七定案①）
> - **core 不迁**：core 子插件化（会话/摘要/todo 迁 DLL）要求 CLFContext（vector\<CLFMessage\> 含 STL）跨边界传递——序列化成本高；热替换会话状态机的收益为零。C2 拆出的对象（CLFTodoStore/CLFSessionFileCtx）保持进程内（阶段 1 成果仍被消费：拆分本身就是插件化收益的一半）。见 §七定案②
> - **UI 不迁**：UI 是插件宿主的宿主侧（main 极薄后 UI 就是 main 的组成）；"UI 插件"唯一场景 = 可替换 UI 实现，非本项目目标。见 §七定案③
> - **适配器（handler）随工具域走**：handler 与能力同域打包（一个 DLL = 一个能力域 + 其工具定义与 handler），不再单列"适配器插件"层。见 §七定案④
> - **插件化范围定案**：能力层 + 工具层（9 个工具随域迁出）；core 内建 2 个工具（todo_write/compress_context，自引用见 §3.6）

## 三、技术设计（DLL 热拔插，Windows/MSVC）

### 3.1 ABI 边界：C 工厂符号 + 纯虚接口

```cpp
// 每个插件 DLL 只导出两个 C 符号（唯一导出面）
extern "C" __declspec(dllexport)
CLFPlugin* CLFPluginCreate(const CLFHostApi* host);
extern "C" __declspec(dllexport)
void       CLFPluginDestroy(CLFPlugin* plugin);
```

- **跨边界禁传 STL/异常**：字符串 `const char*` + 宿主分配回调；复杂数据 POD 或宿主 API 序列化
- **接口版本化**：CLFPlugin_v1 / CLFHostApi_v1——不兼容升级 = 新版本号，老 DLL 不砸
- **内存归属**：谁分配谁释放；跨边界走宿主 alloc/free（统一 /MD 保证 CRT 堆一致）
- 插件内部自由用 STL，仅边界转换

```cpp
class CLFPlugin {                       // 自描述：管理器加载后先读元数据建依赖图
public:
    virtual const char* name() const = 0;      // 唯一 ID，如 "tools.fileops"
    virtual const char* version() const = 0;
    virtual const char** requires() const = 0; // 依赖插件 ID（可空）
    virtual const char** provides() const = 0; // 提供服务名（可空）
    virtual bool init() = 0;                   // 自治初始化（失败 → 管理器标记禁用，其余不受影响）
    virtual void shutdown() = 0;               // 自治清理
    // + 领域能力接口（如工具提供者：listTools/findTool/callTool）
};

class CLFHostApi {                      // 管理器给插件的注入面
public:
    virtual void log(Level, const char*) = 0;
    virtual const char* config(const char* pluginId, const char* key) = 0;  // 本插件配置段
    virtual CLFService* getService(const char* pluginId, const char* service) = 0; // 唯一拿依赖通道
    virtual void* alloc(size_t); virtual void free(void*);
};
```

> **论证定案（2026-09-03 深化）——领域能力接口与跨边界数据传递**：

**① 跨边界数据传递 = 回调推送模式**（关键定案）。现状取证：ToolExecutor 的 `prepareWritePreview` 直接消费 `CLFFileSnapshot{std::string content}` 与 `vector<CLFDiffLine>`（含 STL）——跨边界禁传 STL 后，大对象传递只有两条路：
- 宿主分配回调（`alloc` 序列化整块传递）——一次拷贝 + 归属清晰，适合大块内容（文件内容）
- **回调推送**（宿主传结果回调，插件逐行/逐块推）——零额外拷贝，适合 diff 行流、搜索结果流
**定案：优先回调推送；整块传递仅用于有明确所有权语义的小块（路径、错误文本）。** 试点时 FileOps 域接口按此设计。

**② 能力域接口草案（试点前由 pro 细化签名，模式如下）**：
```cpp
// 宿主侧回调集合（POD 函数指针 struct，由 core 提供，经 call 参数传入）
struct CLFFileCallbacks {
    void (*onError)(void* ctx, const char* msg);              // 错误文本
    void (*onDiffLine)(void* ctx, int op, int oldLine, int newLine, const char* text); // diff 逐行推
    void (*onContent)(void* ctx, const char* data, size_t len); // 文件内容整块
};

class ICLFFileService {  // getService("tools.fileops", "file") 返回
public:
    virtual bool readFile(const char* path, void* ctx, const CLFFileCallbacks* cb) = 0;
    virtual bool previewEdit(const char* path, const char* oldStr, const char* newStr,
                             void* ctx, const CLFFileCallbacks* cb) = 0;
    // writeFile/editFile/diff 同模式；错误统一走 onError（跨边界异常零逸出）
};
```

**③ 工具插件域接口（handler 随域走）**：
```cpp
// POD 工具元数据（跨边界安全，与进程内 CLFTool 同构但无 std::function）
struct CLFToolMetaPOD {
    const char* name; const char* description; const char* parametersSchema;
    int risk;            // CLFToolRisk 枚举值
    int flags;           // 能力标签位集（阶段 1 B1 的 m_isSearch/m_isRead 映射至此）
    int concludesTurn;   // A5 先例
};
class ICLFToolProvider {
    virtual int toolCount() = 0;
    virtual const CLFToolMetaPOD* toolMeta(int index) = 0;
    // 调用：argsJson 进；结果经回调出（tool result JSON 由宿主侧收）
    virtual bool callTool(const char* name, const char* argsJson,
                          void* ctx, const CLFToolCallbacks* cb) = 0;
};
```
管理器收集元数据 → 进程内装配 `CLFTool`（handler 绑定为 callTool 路由）→ AgentLoop 注册表。**阶段 1 B1 的标签加在 CLFTool 上与此兼容：跨边界以 flags 位集表达。**

**④ 版本查询**：`CLFHostApi::apiVersion()` 返回宿主 API 版本号；插件 `CLFPlugin::compatHostVersion()` 声明兼容范围——不匹配 → 管理器拒绝加载 + 提示重建。

- 插件拿依赖**只能走 host->getService** → 管理器路由 → "调用全部由外部插件管理器管"
- 服务不可用（依赖停用/加载失败）→ 返回 null → **调用方自兜底**（降级/报错，不崩）

### 3.2 管理器职责（CLFPluginManager）

| 职责 | 说明 |
|---|---|
| 发现 | 扫描 plugins/ 目录 DLL |
| 依赖图 | 轻量读 name/requires/provides → 拓扑排序 → 检出缺失/环 |
| 加载 | 拓扑序 LoadLibrary + 工厂 + init() |
| 启用/停用 | 停用 = quiesce（无在途调用）→ 通知依赖方 → shutdown → FreeLibrary |
| 调用路由 | 服务注册表 (pluginId, service) → 实例；find/list 供模型适配与 UI |
| 配置注入 | 各插件读自己配置段（独立文件 config/plugins/<name>.toml） |
| 热替换 | 停用旧 → 加载新 → 路由切新实例 |
| 隔离兜底 | 单插件 init 失败/异常 → 仅该插件不可用，管理器与其余不受影响 |

**局限如实说明**：进程内 DLL 无真崩溃隔离（插件段错误 = 进程挂）；真隔离 = 进程级，列为后续选项，不阻塞当前设计。

### 3.3 "热"的语义（CLI 务实定义）

- 启动发现 + `/plugin` 管理命令（list/load/unload/reload）
- 卸载/替换仅 quiesce 后执行（无在途调用；agent 空闲/回合边界）
- 对话中禁停 → 管理器返回明确错误 → 模型走已有失败自兜底路径

### 3.4 配置与数据归属（自治具体化）

- 每插件自己的配置段（独立文件 config/plugins/<name>.toml）
- 每插件自己的状态/数据：不写全局单例；路径经 host API 获取
- 兜底数据面：缺配置/数据源时用内置默认（推广 TipsBar hardcoded fallback 模式）

### 3.5 构建/部署约束（MSVC，写入工程约定）

- 统一编译链：MSVC + 统一运行时（/MD）+ 统一平台工具集
- 每插件独立 CMake target（add_library(... SHARED)），只导出工厂 C 符号
- 接口头（CLFPlugin/CLFHostApi/POD）= 唯一跨 DLL 共享头，独立小目标或 header-only，禁依赖其他头

### 3.6 调用链路与内置工具 fate（2026-09-03 论证定案，关键空白打通）

**现状取证（阶段 1 评审）**：ToolExecutor（core）**直接 include CLFTools/CLFDiff.hpp + CLFFileOps.hpp 静态调用**——prepareWritePreview 直调 readFileWithSnapshot/previewEdit/computeDiff（ToolExecutor.cpp:121-169）。这是 core → 能力实现的硬依赖，试点必须切断。

**调用链目标态**：
```
模型 → AgentLoop → ToolExecutor
  ├─ 写工具 diff 预览：经 manager.getService("tools.fileops", "file") → ICLFFileService
  │   （能力调用，回调推送模式，见 §3.1②）
  ├─ 插件工具执行：经工具注册表路由 → ICLFToolProvider::callTool
  │   （handler 在 DLL 内，结果 JSON 回调回 core，走既有 formatToolResult）
  └─ 兜底：getService 返回 null（插件停用/加载失败）→ 明确错误回传模型
      （复用现有 "Tool not found" / 失败路径，模型走已有自兜底，不崩）
```

**内置工具 fate 定案（§七⑤）**：
- **迁 DLL（9 个）**：read_file / write_file / edit_file / list_directory（→ tools.fileops）、execute_command（→ tools.command）、search_content（→ tools.search）、web_fetch（→ tools.web）、get_current_time / echo（→ tools.misc）
- **留 core 静态注册（2 个）**：**todo_write / compress_context**——取证：二者 handler **捕获 CLFAgentLoop 引用**（BuiltinTools:566/581，自引用约束注释）且直接操 core 内部状态（setTodos/markTodosDirty/appendTodoSnapshotNow/setTodoPanelDone/compressContextNow）。迁 DLL 必须把 core 内部服务暴露给插件（host→getService("core.todos")），耦合反向、收益为零。**定案：core 绑定工具留 core。**
- **CLFBuiltinTools 演变**：注册表收集器——从管理器收集插件元数据（CLFToolMetaPOD）装配 CLFTool + 保留 2 个 core 内置工具的注册。**与阶段 1 B1 联动**：能力标签随元数据跨边界（flags 位集），executor 名字匹配已删（B1），新工具接入 = 新插件元数据，executor/注册表零改。
- **配置归属**：config/plugins/<name>.toml 独立文件（不经主配置 agent_settings，避免主配置膨胀）；host->config() 按 pluginId 路由；缺配置 → 插件内置默认（推广 TipsBar hardcoded fallback 模式）

### 3.7 工具/能力依赖图取证（2026-09-03，回答"工具集之间是否有互调"）

**取证结论：工具集（handler）之间零互相调用；能力域之间零互相调用。** 全仓调用点枚举如下：

| 调用方 | 被调用 | 类别 |
|---|---|---|
| 各 handler（BuiltinTools 8 处） | 同域能力函数（readFile/writeFile/editFile/listDirectory/executeCommand/searchContent/webFetch） | 域内 |
| ToolExecutor（core，唯一跨层调用方） | FileOps（readFileWithSnapshot/previewEdit/getFileMtime/getFileSize）+ Diff（computeDiff/CLFDiffLine/CLFDiffStats/CLFDiffOp） | **core → 能力，唯一链路** |
| todo_write / compress_context handler | CLFAgentLoop（setTodos/compressContextNow 等） | 工具 → core 自引用（留 core，§3.6） |
| FileOps 内部（readFileWithSnapshot→readFile、editFile→readFile） | FileOps | 域内互调 |
| SearchContent / CommandExec / WebFetch | CLFEncoding（clf_types，basic 层） | 共享 basic，非跨域 |
| qa_* 测试 | 各能力函数 | 测试直调，不影响插件依赖图 |

**对插件化的四个推论**：
1. **5 域 DLL 之间 requires() 全空**——无插件间依赖，管理器依赖图退化为平凡图（仅校验宿主 API 版本）；卸载任一域零波及（§3.2"单插件失败不影响其余"在能力层面天然成立）
2. **工具协作 = 模型编排，不在 handler 层**——CLFCode 的 agent loop 循环让模型按轮调用不同工具，handler 从不互调；插件化不改变此架构属性，跨域协作天然走模型轮次
3. **C1 接口化范围 = 唯一链路**（ToolExecutor → FileOps/Diff）——比初版担心的更小；接口化后其余域（command/search/web）**现状就无 core 调用**，铺开时零 core 改动
4. **过时注释修正（回流阶段 1）**：BuiltinTools.cpp:138-139 注释称"CLFFileOps::readFile 还被 SystemPromptBuilder 等内部路径调用"——**证伪**：SystemPromptBuilder 用裸 std::ifstream 自读（154/204/288），FileOps 唯一 core 调用方 = CLFToolExecutor。列阶段 1 P2-6 顺手修。

### 4.1 试点（2.2）

**试点逐步（pro 执行时细化）**：
1. C1+：clf_capabilities 静态目标 + ICLFFileService 接口 + ToolExecutor 改经接口（ctest 回归，功能等价）
2. 2.1：CLFPluginManager 骨架 + clf_plugin_api 头（CLFPlugin/CLFHostApi/CLFToolMetaPOD/CLFToolCallbacks）+ CMake DLL target 模板
3. 2.2a：tools.fileops.dll——FileOps/Diff 编 DLL + 工厂导出 + read/write/edit/list 工具元数据与 handler 打包
4. 2.2b：注册表装配——管理器收集元数据 → 装配 CLFTool → AgentLoop 注册（todo_write/compress_context 保持 core 注册）
5. 2.2c：/plugin 命令（list/load/unload/reload）

验证点：
1. 动态加载：manager 发现并加载，元数据入注册表
2. 路由：模型适配层调 write_file 经 manager.find → 路由 DLL 实现
3. 停用/热替换：/plugin unload tools.fileops → reload 新版 → 路由切新实例
4. 兜底：停用后模型再调 → 明确错误，模型走已有失败路径不崩
5. 依赖解析：requires 缺失 → 报错且不影响其他插件
6. 功能回归：文件操作全族（read/write/edit/list + diff 预览 + TOCTOU + 确认流）与 v0.6.0 等价

### 4.2 铺开路径

反向迭代：任一子步发现阶段 1 拆分不合理 → 回流修正（阶段 1 出口标准重新核验）

3. 管理器验证通过：加载/依赖/生命周期/路由/热替换/兜底
4. main 极薄：启动管理器 → 插件列表 → 配置 → 等输入
5. 阶段 3 挂载点就绪：管理器可作为第三方集成插件（集成插件本身也是插件）的宿主
6. core/basic/UI 内建（不迁 DLL）——理由见 §二 论证定案

## 七、开放项（2026-09-03 论证全部定案）

| 项 | 定案 |
|---|---|
| ① basic 层形态 | **header-only 静态共享头，不 DLL**（宏/inline 编 DLL 反而亏；clf_plugin_api 头同此模式——唯一跨 DLL 共享头） |
| ② core 子插件 | **不迁 DLL**——C2 拆角色（CLFTodoStore/CLFSessionFileCtx）保持进程内对象；跨边界传递 CLFContext（STL）成本高、热替换会话状态机零收益 |
| ③ UI 插件 | **不迁**——UI 是宿主侧本身；可替换 UI 非项目目标 |
| ④ 适配器插件 | **并入工具域**——handler 与能力同域打包（一个 DLL = 一个能力域 + 其工具定义与 handler），不单列 |
| ⑤ 内置工具 fate | **9 迁 2 留**——todo_write/compress_context 捕获 agent 引用（自引用），留 core；其余 9 个随域迁。CLFBuiltinTools 演变 = 注册表收集器 + 2 个 core 工具注册（§3.6） |
| ⑥ 插件粒度 | **一个 DLL = 一个能力域**（5 域：fileops/command/search/web/misc） |
| ⑦ 热替换语义 | **启动发现 + /plugin reload**（quiesce：无在途 runTurn + 无确认挂起）；对话中禁停 → 管理器返回明确错误 → 模型走已有失败自兜底 |
| ⑧ 试点模块 | **FileOps 域确认**（含 Diff——diff 预览是其工具域内依赖） |
| ⑨ 崩溃隔离 | **务实方案**：每插件 init/调用 try/catch 兜底（失败仅该插件禁用）+ set_terminate 已有；真隔离（进程级）后置选项 |
