## 二、现状与总目标

**现状**（v0.6.0）：除 MCP / subagent 外能力齐备、可正常干活；用户近两日实测稳定性与体验可接受。
**总目标**：CLFCode 演进为 **插件宿主 + 能力总线**——自身模块插件化（内部世界），并为第三方工具提供集成通道（第三方世界）。

**两个世界（机制不同，不共用契约）**：

| | 内部插件世界 | 第三方集成世界 |
|---|---|---|
| 内容 | 自研模块 / 自研工具 | 外部系统（dsh / Claude Code / MCP server / 子代理…） |
| 机制 | 进程内 DLL 热拔插（主进程 = CLFCode） | 进程间通信 IPC（CLFCode 为主进程） |
| 协议 | C 工厂 + 纯虚接口（内部 ABI） | 每目标各自适配，不强行统一（先调研） |

## 四、阶段主要工作与排期要点

### 阶段 1：代码审查与模块重构
1. 功能审查（结构/SOLID/重复三视角，问题清单 P0/P1/P2）
2. 模块化拆分（按未来插件边界划：basic/能力/core/适配/UI，依赖单向向下）
3. 修复执行（批次 A 纯搬移 → B 防雪崩接口化 → C 结构性；每批编译+测试+回归）
4. 验证回归 → 出口验收
> 排期：批次 A/B/C 顺序执行，每批独立可交付可回退；谷价时段路由 pro；执行中发现拆分不彻底 → 回流修正

### 阶段 2：自身插件化
1. 插件管理系统（CLFPluginManager + ABI 定义）
2. 试点：FileOps 域迁 DLL（验证动态加载/路由/停用/热替换/兜底；依赖阶段 1 C1 接口化）
3. 铺开其余域（fileops/command/search/web/misc；每批插件化后原功能回归验证）
4. main 变薄（启动管理器 → 加载插件列表 → 初始化配置 → 等待输入）
> 排期：先管理器 → 试点成功 → 铺开；过程中发现阶段 1 拆分不合理 → 回流修正（反向迭代）

### 阶段 3：第三方集成（方向记录，本期不排期实现）
1. 自研"第三方工具集成插件"（挂载阶段 2 插件管理系统）
2. 初步用例 dsh（协议调研先行）
3. 安装模型：配置文件声明 + 未装提示 + load 命令加载
> 排期：**占位**。激活 = 阶段 2 完成 + 用户排期。可复用既有 dsh 资产（设计/dsh/、分析/dsh/）

## 六、决策记录（已拍板，各阶段分册遵守）

| # | 决策 | 内容 |
|---|---|---|
| D1 | 插件形态 | **动态库（DLL）热拔插**，非静态注册——静态则插件化无意义 |
| D2 | 两个世界 | 自研工具 = 内部插件（进程内 DLL）；第三方 = IPC，机制不同，不共用能力契约 |
| D3 | 外部协议 | 每外部系统**各自适配，不强行统一**（不同系统调用方式不同，强统不划算；需调研） |
| D4 | 阶段顺序 | ① 功能梳理拆分修到无缺陷 → ② 内部插件化（先管理器→试点→铺开）→ ③ 第三方集成 |
| D5 | 自治与兜底 | 插件自己管自己、自己给自己兜底；所有插件调用由外部插件管理器统管 |
| D6 | 安装模型 | 仅配置文件声明；管理器不感知装没装 → 需要时提示安装 → load 命令加载 |
| D7 | 试点目标 | 阶段 3 初步用例 = **dsh**（自研第三方工具集成插件） |
