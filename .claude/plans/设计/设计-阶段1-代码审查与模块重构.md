## 二、现状测绘

### 2.1 全局根因（一句话）

**CMake 声明 clf_core 编译了 `CLFTools/CLFDiff.cpp` + `CLFFileOps.cpp`**（注释"编入 clf_core 避免循环依赖"）——core → tools 目录的反向依赖被"物理编入"绕过，**目录分层与构建分层不一致**，是后面多处问题的根。

### 2.2 三处约定缺失（防雪崩最高杠杆点）

1. **工具分类靠名字匹配**（加工具改 executor）
2. **输出接口纯虚全量实现**（加方法改 5 个类）
3. **会话策略由 UI 编排 core 原语**（加状态改 UI 多处）

### 2.5 职责边界模糊（关键）

- **core ↔ UI 双向泄漏**：core 做 UI 排版（restoreSession 拼 📋/✓ 文案 + 折叠块、finishTurn 拼文案、ToolExecutor 渲染 diff）；**UI 持有会话生命周期策略**（何时建 jsonl/追加 turn 在 CLFRepl::submit、/clear 六步状态机、/exit、/resume——UI 编排 core 6+ 原语）

## 四、模块化拆分蓝图（按未来插件边界）

分层（依赖单向向下，无循环；阶段 2 插件边界 = 本分层）：

```
basic（无业务：宏/UTF-8/时间/结果类型/公共 util）      ← 最底层，谁都能依赖
  ↓
能力层（偏业务领域能力：FileOps / Diff / CommandExec / Search / WebFetch）← 无 core 依赖，core 可调
  ↓
core（agent 编排 / 会话 / 摘要 / 安全 / todo 状态）     ← 编排不实现细节
  ↓
适配器（handler：模型 JSON ↔ 能力翻译）                ← 只做翻译
  ↓
UI（视图 / 输入 / 确认框；通过接口与后端交互）           ← 顶层分界线
```

> 注（阶段 2 论证联动）：适配器（handler）在阶段 2 随能力域打包进 DLL（"适配器并入工具域"，见阶段 2 分册 §二定案④）——阶段 1 仅保证 handler 层契约清晰（A4/B1），不要求物理独立。

模块归属现状（阶段 1 拆分时的目标形态）：
- **已是插件雏形**（内聚+接口化，拆分成本低）：CLFTypes（basic）、CLFFileOps（能力）、CLFNetwork（接口+实现分离）
- **需拆分**：CLFBuiltinTools（handler/注册/能力混绞）、CLFAgentLoop（拆会话/摘要/todo/安全子状态）、CLFSessionManager（拆存储+清死代码）、CLFRepl::run（拆视图/控制器）、CLFTerminal（状态收私有）
- **待定归属**：FileOps/Diff 正式归属（C1 裁定）、handler 适配层独立、工具注册机制（阶段 2 管理器解决）
