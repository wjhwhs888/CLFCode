## 三、设计

### 3.1 捕获层：双拼写归一解析（两处同构）

解析顺序（dsh 同构）：`prompt_tokens_details.cached_tokens`（OpenAI 兼容）优先，`prompt_cache_hit_tokens`（DeepSeek 原生）兜底。照既有"缺失保持原值——不估猜"哲学。

**① `CLFStreamAccumulator::feedUsage`（流式）**
```cpp
// 缓存命中 token：OpenAI 兼容拼写优先，DeepSeek 原生拼写兜底（dsh translate.ts 同构）
if (usage.contains("prompt_tokens_details") && usage["prompt_tokens_details"].is_object()
    && usage["prompt_tokens_details"].contains("cached_tokens")
    && usage["prompt_tokens_details"]["cached_tokens"].is_number())
    m_usageCacheHit = usage["prompt_tokens_details"]["cached_tokens"].get<int>();
else if (usage.contains("prompt_cache_hit_tokens") && usage["prompt_cache_hit_tokens"].is_number())
    m_usageCacheHit = usage["prompt_cache_hit_tokens"].get<int>();
```

**② `CLFProtocolAdapter::parseAssistantResponse`（同步）**：同逻辑 → `CLFAssistantResponse::m_usageCacheHit`。

### 3.2 累计层：独立类 `CLFTurnUsage`（SOLID 复查修订，2026-09-08）

**为何独立成类**：回合累计 + 百分比 + 文案是一个内聚职责簇（4 操作、纯逻辑零依赖），若按初稿放 AgentLoop（2 个 int 成员 + 私有 helper），与 C2 拆角色方向（P1-1 god 类治理）背道而驰——AgentLoop 刚拆走 3 个对象，不应再长出新职责簇。先例：`CLFTypes/CLFPeriodicTimer.hpp` 独立文件 + `ToolStats` 统计结构同族（CLFTypes.hpp:66）。**捕获层两处解析刻意不抽**（CCP：usage 字段解析与既有三字段因同一原因——provider 协议变更——变化，留在原类）。

**新文件 `src/CLFTypes/CLFTurnUsage.hpp`**（header-only，方法内联——CLFStreamAccumulator 同模式，零 CMake 源列表改动）：
```cpp
// CLFTurnUsage.hpp — 回合 usage 统计（缓存命中率显示的累计与文案）
// 纯值逻辑类：reset / accumulate / displayLine
// 累计口径：主循环内正常解析轮（R3 gate）累计；runTurn 入口 reset
#pragma once
#include <string>
namespace CLF::CLFTypes {
class CLFTurnUsage {
public:
    void reset() { m_promptTokens = 0; m_cacheHitTokens = 0; }
    void accumulate(int promptTokens, int cacheHitTokens) {
        m_promptTokens += promptTokens;
        m_cacheHitTokens += cacheHitTokens;
    }
    // 回合收尾统计行（缓存命中率显示 §3.3）
    // gate：prompt>0 且 cacheHit>0 才返回非空（无 usage 数据/零命中不宣称 0%）
    // 防虚报：cacheHit>=prompt → 100%，否则 floor 永不四舍五入
    // 注（2026-09-08 审查）：文案/块状分隔为 MVP 形态，UI 布局变化（行内/状态栏）时抽离至显示层
    std::string displayLine() const {
        if (m_promptTokens <= 0 || m_cacheHitTokens <= 0) return {};
        const int percent = m_cacheHitTokens >= m_promptTokens
                          ? 100
                          : m_cacheHitTokens * 100 / m_promptTokens;
        return "\n \n✳ 缓存命中 " + std::to_string(percent) + "%\n \n";
    }
private:
    int m_promptTokens = 0;
    int m_cacheHitTokens = 0;
};
} // namespace CLF::CLFTypes
```

**AgentLoop 接线**（仅持实例 + 编排，零逻辑）：
- 成员 `CLFTurnUsage m_turnUsage;`（hpp:230 旁，替代初稿 2 个 int）
- **reset**：runTurn 入口（cpp:104 `m_lastToolStats = {}` 旁）——回合边界
- **累计**：R3 gate 内（cpp:296-299）：
  ```cpp
  m_turnUsage.accumulate(parsed.m_usagePrompt, parsed.m_usageCacheHit);
  ```
  仅正常解析路径累计（中断/错误路径在 gate 前已 return，与 R3 同规则）；usage 未到达时 prompt=0 天然不累计。
- **精度说明**：触顶收尾请求（wrapUp，cpp:395-429）是独立同步调用，不走 R3 累计点（既有行为——m_totalTokensUsed 同样不累计收尾轮）→ 回合累计不含收尾轮，语义 = "主循环各轮"；不修正，displayLine 无感知。
- **口径注记（2026-09-08 设计审查）**：DeepSeek 每轮请求的 `prompt_tokens` = 本轮全部输入（**含共享历史，非增量**）——多轮工具调用求和后分母含重叠历史。ΣcacheHit/Σprompt 为**回合平均口径**，与 dsh 的"单轮命中率"（逐 assistant 消息，更接近"本轮实际省多少"）不等价。用户知情接受本口径；displayLine 语义 = "本回合全部请求输入中来自缓存的占比（重叠历史重复计权）"。若后续要"末轮命中率"视图，CLFTurnUsage 增方法即可，不影响累计数据。

### 3.3 显示层：回合收尾统计行（新显示区域）

**落点裁决理由**：usage 数据在 finishTurn 时已全链路落定（流式 usage chunk / 同步响应均在回合内到达）；命中率是回合级统计，与 ✻ worked 行同属"回合收尾统计"，两者相邻组成收尾区；零 UI 架构改动（复用 emitContent 内容流）；"新显示区域"语义 = 现有任何行都不追加、独立成行。

**位置**：finishTurn 内 `m_context.addMessage(...)`（:493）之后、return 之前。

**显示规则（gate + 防虚报）**：
```
m_turnPromptTokens <= 0 || m_turnCacheHitTokens <= 0 → 不显示
  （无 usage 数据 / 零命中均不显示——不宣称"0%"，不误导）
m_turnCacheHitTokens >= m_turnPromptTokens → "缓存命中 100%"
否则 → floor(cacheHit * 100 / prompt)%——整数除法天然 floor，永不四舍五入虚报到 100
```

**双通道显示**（关键：不污染模型上下文）：
- **流式**（m_stream=true）：`m_output->emitContent(cacheLine)` 直发——显示顺序 = 总结内容 → todo 收尾 → ✻ worked → **✳ 缓存命中 X%** ✓
- **非流式**（m_stream=false）：`finalContent += cacheLine`——**必须在 `addMessage` 之后追加**，否则缓存行会作为 assistant 消息进上下文污染下一轮请求；由 Repl（:290-293）在 runTurn 返回后一次性显示，顺序 = 总结 → ✻ worked → **✳ 缓存命中 X%** ✓
  - 注：非流式下 todo 收尾行既有行为（无条件 emit，显示在总结之前）不受本设计影响，不修正。
  - 注 2（2026-09-08 审查确认）：既有顺序 appendWorked(:492)→addMessage(:493)——worked 文本若含于 finalContent 会随 addMessage 入上下文（**既有行为**，MVP 外不修）；缓存行特意在 addMessage **之后**追加故不污染（本设计已验证该避让）。
  - **触顶路径（2026-09-08 终检修正）**：触顶（迭代耗尽）**不走 finishTurn**——:384-440 是独立收尾段（wrapUp → kTurnCapNotice → appendWorked → Warn → return），文档初稿"触顶共用 finishTurn 三出口"系错误断言。修正：触顶路径**单独接线同款逻辑**（:437 appendWorked 之后），显示顺序 = 总结 → wrapUp → 提示文案 → worked → 缓存行。双通道逻辑抽 **AgentLoop 私有 helper `appendCacheHitLine(finalContent)`**（见 §四 步骤 4），finishTurn 与触顶两处各一行调用，避免复制。触顶回合（48 轮长回合）缓存收益恰是最有价值的观测场景，与 worked 行显示一致性对齐。触顶路径 finalContent 本不进上下文（:419 仅 wrapUp.m_content 单独 addMessage），非流式追加零污染。

**文案**：`displayLine()` 产出（`"\n \n✳ 缓存命中 X%\n \n"`，与 worked 行同款块状分隔），AgentLoop 不拼文案。

### 3.4 边界与防御

| 场景 | 行为 |
|---|---|
| 非 deepseek provider（无 include_usage） | usage 未到达 → prompt=0 → gate 不显示，零回归 |
| 真实零命中（cacheHit=0 合法） | 不显示（不宣称 0%） |
| 异常数据 cacheHit > prompt | clamp 100%（`>=` 判定） |
| 中断/错误回合 | 早 return，无收尾行（既有语义，无显示） |
| 多工具回合（多次 API 调用） | Σ 累计，仅回合末显示一次 |
| 触顶收尾请求（wrapUp） | 独立同步调用不走 R3 累计点（既有行为）→ 不计入回合累计；不修正 |
| 触顶回合显示 | **触顶路径不走 finishTurn**（:384-440 独立收尾段）→ 单独接线（helper 同款逻辑，:437 后）；中断早退（:388/:408）无缓存行，与中断语义一致 |
| 老会话 / jsonl | 格式零改动（§一.4 定案） |
