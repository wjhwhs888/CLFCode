## 定稿摘要（pro 先读这一页）

**一句话**：命令执行层的职责是**把"跑一条命令"这件事的边界管住**——谁来终止、什么时候终止、输出留多少、错误怎么表达；**argv 用于"程序知道自己要跑什么"，shell 字符串只留给"模型想干什么"**（dsh 与 Claude Code 的共同做法）。

| 目标 | 内容 | 判定门 |
|------|------|--------|
| **G1 可终止** | 取消与超时**走同一条终止路径**；终止**整个进程树**；结果区分原因 | 中断时 ≤1 秒返回；无孤儿进程 |
| **G2 可限额** | 执行器层就限制输出字节数（不是先全量进内存再截断）；**头+尾**截断，结论不丢 | 长输出命令：模型能看到尾部结论 |
| **G3 可判定** | 错误归一化（`not_found` / `permission` / `timeout` / `non_zero_exit` / `platform_mismatch` / `interrupted`） | 模型不必读 raw 文案就能决定下一步 |
| **G4 可跨平台** | 第一期 Windows 实现，接口按第二期（Ubuntu 24.04 / CentOS 7 / Kylin V10）留门 | 平台差异不出平台层（§五） |

**根因集（flash 判断：去掉任一项，本次现象必然复现）**：G1（取消 + 杀树）、G2（限额与头尾截断）。**接近根因**：错误归一化、argv 化内部辅助命令（消 `2>nul` 类）。**可裁剪**：分级超时表细节、后台执行、持久 shell/PTY。（三层划分是**建议**，pro 可重划并要求说明理由。）

**已定参数（2026-09-22 用户拍板）**：命令**默认超时 120s**（对齐 Claude Code Bash 的 2 分钟默认）；**上限 = 配置项** `command_max_timeout_sec`，默认 **600**（与用户既有 cc-switch 配置 DeepSeek 参数的"超时可配"形态一致）。接线要点见 §10.2。

## 术语与编号规则

| 术语 | 含义 |
|------|------|
| **shell 模式** | 命令以**字符串**给出，由平台 shell 解释（`cmd /s /c`、`/bin/sh -c`）——**模型面向的形态** |
| **argv 模式** | 命令以**程序 + 参数数组**给出，**不经 shell**——**程序面向的形态** |
| **终止路径** | `terminateTree(reason)`：杀整棵进程树 + 收尾（唯一实现，两个触发源） |
| **取消（cancel）** | 用户 ESC/Ctrl+C 触发的中止（触发源之一） |
| **超时（timeout）** | 到达 `m_timeoutSec` 触发的中止（触发源之二） |

**编号**：`G1-G4` 目标；`W-*` 缺陷；`批*` 工作项；`C1-Cn` 本文档 qa 用例；`I1-I3` 不变量。

## 一、目标与非目标

### 1.1 目标
- **G1 可终止**：取消/超时共用一条终止路径，杀整棵进程树，结果标注原因；
- **G2 可限额**：执行器层限额（`m_maxOutputBytes`），头+尾截断，结论不被截掉；
- **G3 可判定**：错误归一化为稳定枚举，附识别模式；
- **G4 可跨平台**：接口与实现分层，第一期只交 Windows 实现。

### 1.2 非目标（第一期）
- 不改**模型面向的工具形态**：`execute_command` 仍收 shell 字符串（与 dsh/Claude Code 一致）；
- 不做**持久 shell / PTY 终端**（dsh 的 `-persistent` 与 Claude Code 的 cwd 持久语义）——登记为第二期增强；
- 不做**后台执行**（Claude Code 的 `run_in_background`）——登记；
- 不做沙箱（dsh 的 bwrap/landlock/seatbelt/ACL——第二期若需要另立设计）；
- 不动 `3rdparty/`；不动脚本层。

## 四、设计原则

1. **双模分工铁律**：模型面向 = shell 模式；宿主内部辅助命令 = argv 模式（§九）。
2. **终止路径唯一，触发源两种**：取消与超时**必须**走同一实现，只在结果里区分原因（否则复现"两个入口两套行为"——`设计-中断时效性` B3 的教训）。
3. **限额在源头**：`m_maxOutputBytes` 在执行器读取阶段生效，不依赖"读完再截"。
4. **结论优先保留**：截断必须**头+尾**（命令的结论在尾部）。
5. **平台差异不出平台层**：`#ifdef` 集中在执行器平台实现与 `CLFPlatform`，上层只见 `CLFExecSpec/CLFExecResult`。
6. **零行为变更优先**：不改 shell 包装（`chcp 65001 >nul &`）、不改 cwd 校验语义、不改退出码白名单语义（`exitCodeMeansSuccess`）。

## 五、架构分层与职责边界

```
工具层   execute_command（shell 字符串，模型面向）
         ├─ 危险命令检测 / 退出码白名单 / cwd 边界校验（现有，不动）
         └─ 结构化工具（read_file / list_directory / search_content）——不经 shell
   │  CLFExecSpec{ m_command } ─────────────┐
   ▼                                        │  CLFExecSpec{ m_argv }
执行层   CLFProcessRunner（本文档）         │  ← 内部辅助命令（§九）
         ├─ 平台分派（Windows / POSIX）
         ├─ 终止路径 terminateTree(reason) ← 取消 / 超时
         ├─ 限额与头尾截断（§6.4）
         └─ 错误归一化（§6.5）
   ▼
平台层   CLFPlatform（设计-平台层收敛 §四）：路径 / 控制台 / 编码 / 剪贴板原语
         进程创建与作业对象原语（Windows：CreateProcessW + Job Object）
```

## 六、接口设计

### 6.1 `CLFExecSpec` / `CLFExecResult`（命名遵项目规范：CLF 前缀 + m_ 成员）

```cpp
// 执行请求（宿主内部结构，不进插件 ABI）
struct CLFExecSpec {
    std::string              m_command;          // shell 模式：命令字符串（非空即走 shell）
    std::vector<std::string> m_argv;             // argv 模式：m_argv 非空时优先，不经 shell
    std::string              m_cwdUtf8;          // 空 = 继承当前工作目录
    int                      m_timeoutSec = 120; // 默认 120s（§10.2）；有效值 = min(请求值, 配置上限)，执行器另有硬顶
    size_t                   m_maxOutputBytes = 256 * 1024;   // 执行器层限额（stdout/stderr 各自）
    bool                     m_captureStderr = true;
};

struct CLFExecResult {
    int         m_exitCode     = -1;
    bool        m_timedOut     = false;
    bool        m_interrupted  = false;   // 取消触发（与 m_timedOut 互斥）
    bool        m_launchFailed = false;
    bool        m_truncated    = false;
    std::string m_stdout;                 // 已按头+尾截断
    std::string m_stderr;
    std::string m_errorKind;              // §6.5 枚举之一；空 = 正常
};
```

### 6.2 执行器

```cpp
class CLFProcessRunner {
public:
    // isCancelled 为空 = 不可取消（行为与现状一致）
    static CLFExecResult run(const CLFExecSpec& spec,
                             const std::function<bool()>& isCancelled = {});
    // 供危险命令检测 / 错误归一化复用的首 token 提取（去路径、去引号、按 PATHEXT 归一）
    static std::string executableName(const std::string& command);
};
```

- **兼容门面保留**：`CLFTools::executeCommand(command, timeoutSeconds, cwd, isCancelled)`（`设计-中断时效性` §A.3 已定签名）**内部转调** `CLFProcessRunner::run`，外部行为不变。
- 落点建议：`src/CLFTypes/CLFProcessRunner.*`（与 `CLFPlatform` 同层，零项目依赖）或 `src/CLFTools/`；**由 pro 按依赖方向选定并说明**（SDP：不应反向依赖 core）。

### 6.3 与取消 / 超时的接口

- 触发源：① `isCancelled()` 返回 true；② 到达 `m_timeoutSec` 或内部读超时。
- **两者都调用** `terminateTree(reason)`（§七/§八 的唯一终止实现），随后：
  - 取消 → `m_interrupted = true`，`m_errorKind = "interrupted"`；
  - 超时 → `m_timedOut = true`，`m_errorKind = "timeout"`。
- **检查粒度**：Windows 现成的 `WaitForSingleObject(pi.hProcess, 50ms)` 轮询即为检查点（无需新线程）；POSIX 现成的 `waitpid(WNOHANG)` + 100ms 同理。
- 上层的协议闭合与文案由 `设计-中断时效性` §十一 / §11.3 负责，本文档只保证"结果带得出原因"。

### 6.4 输出限额与截断口径（统一）

| 层 | 口径 | 说明 |
|----|------|------|
| **执行器读取** | `m_maxOutputBytes`（默认 256KB，**头+尾各半**） | 超限即停读该流并置 `m_truncated`（防内存膨胀） |
| **入库（模型可见）** | **头+尾**，标记省略量 | 命令通道**从"仅头 8000 字符"改为头尾**——修 W-6 |
| **UI 显示** | 保持现状（头尾 16+16 行） | 不动 |
| **`web_fetch`** | 保持现状（8192+2048 字节） | 不动 |

- **复用优先**（项目规范）：字节级用现成的 `headTailCapBytes`（`CLFWebFetch.cpp:28`），行级用 `headTailCapWithMarker`（`CLFTypes.hpp:222`）——**不要再写第三份截断实现**。
- 阈值建议：命令输出入库 head/tail 各 `8KB`（比现 8000 字符更宽松且明确），标记格式沿用 `[truncated, original: N chars]`。

### 6.5 错误归一化

| `m_errorKind` | 含义 | 识别模式（Windows / POSIX） |
|---------------|------|------------------------------|
| `not_found` | 程序不存在 | `is not recognized as an internal or external command`、`The system cannot find the file specified`（Win32 2）、POSIX `ENOENT` / `command not found` |
| `permission` | 权限不足 | `Access is denied`（Win32 5）、`EACCES` / `EPERM` / `Permission denied` |
| `timeout` | 超时终止 | 我们自己的 `m_timedOut` |
| `interrupted` | 用户取消 | 我们自己的 `m_interrupted` |
| `non_zero_exit` | 正常启动但退出码非 0（**且不在白名单**） | 退出码 + `executableName` 白名单判定（`exitCodeMeansSuccess` 语义不变） |
| `platform_mismatch` | 该平台不存在该命令/语法 | 例如在 cmd 下用 `&&` 之外的 POSIX 语法、`head/tail/grep` 等（**保守判定，宁可归 `not_found`**） |
| `launch_failed` | 创建进程本身失败 | `CreateProcessW` 失败码 / `posix_spawn` 失败 |

- 归一化结果作为结构化字段返回（JSON 里加 `"errorKind"`），**原始 stderr 仍完整保留**——归一化是给模型的**快信号**，不是替代证据。
- `exitCodeMeansSuccess` 的既有白名单语义**不动**（`grep/rg/findstr/diff/fc` 退出码 1 视为成功）。

## 九、辅助命令 argv 化（消 `2>nul` 类）

**问题**：`CLFSubprocessRunner::run(cmd)`（[CLFSubprocessRunner.cpp:8-17](src/CLFCore/CLFSubprocessRunner.cpp#L8-L17)）走 `popen`（= 必然经过 shell），调用点写的是 shell 语法 → `2>nul` 缺陷出生于此。

**方案**：`CLFSubprocessRunner` 改为 **argv 模式门面**（内部调 `CLFProcessRunner::run`，`m_argv` 非空）：

| 现调用点 | 现命令 | argv 化后 |
|----------|--------|-----------|
| `detectOsInfo` | `ver 2>nul` | ⚠ `ver` 是 **cmd 内建**，无双模直执 → 改用 **`CLFPlatform` 的版本原语**（读注册表/`GetVersionExW`）或显式 shell 模式并走平台层 `nullDevice()`；**由 pro 在实施时定**（见 §十四 待核实） |
| `detectOsInfo`（POSIX 分支） | `uname -a 2>/dev/null` | `argv = {"uname", "-a"}`（不需重定向：stderr 单独捕获） |
| `captureGitStatus` | `git -C "<root>" branch --show-current 2>nul` 等 3 条 | `argv = {"git","-C",root,"branch","--show-current"}` 等（**stderr 与 stdout 分开捕获，不再需要 `2>nul`**） |

- **收益**：`nul` / `$null` / `/dev/null` 这一整类问题消失；引号/注入面消失；`stderr` 可控。
- **代价**：`git` 不在 PATH 时的错误要自己归一化（正好用 §6.5）。
- **不改**：模型面向的 `execute_command` 仍是 shell 字符串。
