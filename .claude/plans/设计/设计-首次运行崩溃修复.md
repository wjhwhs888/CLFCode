# 设计-首次运行崩溃修复方案

> **状态**：已实施，长期观察（当前无法复现）
> **创建**：2026-08-11
> **实施**：2026-08-11
> **关联**：用户报告首次运行必崩，第二次起正常，公司和家里电脑均复现

---

## 一、Context（背景）

### 问题描述

CLFCode 在首次启动后，第一轮对话进行到工具执行阶段（约第 2-5 条工具调用），**静默退出，无任何报错信息**。第二次启动后一切正常。

### 崩溃特征

| 特征 | 详情 |
|------|------|
| 触发条件 | 首次运行，第一轮对话 |
| 崩溃位置 | 工具执行阶段（非 API 请求） |
| 崩溃形式 | **静默退出**（无报错、无弹窗） |
| 复现率 | 100%（两台机器均复现） |
| 执行路径 | async submit 线程 → roundTurn() → CLFToolExecutor::execute() |

### 根因分析

**核心机制**：所有 catch 块只捕获 `const std::exception&`，非标准异常会穿透所有 catch 层，到达 `std::thread` 入口函数后触发 `std::terminate()` → 进程静默退出。

**异常逃逸路径**：
```
std::thread (CLFAsyncSubmit::launch)     ← 无 catch，异常在此触发 std::terminate()
  └─ CLFRepl::submit()                    ← catch (const std::exception&)
       └─ CLFAgentLoop::runTurn()         ← catch (const std::exception&)
            └─ CLFToolExecutor::execute()  ← handler 有 catch (const std::exception&)
```

**首次运行特异的触发因素**（分析出的两个最可能原因）：

1. **子进程 stdin 继承控制台句柄**（`CLFCommandExec.cpp:65`）：
   - `execute_command` 将父进程（FTXUI alternate screen buffer）的 `STD_INPUT_HANDLE` 传给子进程 cmd.exe
   - 首次运行时 FTXUI 刚进入 alternate screen，终端状态不稳定
   - cmd.exe 子进程可能向控制台发送状态查询序列，与 FTXUI 事件循环产生冲突
   - 产生意外的终端事件（类似 ESC 序列泄露）

2. **非标准异常穿透**：FTXUI / httplib / Windows API 内部可能抛出非 `std::exception` 类型的异常，在工具密集执行的首次运行中被触发

### 为什么必须优先修复

- **用户体验灾难**：首次使用就崩溃，极大概率导致放弃使用
- **隐蔽性强**：第二次运行正常，用户可能归因于"偶然"，不会报告
- **阻塞后续开发**：无法在干净环境中稳定运行

## 二、修复方案

### 方案概览

三个修复点，按防御层级排列：

| 层级 | 修复 | 类型 | 说明 |
|------|------|------|------|
| L1 | 线程边界加 `catch(...)` | 治标（防 `std::terminate`） | 确保任何异常都不会导致静默退出 |
| L2 | 子进程 stdin 隔离 | 治本（推测根因） | 移除控制台句柄继承 |
| L3 | 崩溃诊断日志 | 辅助（定位精度） | 在关键节点写日志，下次异常可精确定位 |

### L1：线程边界异常兜底

**目标**：即使有未预期的异常逃逸，也不会触发 `std::terminate()`，而是记录日志并优雅恢复。

**修改文件**：`src/CLFUI/CLFAsyncSubmit.cpp`

**修改内容**：在 `launch()` 的线程函数中加 `catch(...)`：

```cpp
// 修改前
void CLFAsyncSubmit::launch(std::function<void()> task) {
    join();
    m_submitting = true;
    m_thread = std::thread([this, t = std::move(task)]() {
        t();
        m_submitting = false;
    });
}

// 修改后
void CLFAsyncSubmit::launch(std::function<void()> task) {
    join();
    m_submitting = true;
    m_thread = std::thread([this, t = std::move(task)]() {
        try {
            t();
        } catch (const std::exception& e) {
            // 标准异常：记录后清理上下文
            CLF::CLFCore::CLFLogger::instance().error(
                std::string("[AsyncSubmit] Uncaught std::exception: ") + e.what());
        } catch (...) {
            // 非标准异常（SEH / 未知类型）：记录后继续
            CLF::CLFCore::CLFLogger::instance().error(
                "[AsyncSubmit] Uncaught unknown exception — thread rescued from std::terminate");
        }
        m_submitting = false;
    });
}
```

**需要新增 include**：
```cpp
#include "CLFCore/CLFLogger.hpp"
```

**影响范围**：`CLFAsyncSubmit` 仅此一处线程入口。修改后异常会被记录到日志文件，方便后续排查。

### L2：子进程 stdin 隔离

**目标**：阻断 cmd.exe 子进程对 FTXUI 控制台的输入句柄访问，消除终端序列干扰。

**修改文件**：`src/CLFTools/CLFCommandExec.cpp`

**修改内容**：将子进程 stdin 从继承控制台句柄改为 NULL（或空管道）。

```cpp
// 修改前（CLFCommandExec.cpp:65）
si.hStdInput = GetStdHandle(STD_INPUT_HANDLE);

// 修改后
si.hStdInput = nullptr;  // cmd.exe /s /c "..." 不需要 stdin
```

**理由**：
- `cmd.exe /s /c "command"` 模式下，所有命令内容已在命令行参数中，**stdin 完全不需要**
- `GetStdHandle(STD_INPUT_HANDLE)` 返回的句柄指向 FTXUI 管理的 alternate screen buffer
- 子进程持有此句柄可能发送控制序列干扰 FTXUI 事件循环
- 传 `NULL` 是最简洁最安全的做法（若担心某些命令需要 stdin，可传空管道读取端）

**备选方案**（更保守，但更安全）：
```cpp
// 创建空管道作为 stdin（子进程读到的永远是 EOF）
HANDLE hInRead = nullptr;
HANDLE hInWrite = nullptr;
SECURITY_ATTRIBUTES sa = {sizeof(sa), nullptr, TRUE};
if (CreatePipe(&hInRead, &hInWrite, &sa, 0)) {
    SetHandleInformation(hInWrite, HANDLE_FLAG_INHERIT, 0);
    si.hStdInput = hInRead;
} else {
    si.hStdInput = nullptr;
}
// ... CreateProcess ...
if (hInRead) CloseHandle(hInRead);
if (hInWrite) CloseHandle(hInWrite);
```

**推荐**：直接用 `nullptr`。备选方案增加了代码复杂度但没有实际收益（CLFCode 的使用场景中，子进程永远不会读 stdin）。

### L3：崩溃诊断日志

**目标**：在关键节点打日志，下次若仍有异常，可从日志精确定位出问题的工具和参数。

**修改文件**：`src/CLFCore/CLFToolExecutor.cpp`

**修改内容**：在 `execute()` 的工具调用循环中加入执行前后日志（仅 Debug 级别）：

```cpp
for (const auto& call : calls) {
    // ... 中断检查 ...
    
    // 新增：执行前日志
    LOG_DEBUG("Executing tool: " + call.m_name + " with args: " + 
              (call.m_arguments.size() > 100 
               ? call.m_arguments.substr(0, 100) + "..." 
               : call.m_arguments));
    
    // ... 工具查找、安全策略检查 ...
    
    try {
        result.m_content = it->m_handler(call.m_arguments);
        // 新增：执行成功日志
        LOG_DEBUG("Tool " + call.m_name + " completed, result: " + 
                  std::to_string(result.m_content.size()) + " chars");
    } catch (const std::exception& e) {
        // 新增：执行异常日志（已有 catch，加日志即可）
        LOG_ERROR("Tool " + call.m_name + " exception: " + e.what());
        // ... 原有错误处理 ...
    }
    
    // ... 结果处理 ...
}
```

或者使用现有的 `CLFLogger::instance().debug(...)`。注意：需要在文件头部确认 `CLFLogger.hpp` 已被 include（当前 CLFToolExecutor.cpp 没有 include logger）。

## 四、长期观察策略

### 当崩溃再次出现时的诊断流程

1. **查看日志**：`doc/log/clf_agent.log`
   - 搜索 `[AsyncSubmit]` → 确认是否为线程异常逃逸
   - 搜索 `[ToolExec]` → 定位崩溃前最后执行的工具和参数
   - 根据日志中最后一个 `[ToolExec] executing:` 确定是哪个工具触发的

2. **根据日志判断**：
   - 若有 `[AsyncSubmit] Uncaught` → 说明 L1 兜底生效，根因在工具或 API 层
   - 若无 `[AsyncSubmit]` 且进程仍静默退出 → 根因在更底层（如 FTXUI 主线程崩溃），需扩大搜索范围
   - 若某个 `[ToolExec] executing:` 之后无对应 `done` 或 `failed` → 该工具 handler 内部触发了非标准异常

3. **复现时进一步加固**：
   - 若根因为 `execute_command` → 考虑 L2 备选方案（空管道替代 nullptr）
   - 若根因为特定工具 → 对该 handler 内部加更细粒度的 try/catch
   - 若根因在 FTXUI 渲染线程 → 考虑在 Renderer 中加异常保护

### 日常检查项

- 每次启动后关注 `doc/log/clf_agent.log` 中是否有 `[AsyncSubmit]` 或 `[ToolExec]` 异常记录
- 工具执行中出现 `[ToolExec] ... failed:` 属于正常错误（如文件不存在），但 `[AsyncSubmit]` 出现必须关注

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| L2 `nullptr` 导致某些命令失败 | 极低 | 低 | cmd.exe 命令行模式不需要 stdin |
| L1 `catch(...)` 掩盖真实 bug | 中 | 中 | L3 日志记录所有异常，不会被掩盖 |
| 修复未覆盖根因（若根因在 FTXUI 主线程） | 低 | 高 | L1+L3 只保护 async submit 线程；若主线程崩溃仍需扩大防御面 |
| 长期未复现，防御代码成为死代码 | 中 | 低 | 防御代码极轻量（~10 行），不影响性能和可读性 |

## 六、验证标准

1. 首次运行（干净环境）→ 输入触发多工具调用的指令 → **不再静默退出**
2. 若仍有异常 → 日志文件包含 `[AsyncSubmit]` 开头的错误记录，指明异常类型
3. 所有已有测试通过
4. 正常对话流程不受影响
5. 长期运行中 `[AsyncSubmit]` 关键词不出现在日志中（除非真实异常发生）
