## 一、ABI 头设计

### 1.1 文件划分与依赖纪律

```
src/CLFPluginApi/
├── CLFPluginApi.hpp     # 核心 ABI（本步新建）
├── CLFToolApi.hpp       # 工具插件域（本步新建）
└── CLFFileService.hpp   # 文件能力域（C1 已落地，本步一行回流修正）
```

**依赖纪律**（§3.5 原文"禁依赖其他头"的精确化）：

- ❌ **禁**依赖 `CLFPluginApi/` **之外**的任何项目头（clf_types / core / UI / tools / 第三方）
- ✅ **允许** `CLFPluginApi/` 内部头之间互相依赖（同属一套 ABI，共享同一版本号）

> **修正说明**：§3.5 原文"独立小目标或 header-only，禁依赖其他头"若按字面执行，`CLFToolApi.hpp` 无法包含 `CLFPluginApi.hpp`（ICLFToolProvider 需要 CLFService 基类），会导致 ABI 头被迫塞进单文件。此处按"禁依赖目录之外"解释，**不改变原文意图**（隔离 ABI 与实现），仅消除字面歧义。

**标准头**：全部 `#pragma once` + `#include <cstddef>` / `<cstdint>`（无其他 include）。

### 1.2 CLFPluginApi.hpp（核心）

```cpp
// CLFPluginApi.hpp — 插件 ABI 核心（clf_plugin_api，唯一跨 DLL 共享头之一）
// 阶段 2 分册 §3.1 细化：C 工厂符号 + 纯虚接口 + POD 服务表；
// 跨 DLL 边界禁传 STL / 异常 / RTTI（§3.1 + 本步补充纪律）。
// 本头不依赖 CLFPluginApi/ 之外的任何项目头，宿主与插件统一编译链共享。
//
// 生命周期约定（实现侧义务）：
// - 所有 const char* 返回值由**返回方**持有，调用期间有效，接收方必须立即复制
// - 服务实例（CLFService*）由**提供方插件**持有，生命周期 ≥ 其 DLL 被加载期间
// - 【审查补 2026-09-11】unload 后该插件全部服务实例失效——消费方**不得跨 unload
//   缓存 CLFService\***；每次使用前经 getService 重新获取（卸载后查询返回 nullptr，§3.3）
//   【注意（pro 拍板补）】宿主侧**长期持有**的服务指针（如 C1 的 AgentLoop 构造注入
//   ICLFFileService*）与此约束的交互：2.1 无宿主长期持有、无热卸载，无冲突；
//   2.2a 迁 DLL 后宿主持有指针指向插件实例，2.2c 支持热卸载时须随 unload 失效——
//   列入 2.2a 实施评估（实现形态：持指针改每次 getService，或 unload 前通知宿主刷新）
//
// example（插件侧）：
//   class MyPlugin : public CLF::CLFPluginApi::CLFPlugin { ... };
//   extern "C" CLF_PLUGIN_EXPORT CLFPlugin* CLFPluginCreate(const CLFHostApi* host) {
//       return new MyPlugin(host);
//   }

#pragma once
#include <cstddef>
#include <cstdint>

namespace CLF::CLFPluginApi {

// ============================================================================
// ABI 版本
// ============================================================================

// 不兼容变更 = +1；宿主与插件版本不等 → 管理器拒绝加载 + 提示重建（§3.1④）
constexpr uint32_t CLF_PLUGIN_API_VERSION = 1;

// ============================================================================
// 日志级别（跨边界 POD 编码）
// ============================================================================

// 与 CLF::CLFCore::CLFLogLevel 序对齐（0=Debug/1=Info/2=Warn/3=Error）；
// 对应关系由 CLFHostApiImpl.cpp 的 static_assert 双向钉死（照 CLFDiffOpCode 先例）
enum CLFLogLevelCode : int {
    LogCodeDebug = 0,
    LogCodeInfo  = 1,
    LogCodeWarn  = 2,
    LogCodeError = 3,
};

// ============================================================================
// 服务基类与服务表
// ============================================================================

// 所有跨边界服务接口的公共基类（ICLFFileService / ICLFToolProvider 等继承之）。
// 存在的唯一目的：让 CLFHostApi::getService 有类型安全的返回类型——
// 单继承链下 static_cast<具体接口*>(CLFService*) 地址调整正确（禁 RTTI，见 §1.5）
//
// 【实现约束（设计审查 2026-09-11）】服务表项必须指向"该接口自身的 CLFService 基类子对象"：
// 一个插件类若同时实现多个服务接口（多继承 → 多个 CLFService 基类子对象），每个服务表项
// 须用其对应接口视角的 static_cast<具体接口*>(this)（编译期已知偏移）；宿主侧 downcast
// 仅在指针指向对应子对象时正确。禁止把"某一个"CLFService* 复用于多个服务项。
class CLFService {
public:
    virtual ~CLFService() = default;
};

// 服务表中的一项（"服务名 → 实例"）
struct CLFServiceEntry {
    const char* name;      // 服务名（宿主契约，如 "file" / "tool.provider"；非插件 ID）
    CLFService* instance;  // 由提供方插件持有
};

// ============================================================================
// 插件本体（自描述 + 生命周期）
// ============================================================================

class CLFPlugin {
public:
    virtual ~CLFPlugin() = default;

    // 唯一 ID，如 "tools.fileops"（依赖图与日志用）
    virtual const char* name() const = 0;

    // 插件自身版本（如 "1.0.0"，仅展示/日志，不参与兼容判定）
    virtual const char* version() const = 0;

    // 编译期依赖的 ABI 版本（恒为 CLF_PLUGIN_API_VERSION 的值），
    // 与宿主 apiVersion() 精确相等才加载（§3.1④；精确匹配的取舍见 §1.5）
    virtual uint32_t hostApiVersion() const = 0;

    // 依赖的**服务名**表（nullptr 结尾；无依赖返回空表）。
    // 管理器解析为"谁 provides 该服务"建立加载顺序
    virtual const char* const* requires() const = 0;

    // 本插件提供的服务表（nullptr 结尾；无服务返回空表）。
    // 管理器加载后收集入注册表；**禁 RTTI 的关键**——不靠 dynamic_cast 取领域接口
    virtual const CLFServiceEntry* services() const = 0;

    // 自治初始化（失败 → 管理器标记该插件禁用，其余插件不受影响；§3.2 隔离兜底）
    virtual bool init() = 0;

    // 自治清理（卸载前调用；不得抛异常跨越边界）
    virtual void shutdown() = 0;
};

// ============================================================================
// 宿主注入面（管理器 → 插件）
// ============================================================================

class CLFHostApi {
public:
    virtual ~CLFHostApi() = default;

    // 宿主当前 ABI 版本
    virtual uint32_t apiVersion() const = 0;

    // 日志（级别见 CLFLogLevelCode；宿主不再二次判空，插件保证 msg 非空）
    virtual void log(int level, const char* msg) const = 0;

    // 本插件配置段读取：key 不存在返回 nullptr（插件用内置默认，§3.4 fallback 模式）；
    // 返回值宿主持有，调用期间有效
    virtual const char* config(const char* pluginId, const char* key) const = 0;

    // 服务查询（按**服务名**路由，与 requires() 的 SDP 语义统一——修正③）：
    // 不存在返回 nullptr → **调用方自兜底**（降级/报错，不崩；§3.1）
    // 【审查修订 2026-09-11】原签名 (pluginId, service) 要求调用方知提供方身份，与修正③
    // "依赖指向服务名而非实现身份"自相矛盾；定案 = 仅服务名。若将来需要调用方审计，
    // 可加 callerPluginId（语义=调用方身份，不参与路由）。
    virtual CLFService* getService(const char* service) const = 0;

    // 跨边界所有权转移通道（/MD 统一前提下当前实现可直转 malloc/free；
    // 保留此面是为 ABI 不依赖"必须 /MD"的隐式约定，未来 /MT 场景无需改 ABI）
    virtual void* alloc(size_t size) const = 0;
    virtual void  free(void* ptr) const = 0;
};

// ============================================================================
// 插件导出符号（每个插件 DLL 只导出这两个 C 符号，§3.1）
// ============================================================================

// 跨编译器导出宏（MSVC 与 GCC/MinGW 双构建链对称——与 §1.5 禁 RTTI 同一理由）
#if defined(_MSC_VER)
#define CLF_PLUGIN_EXPORT __declspec(dllexport)
#else
#define CLF_PLUGIN_EXPORT __attribute__((visibility("default")))
#endif

// typedef 形态便于插件侧书写（跨边界符号不得为 C++ 名字修饰）
typedef CLFPlugin* (*CLFPluginCreateFn)(const CLFHostApi* host);
typedef void       (*CLFPluginDestroyFn)(CLFPlugin* plugin);

} // namespace CLF::CLFPluginApi
```

**插件侧完整实现样板**（写入 2.2a 编码约定；2.1 的测试插件即照此写）：

```cpp
using namespace CLF::CLFPluginApi;

class MyPlugin : public CLFPlugin, public ICLFToolProvider {
public:
    explicit MyPlugin(const CLFHostApi* host) : m_host(host) {
        // 服务表：静态字符串 + 实例指针（本对象）。
        // static_cast 在派生类内部完成——编译期已知偏移，零 RTTI
        m_services[0] = CLFServiceEntry{"tool.provider", static_cast<ICLFToolProvider*>(this)};
        m_services[1] = CLFServiceEntry{nullptr, nullptr};
    }

    // —— CLFPlugin ——
    const char* name() const override { return "tools.my"; }
    const char* version() const override { return "1.0.0"; }
    uint32_t hostApiVersion() const override { return CLF_PLUGIN_API_VERSION; }
    const char* const* requires() const override {
        static const char* const kNone[] = {nullptr};   // 空依赖表
        return kNone;
    }
    const CLFServiceEntry* services() const override { return m_services; }
    bool init() override { /* 读 host->config 建默认值；失败返回 false */ return true; }
    void shutdown() override {}

    // —— ICLFToolProvider ——
    int toolCount() const override { return 1; }
    const CLFToolMetaPOD* toolMeta(int i) const override { return i == 0 ? &kMeta : nullptr; }
    bool callTool(const char* name, const char* argsJson, void* ctx,
                  const CLFToolCallbacks* cb) override {
        try {
            if (cb && cb->onResult) cb->onResult(ctx, argsJson, std::strlen(argsJson));
            return true;
        } catch (...) {                                  // 异常零逸出（§3.1）
            if (cb && cb->onError) cb->onError(ctx, "internal error");
            return false;
        }
    }

private:
    const CLFHostApi* m_host;          // 非拥有；宿主生命周期 > 插件（管理器保证）
    CLFServiceEntry   m_services[2];   // 必须为成员（含 this 指针，不能是 static 局部）
    static constexpr CLFToolMetaPOD kMeta{
        "my_tool", "示例工具", R"({"type":"object","properties":{}})",
        /*risk=*/0, /*flags=*/ToolFlagNone, /*concludesTurn=*/0
    };
};

extern "C" CLF_PLUGIN_EXPORT
CLF::CLFPluginApi::CLFPlugin* CLFPluginCreate(const CLFHostApi* host) {
    return new MyPlugin(host);   // 构造中保存 host 指针
}
extern "C" CLF_PLUGIN_EXPORT
void CLFPluginDestroy(CLFPlugin* plugin) { delete plugin; }
```

> **服务表必须是成员（不能是函数内 static 局部）**：表内含 `this`（每个实例不同），且 `services()` 返回值须在插件存活期间持续有效。`CLFToolMetaPOD` 的字符串字面量可 static（生命周期 = 程序）。

> **【插件编码约定（设计审查 2026-09-11）】插件 DLL 禁文件级非平凡静态对象**：项目已三次踩此坑
> （静态析构顺序未定义 → 段错误；magic static 死锁）。插件内全局对象的构造/析构发生在
> `LoadLibrary` / `FreeLibrary` 期间，析构期访问宿主或跨 DLL 状态极易崩溃。
> 可 static 的仅限：字符串字面量、`constexpr` POD（如 `CLFToolMetaPOD kMeta`）。

> **`init()` 不带 host 参数的取舍**：§3.1 草案工厂签名 `CLFPluginCreate(const CLFHostApi* host)` 已把 host 交给插件，`init()` 再传一次即双来源。定案：**host 经工厂传入并由插件保存**，`init()` 保持无参（与草案一致）。

### 1.3 CLFToolApi.hpp（工具插件域）

```cpp
// CLFToolApi.hpp — 工具插件域接口（clf_plugin_api，唯一跨 DLL 共享头之一）
// 阶段 2 分册 §3.1③ 细化：工具元数据 POD + 调用回调 + 提供者接口。
// 与进程内 CLFTool（CLFTypes.hpp:124）同构，但无 std::function / 无 STL。
//
// 调用语义（与现有 handler 等价，宿主侧唯一调用点 CLFToolExecutor.cpp:593）：
//   进程内：std::string m_content = it->m_handler(call.m_arguments);
//   跨边界：callTool(name, argsJson, ctx, cb) → cb->onResult 或 cb->onError
//   **两者产出的文本都走既有 formatToolResult 判定 ok/error——行为等价**
//
// example（宿主侧）：
//   std::string content;
//   CLFToolCallbacks cb{};
//   cb.onResult = [](void* ctx, const char* s, size_t n) {
//       static_cast<std::string*>(ctx)->assign(s, n);
//   };
//   cb.onError  = cb.onResult;              // 错误文本同样是结果文本
//   provider->callTool("read_file", args.c_str(), &content, &cb);

#pragma once
#include <cstddef>
#include "CLFPluginApi/CLFPluginApi.hpp"

namespace CLF::CLFPluginApi {

// ============================================================================
// 工具元数据（POD，跨边界安全）
// ============================================================================

// 能力标签位集（阶段 1 B1 的 m_isSearch/m_isRead 映射至此；写/命令分类不经标签——
// CLFToolRisk 即能力声明，B1 设计简化）
enum CLFToolFlags : int {
    ToolFlagNone   = 0,
    ToolFlagSearch = 1 << 0,   // 计入 searchCount 桶（search_content）
    ToolFlagRead   = 1 << 1,   // 计入 readCount/progressReads 桶（read_file / list_directory）
};

// 与进程内 CLFTool 字段一一对应；字符串生命周期 = 插件加载期间（宿主只读不持有）
struct CLFToolMetaPOD {
    const char* name;              // 工具名（全局唯一，管理器装配时查重）
    const char* description;
    const char* parametersSchema;  // JSON Schema 字符串
    int risk;                      // CLFToolRisk 编码（0=Read 1=Write 2=Command）
    int flags;                     // CLFToolFlags 位集
    int concludesTurn;             // 0/1（A5 先例；仅 handler 成功路径生效）
};

// ============================================================================
// 调用回调（宿主提供，经 callTool 参数传入）
// ============================================================================

struct CLFToolCallbacks {
    // 结果文本（成功路径；UTF-8，调用期间有效）。宿主负责走 formatToolResult
    void (*onResult)(void* ctx, const char* content, size_t len) = nullptr;
    // 错误文本（失败/异常被兜底；同样作为结果文本交给 formatToolResult）；
    // 实现侧调用前判空（可为 null）
    void (*onError)(void* ctx, const char* msg) = nullptr;
};

// ============================================================================
// 工具提供者（工具插件对宿主暴露的领域接口）
// ============================================================================

class ICLFToolProvider : public CLFService {
public:
    virtual ~ICLFToolProvider() = default;

    virtual int toolCount() const = 0;

    // index ∈ [0, toolCount())；返回指针由插件持有，生命周期 = 插件加载期间
    virtual const CLFToolMetaPOD* toolMeta(int index) const = 0;

    // 调用：argsJson 进，结果经 cb 出；返回 false = 调用未完成（onError 已推文本）
    virtual bool callTool(const char* name, const char* argsJson,
                          void* ctx, const CLFToolCallbacks* cb) = 0;
};

} // namespace CLF::CLFPluginApi
```

**为什么不做进度回调**：现有 9 个 handler 均为同步返回，无进度通道——执行期 UI 进度由宿主侧（`CLFToolExecutor` 的状态行 / `ProgressGuard`）负责，与 handler 无关。加 `onProgress` 属无源之功能（YAGNI），且会引入"插件主动推 UI"的越界依赖。

**`risk` / `flags` 的类型**：用 `int` 而非枚举，避免枚举底层类型跨编译器差异；语义由枚举常量表达，宿主侧 `static_cast<CLFToolRisk>` 转回（枚举序一致由 qa 钉死）。

### 1.4 服务命名契约（宿主侧约定，插件按此声明）

| 服务名 | 接口 | 提供方 | 消费方 |
|---|---|---|---|
| `tool.provider` | `ICLFToolProvider` | 每个工具域 DLL | 管理器（2.2b 装配工具注册表） |
| `file` | `ICLFFileService` | `tools.fileops`（2.2a） | `CLFToolExecutor`（C1 已接口化，试点零改动） |

> 命名规则：小写下划线、单数、**不前缀插件 ID**（服务名是宿主契约，插件 ID 是提供方身份——同一服务将来可换实现，符合 SDP）。

### 1.5 约束对照表（逐条自查）

| §3.1 硬约束 | 本设计落点 |
|---|---|
| C 工厂符号 + 纯虚接口 | §1.2 两个 typedef + 插件导出样板 |
| 跨边界禁传 STL | 全部参数/返回为 `const char*` / `size_t` / `int` / POD |
| 跨边界禁异常逸出 | `init/shutdown/callTool` 返回 bool + `onError` 文本通道 |
| **跨边界禁 RTTI**（本步补充） | `services()` 显式服务表替代 `dynamic_cast`；`static_cast` 仅用于单继承链 downcast |
| 接口版本化 | `CLF_PLUGIN_API_VERSION` + `hostApiVersion()` 精确匹配 |
| 内存归属：谁分配谁释放 | 字符串由返回方持有（调用期有效）；`alloc/free` 作所有权转移通道 |
| 接口头禁依赖 | §1.1 精确化（禁 `CLFPluginApi/` 之外） |
| 导出符号跨编译器 | `CLF_PLUGIN_EXPORT` 宏（§1.2；与禁 RTTI 同一论证——MSVC/GCC 双构建链对称） |
| 裸指针限于 ABI 边界 | 跨 DLL 禁 STL 的必然——全部非拥有、生命周期由管理器/提供方保证；与全局规范"尽可能避免裸指针"对齐为**有意的例外**，仅限 `CLFPluginApi/` 内 |

**版本匹配用精确相等而非范围**的取舍：范围匹配需要 `min/max` 双字段 + 半兼容语义（"v2 宿主能跑 v1 插件"需逐接口论证），当前 ABI 无此需求；精确匹配的失败模式最清晰（拒绝加载 + 提示重建），且不排除将来加 `minCompatibleApiVersion()` 字段扩展。

**禁 RTTI 的理由**：项目 CMake 同时支持 MSVC 与 GCC/Clang 构建路径；跨 DLL 的 `dynamic_cast` 在 GCC/MinGW 下依赖类型名字符串比较，编译选项不一致时静默失败——属"跨边界最小假设"应排除的机制。显式服务表零 RTTI、零开销、失败可诊断。

## 三、CLFPluginManager 骨架设计

> 定位：**core 内建**（§七② core 不迁 DLL），管理器头**不进入** `CLFPluginApi/`（插件不可见管理器类型）。

### 3.1 类接口

```cpp
// src/CLFCore/CLFPluginManager.hpp
namespace CLF::CLFCore {

class CLFPluginManager {
public:
    // pluginDir 缺省 = exe 目录/plugins（测试可注入临时目录）
    explicit CLFPluginManager(std::string pluginDir = "");
    ~CLFPluginManager();

    CLFPluginManager(const CLFPluginManager&)            = delete;
    CLFPluginManager& operator=(const CLFPluginManager&) = delete;  // 持 DLL 句柄，禁拷贝

    // 发现 → 元数据 → 依赖图 → 拓扑加载。
    // 返回成功加载数；单个插件失败（版本不符/init 失败/缺依赖）→ 标记禁用，不阻断其余
    int  loadAll();

    bool load(const std::string& pluginName);
    bool unload(const std::string& pluginName);   // quiesce 前提由调用方保证（§3.3）
    bool reload(const std::string& pluginName);

    std::vector<std::string> listPluginNames() const;

    // 服务路由（插件与宿主共用；不存在 → nullptr）；按服务名（审查修订 2026-09-11，同 §1.2）
    CLF::CLFPluginApi::CLFService* getService(const char* service) const;

    // 工具提供者汇总（2.2b 装配用；仅返回已加载且提供 tool.provider 的插件）
    std::vector<CLF::CLFPluginApi::ICLFToolProvider*> toolProviders() const;

    // 宿主 API（传给插件的注入面；由 CLFHostApiImpl 实现，见 §3.4）
    CLF::CLFPluginApi::CLFHostApi* hostApi() const;

private:
    struct PluginRecord;                    // 定义在 .cpp（handle/plugin/instance/enabled/error）
    std::vector<std::unique_ptr<PluginRecord>> m_plugins;
    std::unique_ptr<CLFHostApiImpl>            m_hostApi;
    std::string                                m_pluginDir;
};

} // namespace CLF::CLFCore
```

**`unload` 的 quiesce 语义**（§3.3 定案）：管理器**不自行判断**"有无在途调用"（它没有这个信息），由调用方（`/plugin` 命令，2.2c）在 agent 空闲/回合边界发起；管理器只做"通知依赖方 → shutdown → FreeLibrary"。**对话中调用 = 调用方责任**。

### 3.2 加载流程（`loadAll` 状态机）

```
1. 扫描 m_pluginDir 下 *.dll——**【审查说明 2026-09-11】按文件名字典序排序后处理**：
   `directory_iterator` 枚举顺序无保证（跨机器/复制后可变），排序是"多提供方取首个"与日志可复现的前提
   （无目录 → 返回 0，静默降级）
2. 逐个 LoadLibraryW → GetProcAddress("CLFPluginCreate"/"CLFPluginDestroy")
   ├─ 缺符号 → FreeLibrary + 标记禁用（原因："非插件 DLL"）
   └─ 创建实例 → 读 name/version/hostApiVersion/requires/services
3. 版本闸门：plugin->hostApiVersion() != host->apiVersion()
   → CLFPluginDestroy + FreeLibrary + 标记禁用（原因："ABI 版本不符，请重建插件"）
4. 依赖图：requires() 服务名 → 服务名索引（谁 services() 里声明了它）
   ├─ 缺提供方 → 标记禁用（原因："缺依赖服务 X"）
   ├─ 检出环 → 环上全部标记禁用（原因："依赖环"）
   └─ 拓扑排序 → 加载序
   **多提供方歧义规则**（§3.3 允许重复声明，规则须写死）：requires 解析取**文件名字典序排序后首个**提供方 + warn 记录多提供方（审查修订 2026-09-11：原"扫描序"依赖目录枚举顺序，不可复现）
5. 按序 init()：失败 → 标记禁用（其余继续；§3.2 隔离兜底）
6. 成功插件：services() 表逐个入注册表 (pluginId, serviceName) → CLFService*
7. 全程日志：每个插件的加载/禁用结果（CLFLogger::info/warn）
```

> **第 4 步的"服务名索引"需两遍扫描**：先收集全部插件的 `services()` 名，再解析 `requires()`。缺失提供方与环检测在此阶段完成——**均不阻断其余插件的加载**（§3.2"单插件失败不影响其余"）。

**两个必须写进实现的要点**：

1. **版本闸门的固有次序风险**（先有鸡还是先有蛋）：版本检查发生在 `CLFPluginCreate` **之后**（必须先构造实例才能问版本），若插件以极不兼容的 ABI 编译，`Create` 调用本身即可能失败——**无法完全规避**。缓解设计：工厂签名极简（只接一个指针），破坏性变更概率低；版本闸门与 `init()` 之间不调用插件任何其他方法，把风险面收窄到"构造"一步。**此风险如实记录，不假装闸门能防住一切。**

   **可选加固（设计审查 2026-09-11）**：MSVC 下用 SEH（`__try` / `__except`）包住 `CLFPluginCreate` 调用，
   把"构造期崩溃"降级为该插件禁用而非进程崩溃；跨平台有差异（GCC 无 SEH），是否采纳由 pro 评估。
2. **卸载顺序（经典陷阱）**：`CLFPluginDestroy(plugin)` **必须**在 `FreeLibrary(handle)` **之前**调用——函数指针指向 DLL 代码段，先卸库再调用 = 立即崩溃。顺序：`shutdown()` → `CLFPluginDestroy()` → `FreeLibrary()`。

### 3.3 服务注册表

| 操作 | 语义 |
|---|---|
| 写入 | 加载成功后由管理器从 `services()` 收集；`(pluginId, serviceName)` 唯一键 |
| 查询 | `getService(service)`（按服务名；审查修订 2026-09-11）：未命中返回 `nullptr`；**多提供方时取文件名字典序排序后首个**（与 §3.2 步骤 4 的 requires 解析同一索引、同一规则——补 2026-09-11 pro 拍板） |
| 冲突 | 同 `(pluginId, serviceName)` 重复声明 → 后项覆盖 + warn 日志（插件自治，不做跨插件服务独占校验） |
| 停用 | `unload` 时该插件的全部服务项移除 → 后续查询返回 `nullptr`（**调用方自兜底**，§3.1） |
| reload 失败语义 | reload = unload + load；新插件失败（ABI 不符 / init 失败）→ **旧插件已卸载、服务已消失**，调用方自兜底。不做"失败回滚旧实例"——回滚需重载 DLL 且掩盖根本原因 |

**"插件停用后模型再调工具"链路**（§3.6 兜底）：`getService` → `nullptr` → `CLFToolExecutor` 走既有失败路径（"Tool not found" / 错误文本回传模型）→ 模型自兜底。**2.2a/2.2b 需验证此链路**，2.1 只验证 `getService` 返回 `nullptr`。

### 3.4 CLFHostApiImpl（宿主 API 实现）

```cpp
// src/CLFCore/CLFHostApiImpl.hpp（core 内建，不进 clf_plugin_api）
namespace CLF::CLFCore {

class CLFHostApiImpl : public CLF::CLFPluginApi::CLFHostApi {
public:
    explicit CLFHostApiImpl(CLFPluginManager* manager);   // 服务查询回指管理器

    uint32_t apiVersion() const override;                 // 返回 CLF_PLUGIN_API_VERSION
    void     log(int level, const char* msg) const override;   // → CLFLogger 四级别
    const char* config(const char* pluginId, const char* key) const override;
    CLF::CLFPluginApi::CLFService* getService(const char* service) const override;
    void* alloc(size_t size) const override;              // → malloc
    void  free(void* ptr) const override;                 // → free

private:
    CLFPluginManager* m_manager;                  // 非拥有（管理器持有本对象）
    mutable std::map<std::string, std::string> m_configCache;  // config 返回值载体：按 key 缓存（同 key 再调用才覆写，见下）
};

} // namespace CLF::CLFCore
```

**`config()` 的返回值生命周期**（本设计的实现要点）：ABI 约定返回值"调用期间有效"。实现建议：`m_configCache` 用 `mutable std::map<std::string, std::string>` **按 key 缓存**（同 key 再调用才覆写）——插件 init() 里连续取多个 key 并暂存指针时，各指针保持有效；比单 string 每次覆写显著降低插件作者踩坑面，代价可忽略。**宿主侧调用方（插件）仍须在返回后尽快复制**（头注释声明义务不变）。

**`config()` 的数据源**（2.1 阶段）：读 `config/plugins/<pluginId>.json`（修正②），懒加载 + 缓存（按 pluginId 分文件）；key 未命中或文件缺失 → `nullptr`（插件用内置默认）。**配置文件的加载器不属本步**——2.1 先落 `nullptr` 骨架 + TODO 注释，2.2a 接真实现。

> **说明**：`CLFHostApiImpl` 与 `CLFPluginManager` 是**双向引用**（host 持 manager 指针查服务；manager 持 host 对象传给插件）——非所有权环（双方均为非拥有指针），构造顺序：manager 先构造 → 自建 host → 传入。

### 3.5 错误处理与兜底

| 场景 | 行为 |
|---|---|
| 插件目录不存在 | `loadAll` 返回 0，info 日志（正常：无插件 = 全静态构建） |
| DLL 非插件（缺符号） | 跳过 + warn；不影响其余 |
| ABI 版本不符 | 拒绝加载 + 明确原因（"请重建插件"）；**不尝试兼容** |
| 依赖缺失 / 环 | 相关插件禁用 + 原因；其余照常 |
| `init()` 失败 | 该插件禁用；已加载插件不受影响 |
| 插件调用中抛异常 | **宿主不吞跨边界异常**——由插件实现侧 try/catch 转 `onError`（§七⑨ 务实方案：每插件自兜底） |
| `getService` 未命中 | `nullptr` → 调用方自兜底（既有失败路径） |

### 4.1 插件 target 模板（写入 `src/CMakeLists.txt`）

```cmake
# ============================================================================
# 插件 target 模板（阶段 2 §3.5；2.1 建立，2.2a 首个使用）
# 约定：一个 DLL = 一个能力域；只导出工厂 C 符号；与主程序同一编译链与运行时
# ============================================================================
function(clf_add_plugin TARGET_NAME OUTPUT_BASENAME)
    # 用法：clf_add_plugin(clf_plugin_fileops tools.fileops ${PLUGIN_SOURCES})
    cmake_parse_arguments(ARG "" "" "SOURCES;LIBS" ${ARGN})
    add_library(${TARGET_NAME} SHARED ${ARG_SOURCES})
    target_link_libraries(${TARGET_NAME} PRIVATE clf_plugin_api ${ARG_LIBS})
    set_target_properties(${TARGET_NAME} PROPERTIES
        PREFIX ""                                              # 无 lib 前缀
        OUTPUT_NAME "${OUTPUT_BASENAME}"                       # tools.fileops.dll
        MSVC_RUNTIME_LIBRARY "MultiThreadedDLL"                # /MD 硬约束（§3.5）
        RUNTIME_OUTPUT_DIRECTORY "${CMAKE_SOURCE_DIR}/bin/$<CONFIG>/plugins"   # .dll
        ARCHIVE_OUTPUT_DIRECTORY "${CMAKE_SOURCE_DIR}/lib/$<CONFIG>/plugins"   # 导入库
    )
endfunction()
```

**要点**：
- `add_library(... SHARED)` = DLL；**不设** `WINDOWS_EXPORT_ALL_SYMBOLS`（只导出工厂符号，由源码 `__declspec(dllexport)` 控制）
- `MSVC_RUNTIME_LIBRARY` 显式钉死 `/MD`（§3.5"统一运行时"——不依赖 CMake 默认值）
- `.dll` 落 `bin/$<CONFIG>/plugins/`（修正④），导入库落 `lib/$<CONFIG>/plugins/`
- 插件**不**链 `clf_core`（避免把宿主实现拖进 DLL）；只链它需要的：本轮 FileOps 插件链 `clf_types`（basic 共享头）
