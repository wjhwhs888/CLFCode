## 一、背景与目标

### 1.1 问题

当前会话保存是**覆盖式**：每轮 turn 结束把全部 messages 序列化覆盖写 `latest.json`（`CLFRepl.cpp:910` → `CLFSessionManager::save` 覆盖模式），/exit 时归档。后果：

- **中间过程不保留**：只有最后一次保存的最终态，每轮演化、todo 状态变化、时间点全丢
- **无法定位"任务清单属于哪轮对话"**：`todos` 只有一份当前快照，没有轮次/时间归属
- **/resume 后只能看到"最后一次"的清单状态**，看不到"第 2 轮对话完成时"的清单完成情况

### 1.2 实证：Claude Code 怎么做的

对用户本机 Claude Code 会话文件（`~/.claude/projects/<项目分片>/<sessionId>.jsonl`，v2.1.241）实证：

- 工具面是 **`TaskCreate`（追加，id 自增）/ `TaskUpdate`（单项改状态）**，不是整表替换
- 系统**周期性注入 `task_reminder` 附件消息**：`{"attachment":{"type":"task_reminder","content":[完整清单快照],"itemCount":N}}`，带独立 uuid + timestamp，穿插在消息流中（实证会话 49 条）
- 恢复 = 按 jsonl 行序回放 → **快照位置即归属**，演化史完整（5项→6项→13项每步可见）

### 1.3 定案（用户决策，2026-08-25）

**🔒 最高优先级原则（用户定，2026-08-25）**：**UI 显示只是显示，供用户查看，绝不能影响具体工作**——显示优先级最低、随时可调整；数据层（`m_todos`、todo_write、本 jsonl 持久化）是"工作"的根基，稳定且不受显示层任何决定影响。显示层只读 `m_todos`，单向依赖；显示动作（emit/置位）失败不得影响数据落盘与 `runTurn` 返回（详见另案 `设计-任务清单UI显示.md` §一）。

**🏗️ 生产/消费分离（用户定，2026-08-25）**：数据层（本 jsonl 持久化）是**生产者**，对外提供 SessionManager / codec 接口，不含任何渲染代码；UI 层是**消费者**，只读接口消费。换 UI 只需实现 `ICLFOutput` + 消费 jsonl 接口，数据层零改动（详见另案 §一）。

借鉴 Claude Code 的**追加式过程记录**，但按 CLFCode 实际需求**简化**：

- ✅ **改成追加式 jsonl**（一个会话一个文件，不引入多文件）
- ✅ **每轮 turn 结束追加一行**：本轮新增消息 + **轮末 todo 清单快照**（本轮操作过清单才带）
- ✅ **不要中间演化过程**（不做逐次 TaskUpdate 级留痕）——用户明确"不需要中间过程，只需要知道这次对话完成的任务有哪些"
- ✅ **模型总结 = messages 里的 assistant 文本**，天然随消息保存，不需额外处理
- ✅ **resume 回显 = 完整思考过程 + 模型总结 + 每轮清单完成状态**

## 三、设计

### 3.1 文件形态

**一个会话一个 `.jsonl` 文件**，追加写入：

```
会话文件：  doc/contextHistory/<时间戳>_<标题>.jsonl
```

- **无 `latest.jsonl`、无改名归档**（用户定案 2026-08-25）：每个会话文件**创建即定名**，从头到尾名字不变；`/exit` 只是正常关闭，不做任何搬移
- **文件在"第一条新对话输入"时才创建**（懒创建，见 §3.3）——无对话则不产生文件
- **不产生多文件**（用户明确要求）
- 旧 `latest.json` 归档文件**仍可读**（兼容，见 §3.5）；旧归档保留不动

### 3.2 行结构

**第 1 行：header**（会话元数据，文件创建时写一次）

```json
{"type":"header","version":1,"title":"...","started_at":"2026-08-25_09-20-53","session_id":"...","model":"deepseek-v4-flash"}
```

- `session_id`：**新增字段**（现代码无 uuid，`CLFMessageCodec::serialize` 只有 version/messageCount/saved_at/title）。生成方式建议时间戳+短随机串（如 `20260825_092053_a3f9`），用于文件自我标识与未来多会话（S4 项）区分；**定位仍以文件名时间戳 + 行 ts 为主**，session_id 不承担关键定位职责

**第 2..N 行：四类行——`turn`（轮末完整）+ `todo_snapshot`（清单变化即时）+ `complete`（全完成收尾）+ `summary`（会话摘要，/clear 或 S3 自动触发）**

**turn 行：每轮 turn 结束追加一行**（本轮完整消息 + 轮末清单快照）

```json
{"type":"turn","ts":"2026-08-25_09-25-00","messages":[{"role":"user","content":"..."},{"role":"assistant","content":"...","tool_calls":[...]},...],"todos":[{"id":"1","content":"分析项目情况","status":"completed"},...]}
```

- `messages`：**本轮新增**的消息数组（user + assistant + tool，全量字段照现有序列化）
- `todos`：**轮末清单快照**——**仅当本轮内 agent 操作过 todo_write（create/update/clear 任一）才带**；否则省略该字段
  - 判定：`CLFAgentLoop` 加 `m_todoDirty` 标志——**仅 create/update/clear 置位，`list` 不置位**（list 不改数据，快照无意义，见另案 §6.4-D）；轮末读取并清除
- `ts`：轮末时间戳（复用 `timestampStr()`，`CLFSessionManager.cpp:21-32`）

**todo_snapshot 行：每次 `todo_write` 修改清单（create/update/clear）后立即追加一行**（用户定案 2026-08-25——防崩溃丢清单进度）

```json
{"type":"todo_snapshot","ts":"2026-08-25_09-24-37","todos":[{"id":"1","content":"分析项目情况","status":"completed"},{"id":"2","content":"查看语言特性","status":"in_progress"},...]}
```

- 触发：`todo_write` handler **每次成功修改 `m_todos` 后**（create/update/clear）立即调 `agent.appendTodoSnapshotNow()` 追加 + flush，**不等轮末**（接口契约见 §3.9，2026-09-02 定案）
- **目的**：崩溃时清单进度保留到最近一次 update——解决"1-5 同轮建 + 执行到第 4 步崩溃 → 清单结构+进度全丢"的最坏场景（对齐 dsh 事件流：`tool-todo` 每次 `todo/write` 即 `session.append`，`index.ts:210`）
- `list` 不触发（不改数据）

**complete 行：全完成收尾时追加一行**（用户定案 2026-08-25——收尾记录持久化，resume 后历史可见）

```json
{"type":"complete","ts":"2026-08-25_09-30-12","todos":[{"id":"1","content":"分析项目情况","status":"completed"},...]}
```

- 触发：`runTurn` 完成分支 T6（另案 `设计-任务清单UI显示.md` §3.7）——检测 **`全 completed && !m_todoPanelDone`**（**无 m_todoDirty**，另案 §八 补丁 5）时，**数据动作优先**：① 写 complete 行 + flush（`CLFSessionManager::appendComplete(m_activeSessionFile, todos)`，无活动文件则跳过，数据层先保证落盘）→ ② UI 侧 emit 清单行到对话流（显示，try/catch）→ ③ 置 `m_todoPanelDone`（显示，try/catch）。职责分离：complete 行由数据层接口写入，emit/置位由 UI 侧执行（§一 生产/消费分离）
- **目的**：解决"T6 已 emit 但 `m_todoPanelDone` 未置位就崩溃 → resume 后折叠块看不到收尾记录"的缺口（§6 边界 5）——complete 行持久化，resume 回显时可见"任务全部完成"

**summary 行：会话摘要（2026-09-02 审查补入——原设计移除 /exit 的 generateAndCacheSummary 后，摘要机制与 S3 排期出现衔接断点）**

```json
{"type":"summary","ts":"2026-08-25_09-28-00","summary":{"text":"...","method":"rule_based","current_plan":"...","key_decisions":[...],"files_modified":[...],"pending_tasks":[...]}}
```

- 触发：`/clear` 时（`generateAndCacheSummary()` 后追加；**`/exit` 保持纯退出不生成**）；S3 摘要自动触发落地后同样追加此类型行，**行格式已预留，S3 无需改格式**
- 恢复：loadJsonl 逐行解析时记"最后一条可解析的 summary 行"，`restoreSession` 注入 system 消息（复用现有 `CLFAgentLoop.cpp:492-494` 路径）
- 旧 .json 的 summary 字段解析不变（兼容路径）；jsonl 会话的摘要一律走 summary 行

**恢复时 m_todos 的取值优先级**：**最后一条 `todo_snapshot` 行的 todos**（比 turn 行的轮末快照更新——本轮内的中间进度也保留）。若文件里只有 turn 行（旧版/未用 todo）→ 取最后一个带 todos 的 turn 行。

### 3.3 写入时机（文件生命周期）

**核心规则：文件在"第一条新对话输入"时才创建**——懒创建，无对话则不产生文件。

**当前会话文件指针**：`CLFAgentLoop` 持有 `m_activeSessionFile`（可为空，§3.9 契约），内存态即可（用户确认：不落额外状态文件）。**懒创建下启动时无需扫描目录**——第一条输入才建文件，启动时 `m_activeSessionFile` 为空，无文件指针推断需求（`/resume` 列表另走 `CLFSessionManager::list`，与 m_activeSessionFile 无关）。

| 事件 | m_activeSessionFile | 文件动作 |
|---|---|---|
| 程序启动 | 空（null） | 无文件 |
| `/resume 1`（仅查看） | 空（记 `m_resumedFrom=1`） | **不建文件**（懒复制，零副作用） |
| resume 后 `/clear` | 空，清 `m_resumedFrom` | 无（从未建文件，无残留） |
| **resume 后输入新对话** | `beginSessionFile` 建新文件 `时间戳_会话1续.jsonl`，**随后清 `m_resumedFrom`**（生命周期定案，另案 §八 补丁 4） | header + 会话1 全部行副本（turn + todo_snapshot + complete + summary，§3.9 契约）+ 本轮追加 |
| 正常启动后第一条输入 | `beginSessionFile` 建新文件 `时间戳_标题.jsonl` | header + 本轮追加 |
| **todo_write 修改清单（create/update/clear）** | 不变 | handler 调 `agent.appendTodoSnapshotNow()`：**立即追加 `{"type":"todo_snapshot",...}` + flush**（不等轮末，防崩溃丢进度） |
| 每轮 turn 结束 | 不变 | `appendTurnLine()` 追加一行 `{"type":"turn",...}`（随时存盘） |
| 正常对话中 `/clear` | 先追加 summary 行（`generateAndCacheSummary()` 后，§3.2）→ 关闭当前文件（保留），置空 | 旧文件保留为独立会话 |
| `/exit` | 正常关闭（置空） | **无改名、无归档、无搬移**（不再生成摘要，摘要改由 /clear 触发） |
| 崩溃/杀进程 | — | 文件停在最后已 flush 的行（turn 或 todo_snapshot）；**不触发任何改名** |

**追加写入**：`std::ofstream` 以 `ios::app` 打开（照 `CLFLogger.cpp:102` 的既有模式），每行写完 flush。

> ⚠️ **保存 = 随时即时追加（每轮 turn + 每次清单变化）；`/exit` 只是正常结束，不承担保存/归档职责**。
> 崩溃/断电/杀进程时：**已完成轮次的 turn 行 + 已发生的 todo_snapshot 行已在文件中**（每行写完即 flush）。丢失范围：
> - 当前轮未落盘的**消息**（本轮对话/工具调用，turn 行未写）——最多丢当前轮消息
> - **清单进度不丢**（每次 update 已即时写 todo_snapshot）——解决"1-5 同轮执行到第 4 步崩溃"最坏场景
> 崩溃残留文件原样保留，下次启动不自动续、不污染新会话。

### 3.4 恢复（resume）

#### 3.4.1 resume = 查看与续写分离（懒复制，用户定案 2026-08-25）

**resume 是"查看"动作，默认不产生任何文件副作用**；只有 resume 后**输入第一条新对话**（真正续写）才触发复制。

```
/resume 1（仅查看）：
  加载 会话1 全部内容到 context + 回显
  m_resumedFrom = 会话1文件路径，m_activeSessionFile = 空    （不建文件、不复制）

  ├─ 用户 /clear → 清空 context，清 m_resumedFrom
  │                 → 无任何文件副作用，干净 ✅
  │
  └─ 用户输入新对话（续写）→ 触发复制：
      ① 会话1 原始归档    → 保留不动（冻结的历史快照）
      ② 建新文件 时间戳_会话1续.jsonl：
         header
         + 会话1 全部行原样复制（turn + todo_snapshot + complete + summary，§3.9 契约）
         + 本轮 turn 行
      ③ 之后每轮续写追加（每轮即时落盘）
      m_activeSessionFile = 新文件；m_resumedFrom 清除
```

**为什么懒复制**（用户理由）：resume 查看后很可能 `/clear` 开新对话——若 resume 时立即复制，会把这些内容污染进新会话。只有"真的续写"才复制，保持清洁。

**要点**：

- **两份会话1 记录的分工**：原始归档 = 冻结快照（"resume 前那一刻"）；延续会话里的副本 = 活跃起点（会继续长）
- **todo 状态延续**：延续会话的初始 `m_todos` = 会话1 **恢复取值优先级的结果**（最后 todo_snapshot > 最后带 todos 的 turn 行，§3.4.2 步骤 4），续写时清单状态无缝衔接
- **resume 延续会话**（如 resume 6）= 看到会话1 完整历史 + 续写内容，是完整对话
- **心智模型统一**：每个文件 = 一个时间段的会话；resume = 从某个快照续开新的时间段；查看 ≠ 续写（后者才产生文件）
- **崩溃语义自然**：文件里有什么就 resume 显示什么——turn6 崩溃未写入，resume 显示 turn1-5，turn6 不存在（非"丢失"，是"从未写入"），无歧义

**`m_resumedFrom` 生命周期（定案，2026-09-02，另案 §八 补丁 4/5）**：置位 = `restoreSession` 内部（恢复即进入续写态）；清除 = ① `/clear` ② `beginSessionFile` 建续写文件后。续写会话的**第 2 轮及以后输入按普通语义**（新回合清面板，另案 §3.3）——清单数据仍留 `m_todos` 与 jsonl 历史，模型可 `list` 查看，语义自洽。若永远不清除，续写会话将永远不清面板，与"每回合清空"矛盾。

#### 3.4.2 restoreSession 实现

`restoreSession(filePath)` 改为：

1. 若文件是 `.jsonl` → 逐行读：
   - header 行：解析元数据（title/session_id/model）
   - `turn` 行：**messages 全部并入 context**（与现有 `:484-488` 一致，跳过 system）；**todos 快照**（若带）记为"该轮清单状态"
   - `todo_snapshot` 行：**记为最新清单状态**（覆盖之前的值——它比 turn 行更新，含本轮中间进度）
   - `complete` 行：仅用于回显（§3.6 折叠块收尾行），不参与 m_todos 恢复
   - `summary` 行：**记为最新摘要**（覆盖之前的值，取最后一条可解析的）——恢复后注入 system 消息（复用 `CLFAgentLoop.cpp:492-494` 路径）
2. 若文件是旧 `.json` → 走现有 `parseFull` 路径（兼容）
3. 回显（`CLFAgentLoop.cpp:463-482` 改造）：
   - 现有折叠块逻辑保留（user/assistant 全量文本）
   - **新增**：每轮 turn 行尾，若该行带 `todos` 快照 → 追加一行清单状态（见 §3.6 显示格式）
4. **`m_todos` 恢复取值优先级**：**最后一条可解析的 `todo_snapshot` 行的 todos**（撕裂/损坏行跳过，取之前最近一条——崩溃时进度可能回退一格，但比全丢强，§6）；若文件无 todo_snapshot → 最后一个带 todos 的 turn 行（旧版/未用 todo 兼容）（与现有 `:451` 对齐）
5. **不建文件、不复制**（懒复制：续写文件由"第一条新输入"触发，见 §3.4.1）

> **与实时任务面板的衔接**（跨文档，另案 `设计-任务清单UI显示.md` §3.7/§3.3）：resume 后**面板显示 = `m_todos`（= 恢复取值优先级的结果：最后 todo_snapshot > 最后带 todos 的 turn 行，见步骤 4）**——这是"继续做"的起点，不是普通新回合，**面板应显示**（用户定案 2026-08-25）：
> - 最后快照**非全完成** → 任务面板重现（未完成项可见，作为续写起点；**同时清 `m_todoPanelDone`**，§6.4-B）
> - 最后快照**全部已完成**（收尾语义）→ 任务面板**不显示**（置 `m_todoPanelDone`；完成记录已在对话流历史里，避免重现一个已完成清单）
> - **resume 续写期间不清空面板**（§6.4-E）：第一条续写输入是"继续做"，面板保留（用户问"2 3 怎么回事"时可见），直到模型 create 新清单 / 全完成 / clear 才变化——区分依据 `m_resumedFrom` 非空
> - **折叠块与面板分工**：折叠块 = 每轮各自的历史快照（1/3 → 3/3 演进可见，§3.6）；面板 = 当前（最后一轮快照）——"过去"与"现在"分离

> 注：续写触发点 = `CLFRepl::submit` 检测 `m_agent.getActiveSessionFile()` 为空（且非命令输入）时，调 `m_agent.beginSessionFile(input)` 按 §3.4.1 建文件：内部判定 `m_resumedFrom` 非空 → header + 副本 + 本轮（随后清 `m_resumedFrom`）；否则 → header + 本轮。具体接线见 §3.9 调用点总表与 §4.1 J4/J5。

### 3.6 resume 显示格式

```
● 会话已恢复 · 12 条消息（ctrl+r 展开）

> 对话1：帮我查看项目进度
AI: （总结项目情况…）

> 对话2：按照某某继续
AI: （逐步执行…）
  📋 本轮清单 1/3：✓ 分析项目情况 · ⏳ 查看语言特性 · ○ 提交状态

> 对话3：本地验证通过，提交推送吧
AI: （提交推送…）
  📋 本轮清单 3/3：✓ 分析项目情况 · ✓ 查看语言特性 · ✓ 提交状态
```

- **折叠块内**（`showFoldedBlock`）：消息文本照旧逐条
- **每轮清单状态**：该轮带 todos 快照时，折叠块内该轮末尾追加一行清单摘要
  - 格式：`📋 本轮清单 n/total：✓ 内容 · ⏳ 内容 · ○ 内容`（completed=✓绿 / in_progress=⏳高亮 / pending=○灰，复用任务面板的颜色语义）
  - **该轮未操作清单 → 不显示**（用户明确："这次对话没有就不列出"）
- **complete 行回显**：`{"type":"complete",...}` → 折叠块内追加一行 `📋 任务清单（全部完成）: ✓ A · ✓ B · ✓ C`（与运行中 T6 追加的对话流格式一致，§3.2 complete 行）——崩溃在 T6 后时，resume 仍能看到收尾记录
- 模型总结（若有）就是 assistant 消息文本，天然在折叠块里，**无需额外处理**

### 3.7 与实时任务面板的关系

- 实时任务面板（另案 `设计-任务清单UI显示.md`）显示**当前** `m_todos`——进行中的活状态
- jsonl 轮末快照是**历史**——resume 时回放"每轮完成情况"
- 两者数据同源（`m_todos`），互不冲突：面板管"现在"，jsonl 管"过去"

### 3.8 线程安全（2026-09-02 核实定案，另案 §八 补丁 1）

**线程模型基准**：`CLFAsyncSubmit` 单工作线程串行执行（`launch` 前 `join()`，`CLFAsyncSubmit.cpp:12-27`）——submit/命令分发/runTurn/todo_write handler/**所有 jsonl 追加（todo_snapshot/turn/complete/summary）全部同线程串行**，写路径**无并发**。UI 主线程只读（渲染）。

- `m_todos` 加锁方案照 `设计-任务清单UI显示.md` §3.9（`mutable std::mutex` + `getTodos()` 返回副本）——真跨线程边界（工作线程写 ↔ 渲染读）
- `m_todoDirty` 用 `std::atomic<bool>`（handler 置位、`appendTurnLine` 读取清除——全在工作线程，atomic 为防御性）
- **文件写入互斥（防御性）**：`CLFSessionManager` 的 `append*` 方法统一加 **static `std::mutex`**——当前接线串行不依赖此锁，但照 CLFLogger 惯例（mutex + ios::app + flush 三件套，`CLFLogger.cpp:70`）防未来并发调用方（如 S3 摘要自动触发若移到其他线程）。**每个 append 方法：锁 → 打开 `ios::app` → 写 → flush → 关闭**（每次独立打开，不缓存共享流对象）

### 3.9 会话文件上下文 API 契约（2026-09-02 定案，接线层的核心接口）

> 原 J3 的"（回调/注入）"三字在此展开为具体接口——todo_write handler（只有 agent 引用）与 runTurn 完成分支（AgentLoop 内部）写 jsonl 都需要会话文件路径，而 AgentLoop 目前不持有 historyDir（现状 `saveSession(dirPath)` 由 Repl 每轮传参，`CLFAgentLoop.cpp:414`）。

**CLFAgentLoop 新增成员与接口**：

```cpp

//   锁内取 todos 快照 → serializeTodoSnapshot → SessionManager::appendTodoSnapshot → 失败 warn 不抛

void        markTodosDirty();                    // create/update/clear 置位（list 不调）
```

## 五、人工验收清单

1. 新建会话 → 输入第一条对话 → 确认生成 `时间戳_标题.jsonl`，首行为 header
2. 对话1（无清单）→ 结束追加一行 turn（无 todos 字段）
3. 对话2（建清单逐步完成）→ **每次 update 即时追加 todo_snapshot 行**；结束追加 turn 行（带轮末 todos 快照）
4. 对话3（提交推送，无清单操作）→ 结束追加一行 turn（无 todos 字段，但消息全量）
5. 中途查看当前会话文件：turn 行 + todo_snapshot 行交错，时间戳递增、行序 = 发生顺序
6. `/exit` → 正常退出，**无改名、无归档**——当前会话文件名字从头到尾不变
7. 重启 + `/resume` 归档会话 → 折叠块内：完整消息 + 每轮清单状态行（对话2有、对话1/3无）
8. resume 后清单状态 = **最后一条 todo_snapshot**（若只 update 未到轮末，取它而非 turn 行快照）
9. 恢复旧版 `latest.json`（覆盖式时代归档）→ 照常可 resume（兼容路径）
10. 故意破坏 jsonl 中间一行 → resume 跳过该行不崩溃，其余正常
11. **懒创建**：启动后不输入任何对话 → 退出，`contextHistory/` 下**不产生新文件**
12. **resume 查看零副作用**：`/resume` 会话1 后**不输入**直接 `/clear` → 无新文件产生，无残留
13. **resume 续写触发复制**：`/resume` 会话1 → 输入第一条新对话 → 生成 `时间戳_会话1续.jsonl`（header + 会话1 全部行副本 turn+todo_snapshot+complete+summary + 本轮）
14. **续写完整性**：续写若干轮 → `/exit` → 再 resume 延续会话 → 看到从会话1开头到续写结尾的完整对话
15. **todo 状态延续**：会话1 末轮 todos = 1/3 → 续写后新文件初始清单为 1/3 → 续写完成后 resume 看到清单从 1/3 演进到最终态
16. **会话1 原始文件不变**：续写后原始归档内容原样（冻结快照验证）
17. **无改名验证**：整个流程 `/exit` 后无任何"改名/归档"动作——文件名字从头到尾不变
18. **崩溃残留（消息）**：turn6 进行中杀进程 → 文件含 turn1-5 → 重启 `/resume` → 显示 turn1-5，turn6 不存在
19. **崩溃后不污染**：崩溃残留文件存在时启动 → 新对话另开新文件，残留文件原样保留
20. **崩溃清单进度不丢（关键）**：同轮建清单 1-5 + 执行到第 4 步杀进程 → 文件含 create/update 的 todo_snapshot 行 → 重启 `/resume` → **m_todos = [1✓ 2✓ 3✓ 4✓ 5○]**（进度保留，非全丢）
21. **complete 行**：全完成收尾 → 文件追加 `{"type":"complete","todos":[...]}` 行；resume 后折叠块可见"任务全部完成"记录
22. **T6 收尾顺序**：先写 complete 行 → 再 emit 对话流 → 再置 m_todoPanelDone（崩溃在任意步骤后 resume 均一致）
23. **撕裂行回退**：故意制造 todo_snapshot 撕裂行 → resume 取前一条可解析快照（进度回退一格，不崩溃）
24. **磁盘满**：写入失败 → warn 日志 + 不崩溃（模拟磁盘满场景）
25. **summary 行**：会话中 `/clear` → 文件追加 `{"type":"summary",...}` 行 → resume 该文件 → 摘要作为 system 消息注入（/context 可见），折叠块显示正常
26. **/exit 无摘要**：`/exit` 关闭的会话文件无 summary 行 → resume 无摘要注入（正常，不报错）
27. **活跃文件标记与 resume**：进行中会话（已建 .jsonl）时 `/resume` 列表 → 当前会话标记 [当前]（与归档混排、不排除）→ `/resume` 选 [当前] → 输入新对话 → 生成"续"文件、`m_activeSessionFile` 切换到续文件 → **原文件冻结在 resume 时点不再被写**（后续 turn 只写续文件）
28. **[当前] 标记**：进行中会话在 `/history` 与 `/resume` 列表中标记 [当前]（重定义 = 活跃文件路径匹配，`list` 的 `activeFilePath` 参数）
29. **续写会话第 2 轮语义**：resume 未完成会话 → 输入第一轮（面板保留、m_resumedFrom 清除）→ 输入第二轮 → 面板按普通新回合清空（数据留 jsonl 历史）

## 六、边界情况与风险

| 情况 | 处理 |
|---|---|
| 崩溃中断（尾行不完整） | 尾行 JSON 解析失败 → 跳过，不整体失败；已 flush 的完整行不丢 |
| **崩溃清单进度** | **不丢**——每次 create/update/clear 已即时写 todo_snapshot（flush），恢复取最后一条；仅当前轮未落盘的消息丢失（§3.3） |
| **todo_snapshot 写一半崩溃（撕裂）** | 撕裂行 JSON 解析失败 → 跳过；恢复取**最后一条可解析的 todo_snapshot**——进度可能回退一格（如 4 步做完但快照撕裂 → 恢复到 3 步），但比全丢强（用户定案接受，§3.4.2 步骤 4） |
| **todo_snapshot 写失败（磁盘满）** | `appendTodoSnapshot` 检测 ofstream 状态，失败 warn 日志（照 `CLFSessionManager.cpp:141-144` 模式）——不静默丢进度 |
| **todo_snapshot 行损坏** | 与 turn 行同规则：JSON 解析失败跳过该行，不整体失败；后续行照常 |
| **todo_snapshot 与 turn 行 todos 冲突** | 恢复取值优先级：最后 todo_snapshot > 最后带 todos 的 turn 行（todo_snapshot 更新，含中间进度） |
| **一轮内多次 update → snapshot 行爆炸** | 可接受（对齐 dsh 事件流）；需知晓体积预期：50 项任务逐项 update = 50 行全量快照（每行含完整清单）。文件体积大于纯 turn 方案，换取崩溃不丢进度（用户定案） |
| **complete 行与 turn 行双写** | 全完成轮：complete 行（T6 收尾）+ turn 行（轮末，含 todos）都写——数据冗余但一致；resume 回显时 complete 行作为"任务全部完成"记录（§3.6 显示格式） |
| **T6 已 emit 但 m_todoPanelDone 未置位就崩溃** | complete 行已写入（T6 先写行再 emit/置位）→ resume 后折叠块可见收尾记录，m_todos 全✓ → 恢复逻辑置 m_todoPanelDone 面板不显示——行为一致（§3.2 complete 行） |
| 文件巨大（长会话） | 追加式 vs 覆盖式的体积权衡：turn 行只存增量消息 + todo_snapshot/complete 行存清单（每次 update 一行，量小）；恢复逐行读 O(n)，可接受 |
| /clear 后新会话 | 关闭当前文件（保留为独立会话），`setActiveSessionFile("")` 置空；下次输入 `beginSessionFile` 新建文件 |
| 崩溃残留文件 | 原样保留，不自动续、不合并、不污染；用户可 /resume 查看 |
| 启动时目录有多个 .jsonl | 仅作为 `/resume` 列表候选（`CLFSessionManager::list`），**不自动选择**为当前文件——懒创建下启动时无当前文件，第一条输入才建（§3.3） |
| **进行中会话出现在 /resume 列表**（2026-09-02 审查发现 + 终审修正） | 取消 latest.json 后，正在写的活跃文件与归档混排。**定案**：`list` 增加 `activeFilePath` 参数，活跃文件**标记 [当前]（不排除）**——resume 活跃文件 = 复制续写（与 resume 任意归档同一行为），续文件创建后 `m_activeSessionFile` 切换、**原文件冻结在 resume 时点不再被写**，无双写乱象（§3.9、另案 §八 补丁 6） |
| **cleanupOld 未适配 .jsonl**（2026-09-02 审查发现） | `CLFSessionManager::cleanupOld`（`CLFSessionManager.cpp:397-418`）只清 .json → jsonl 永不清理。**定案**：扩展名过滤补 .jsonl + `activeFilePath` 参数**排除活跃文件**（cleanupOld 是删除动作，绝不能删正在写的会话——与 list 的"不排除仅标记"语义相反，勿混淆） |
| **摘要机制衔接断点**（2026-09-02 审查发现） | 原设计 /exit 移除 `generateAndCacheSummary` 后，摘要无写入时机且 jsonl 无 summary 载体。**定案**：新增 summary 行类型，/clear 时生成追加（§3.2）；S3 摘要自动触发复用此行类型 |
| resume 查看后 /clear | 零副作用（从未建文件）——懒复制核心场景 |
| 旧 .json 归档 | 永久兼容（扩展名分流），不迁移、不删除 |
| 本轮无消息（异常路径） | turn 行为空 messages 时不追加（照 `saveSession` 空 context 跳过，`CLFAgentLoop.cpp:415-419`）；**但 todo_snapshot 不受影响**（清单变化仍即时写） |
| **跨日 / 时钟回拨的时间戳** | **行序为准，ts 仅展示**——恢复按行序读（非按 ts 排序），回拨不影响正确性；列表排序若用 ts 可能乱，建议排序键用文件名时间戳（创建时刻）而非行 ts |
| m_todoDirty 竞态 | handler 置位 / `appendTurnLine` 轮末读取清除——全在 asyncSubmit 工作线程串行（§3.8），atomic 为防御性 |
| 模型总结 | 就是 assistant 消息文本，天然随 messages 保存，无额外处理 |
| **多实例并发写同一文件** | **不支持**（无文件锁）——同会话不应两个进程同时写；视为单实例约束，文档声明即可 |

## 七、与后续计划衔接

- 本设计是**任务清单 UI 显示**（`设计-任务清单UI显示.md`）的数据层配套——实时面板 + jsonl 历史快照构成完整闭环
- 兼容现有 /resume、/exit、/clear 命令语义，不破坏旧会话（旧 .json 永久可读）
- **S3 摘要衔接（2026-09-02 定案）**：summary 行类型已预留——S3 的"摘要自动触发 + compress_context"落地时，摘要生成后追加 summary 行即可，**无需改 jsonl 行格式**；恢复取最后一条 summary 行的逻辑不变
- 不涉及 dsh 对接决策，可独立排期（约 1-1.5 天）
