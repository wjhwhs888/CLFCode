## 一、解决什么问题

三个相互独立的问题：

| # | 问题 | 现状表现 |
|---|---|---|
| P1 | **触顶报错语义** | 任务 >48 次迭代时，循环耗尽返回 `[Error] Exceeded...`，经 `CLFRepl.cpp:955` 直接显示给用户——用户看到"失败"，但工作其实已做了一部分 |
| P2 | **工具无法声明回合结束** | 工具执行完明明知道"这回合该结束了"（如未来的 ask_user 确认后、subagent 返回后），却无法告诉循环停下来，只能等模型自然停或撞上限 |
| P3 | **模型长时间无响应时无提示** | 深度思考/迷失期间界面无任何提醒，用户不知该等还是该中断（pro 迷失近一小时先例） |

**大任务单回合硬切的深层矛盾**：用户实测大任务需 100+ 次迭代，48 也不够。但**不是要"自动续接"**（用户定案：撞上限自动翻阶段会烧 API）——要的是"能优雅地分阶段做完"：触顶 = 阶段完成点，模型总结进度，用户一句"继续"接着做（上下文跨 turn 保留，CLFCode 已有）。

## 三、设计决策

### 3.1 机制 A：concludesTurn（P0 核心，机制先行，本期零工具声明）

**目标**：工具可静态声明"本次执行后回合应结束"，`CLFAgentLoop` 检测后停止工具循环，但**仍给模型一次收尾发言机会**。

**改动 1：`CLFTypes.hpp` 加字段（静态声明，不做动态返回）**

```cpp
struct CLFToolResult {
    std::string m_toolCallId;
    std::string m_name;
    std::string m_content;
    bool        m_concludesTurn = false;  // 新增
};

struct CLFTool {
    // ...
    bool m_concludesTurn = false;  // 新增：注册时静态声明
};
```

> **pro 修正 ①**：草案 §3.1 写"handler 返回的 CLFToolResult 若 m_concludesTurn=true"——handler 签名是 `string → string`，无法动态返回标志。**动态返回不做**（YAGNI）：本期零工具声明（见下），未来真需要动态决定时再改 handler 签名，改动面可控。

**改动 2：`CLFToolExecutor.cpp`**——构造 result 时复制静态声明：`result.m_concludesTurn = it->m_concludesTurn;`

**改动 3：`CLFAgentLoop.cpp` 检测 + 最终响应**

> **pro 修正 ②**：草案伪代码"concludesTurn → 走到完成分支"语义错误——完成分支拼 `finalContent`（模型文本），工具结果不是模型文本，直接跳过去模型对工具结果零响应机会。dsh 的真实语义是：工具声明结束 → **模型仍做最后一次收尾响应**。

```cpp
bool concluded = false;  // 工具已声明回合结束
for (int iteration = 0; iteration < m_config.m_maxToolCallIterations; ++iteration) {
    // ...请求模型（现有逻辑；parsed.m_content 已累积进 finalContent :319-327）...
    if (CLFProtocolAdapter::hasToolCalls(parsed)) {
        if (concluded) break;
        // ↑ 模型未按声明停止：丢弃其工具调用——不执行、不回填、
        //   不 addAssistantToolCalls。协议安全：模型文本已在 finalContent
        //   （:321-324 累积先于本判定），无悬空 tool_calls 需 result 配对
        // ...addAssistantToolCalls + execute + addToolResult（现有逻辑）...
        for (const auto& result : results) {
            m_context.addToolResult(...);
            if (result.m_concludesTurn) concluded = true;
        }
        continue;
    }
    // 现有完成分支（todo 收尾 + worked + addMessage + 状态点 + return）——
    // 注意：完成分支以 return 结束（:400），不经过循环条件再判定
}

if (concluded) {
    // 模型未按声明停止（发了工具调用被丢弃）：已给最终发言机会，
    // 直接复用完成分支收尾（Done）——完成分支逻辑抽为 finishTurn() helper
    // （concluded-break 与循环内自然停共用，收尾逻辑不复制两份）
    return finishTurn(finalContent, turnStart, StatusKind::Done);
}

// 循环耗尽 → 触顶路径（现有 :417-425 + 收尾请求改造，§3.2）
```

**关键实现约束**：完成分支现以 `return` 结束，`concluded break` 后**不能**落到触顶路径（会误发"已达上限"收尾请求 + Warn）——必须经 `finishTurn()` helper 分流。concluded-break 状态点 = **Done**（concludesTurn 声明的是正常结束；丢弃工具调用是机制行为，非故障）。

**首批声明：无**（草案待讨论 1 裁决）：
- `todo_write` **不声明**——清单全完成 ≠ 回合该结束（模型还需总结汇报机会），且完成分支已有 todo 全完成收尾逻辑（`CLFAgentLoop.cpp:354-385`），声明反而冲突
- 未来候选：ask_user 确认后 / subagent 返回后（届时评估，本期只做机制）

### 3.2 机制 B：触顶优雅收尾 + 总结 + "继续"（P1）

**保留用户定案**：触顶 ≠ 报错；`m_maxToolCallIterations` 是纯内部兜底，用户无需感知；用户一句"继续"自然衔接（上下文已保留）。

**pro 修正 ③（核心）**：草案把"触顶时模型总结进度"押在"系统提示引导 + 轮次注入 + deepseek 实测"上——**模型不知道这是最后一步，触顶瞬间没有机会输出总结**（context 尾部是 tool result）。改为**确定性方案：触顶收尾请求**。

**触顶收尾请求**（循环耗尽后，`CLFAgentLoop.cpp:415` 处）：

1. `m_context.addMessage("user", "已达本轮工具调用上限。请总结已完成的工作与剩余工作，不要调用工具。")`
2. 发起**一次**模型请求——**统一走同步路径**（复用现有 `postJson` + `parseAssistantResponse` + `CLFThinkingIndicator`，不流式）：总结一次性显示，避免为收尾抽 200 行流式 helper（过度抽象）；响应的 tool_calls 忽略
3. 响应文本 → `finalContent` + `m_context.addMessage("assistant", ...)`
4. **独立 try/catch**（pro 修正 ④）：收尾请求在循环**外**，循环内 catch（:402-414）管不到它——异常/队列耗尽（Mock）逸出会砸到 CLFRepl 的 Fatal 分支；收尾请求任何失败都不重试、不逸出 → 降级返回已累积 `finalContent` + 静态提示文案

**触顶收尾输出**：

- 状态点 **Warn（已有，保持）**
- 返回串从 `[Error] Exceeded...` 改为中性文案，如 `(已达工具调用上限，任务可能未完成——输入「继续」可接着做)`（不再以 `[Error]` 开头——它不是错误；补"继续"引导，呼应用户定案的阶段式体验）
- worked 行拼接保持（:417-421 已有）
- **收尾 user 消息与 jsonl**：收尾提示消息仅存 context 内存，不进 jsonl（jsonl 走现有轮末 turn 行机制，无需 J 逻辑改动；与 system 提示同类，resume 重建不依赖）。收尾请求失败时该 user 消息**保留**在 context——连续 user 消息 API 兼容，且下轮用户说"继续"时该提示语义依然有效（模型顺带补上总结），无需 remove 接口

**默认值**：`m_maxToolCallIterations` 代码默认 16 → **48**（pro 建议 + 用户确认 2026-09-02）。理由：① 用户实证校准——16 日常任务误触顶，48 只有"检查整个项目"级大任务才触顶，是实测分水岭；② 语义定位——触顶改造后上限定义"阶段粒度"而非"任务容量"，大任务靠阶段点分段不靠调大数字硬扛；③ 保险丝价值——上限真实职责是止损（空转/迷失时烧钱有界、每阶段有掌控点），100+ 削弱止损且单回合成本失控；④ 与主流 agent 产品 max_turns 兜底同量级。配置项保留可调。

### 3.2.1 收尾路径统一（pro 拍板 2026-09-02，二轮）

五条收尾路径（自然停 / concluded / max-tokens / 触顶 / todo 清单收尾）若各写一套会互相打架（双重 worked、双重清单、状态点覆盖）。**单一汇聚原则**：

| 路径 | 汇聚点 | 状态点 | 说明 |
|---|---|---|---|
| 自然停 | 完成分支（:352-400） | Done | 现有逻辑不动 |
| concluded | 完成分支 | Done | 不产生独立收尾代码——只是循环少转 + 丢弃模型多余工具调用，worked/todo/状态点全复用 |
| max-tokens | 完成分支 | Warn（改） | 完成分支出口按 `finish_reason == "length"` 判定 |
| 触顶 | 触顶路径（:417-425 扩展） | Warn（已有） | 独立但收敛：收尾请求（总结文本入 finalContent）→ worked 拼接（总结在前、worked 在后）→ 返回；**不做 todo 清单收尾**（触顶的"总结"由收尾请求的模型文本承担，避免两套清单收尾） |
| todo 清单收尾 | 完成分支内（:357-385） | 不设 | 现有逻辑不动；触顶路径刻意不经过 |

**轮次注入**：降级为**可选实验**（不阻塞本机制）：system 消息附加"第 N/48 轮"观察 deepseek 是否主动阶段停。若做，实测后决定去留；不做不影响 B 机制。

**空转检测**：不做（草案已降级为可选兜底，本期后置评估）。

### 3.3 机制 C：max-tokens 收尾（P2，小改）

现状占位文本已存在（:325-327）。补一项：完成分支 `finish_reason == "length"` → 状态点 Warn（现状是 Done）。已生成内容保留，不回滚。

**边界**：`length` + 有 tool_calls → 照常执行工具继续循环（length 只约束单次响应 token，下一轮是新响应、新预算），**不**强制收尾——只有 length 且无 tool_calls 进完成分支才置 Warn。

### 3.4 机制 D：Tips 行（P1）

**保留用户定案**：输入框上方一行提示；仅请求处理中显示（绑定 `asyncSubmit.busy()`，空闲隐藏）；常态灰色轮播、静默超阈值浅红；纯提示不干预（agent 不判断、不修复模型思考，决策权给用户）；刷新频率 5s（用户给的范围 5s~10s，取快端）。

**pro 修正 ⑤（数据源裁剪）**：草案"从使用文档（USAGE.md）解析 + 硬编码兜底"是两层数据源 + 格式发明（markdown 里 grep "tips:" 行，文档格式被显示需求绑架）。改为：

- **数据源 = `config/tips.txt`**（config/ 目录约定已有，`CLFConfigLoader.cpp:57-60` 查找链）：每行一条，UTF-8，发布时随包走（`release.ps1:137` 打包清单加 'tips.txt'），用户可编辑。启动加载成功用之
- **兜底 = 代码内置默认条目列表**（含快捷键子集，保证永远有内容）——文件缺失/解析失败时用
- 不再解析 USAGE.md（它是给人读的完整文档，不是轮播数据源）

**pro 修正 ⑥（异常源裁剪）**：草案异常态聚合 3 个源（静默/API 重试/迭代触顶），其中两个**已有显示路径**：

- API 重试中：已有 `emitContent("⚠ ... retry n/N")`（:232-235、:287-290）
- 迭代触顶：触顶收尾已有 Warn + 中性文案（§3.2）

再并入 Tips 聚合 = 重复造轮子。**本期 Tips 异常态只做静默计时一条**；网络/上下文后置评估；若实测发现异常显示分散，再评估聚合。

**静默计时（输出活动计数，pro 修正 ⑦）**：

- **挂载点 = 输出活动计数**，不挂流式回调——后者太窄：同步模式（非交互/收尾请求）无流式回调、工具执行期无流式输出但有进度事件，都会造成计时失真。实现：`ICLFOutput` 加默认虚方法 `notifyActivity()`（或原子活动计数器），`CLFTerminal` 各 emit 入口 +1——覆盖内容/思考/工具进度/错误提示**全部**输出事件
- 判定：活动计数 **300s 无增量** → 浅红 `⚠ 已 Ns 无响应，可 Esc 中断后输入「停止过度思考」继续`（阈值用户定案）
- 输出恢复（计数有增量）→ 回灰轮播
- 与 `m_maxResponseDelaySec`（300s，httplib 总时长超时）不冲突：那是硬兜底，这是软提醒
- **阈值/轮播间隔为构造参数**（默认 300s / 5s）——qa 测试注入小值，不等真实 300s

**布局**（`CLFRepl.cpp:467-477` vbox）：`statusLine` 与 `thinSep` 之间插入 Tips 行；`asyncSubmit.busy()` 为真且 Tips 行非空才渲染。

**类归属（模块化原则）**：新建 `CLFUI/CLFTipsBar.hpp/.cpp`——负责数据加载（tips.txt + 兜底）、轮播索引、静默计时状态、busy 显隐、返回 Element。CLFRepl 只持有并渲染，不内联逻辑。刷新复用 `CLFPeriodicTimer`（5s 单一常量）。

## 六、边界情况

| 情况 | 处理 |
|---|---|
| 多工具并行，一个 concludesTurn | 任一 true → 结束（`\|\|=` 语义） |
| concludesTurn 但工具失败 | 仅成功结果带标志（对齐 dsh：marker 只在成功执行） |
| 迭代上限与 concludesTurn 竞争 | concludesTurn 优先（提前退出），上限是兜底 |
| 中断 vs concludesTurn / 收尾请求 | 中断优先（现有 `m_interrupted` 检查点保持在前） |
| concluded 后模型再发工具调用 | 丢弃、经 `finishTurn()` 正常收尾（§3.1）；状态点 Done |
| concluded 后模型只发工具调用且无文本 | finalContent 空 → 仅 worked 行收尾（§3.1 break 路径） |
| 收尾请求失败 | 不重试，降级：已累积 finalContent + 静态文案（§3.2）；收尾 user 消息保留在 context（连续 user 消息兼容，下轮"继续"自然衔接） |
| 收尾请求后文本仍为空 | 静态文案兜底 |
| max-tokens 且带 tool_calls | 照常执行工具继续循环，不强制收尾（§3.3 边界） |
